## 1. Цель документа

Этот документ определяет **источники данных и сигналы**, используемые в SPA, а также правила доверия, приоритезации и фолбэков.

Цель:
- обеспечить целостность и воспроизводимость данных;
- минимизировать риск манипуляций и сбоев;
- задать единые правила интерпретации сигналов;
- исключить принятие решений на недостоверных данных.

Данные — это **инфраструктура риска**, а не источник доходности.

---

## 2. Принципы работы с данными

- данные всегда считаются потенциально ошибочными;
- ни один источник не считается абсолютной истиной;
- при конфликте данных выбирается более консервативная трактовка;
- деградация качества данных важнее доходности;
- отсутствие данных — валидный стоп-фактор;
- улучшение качества данных не может обходить Risk Policy.

## 3. Классы данных

### 3.1. Market Data (цены и курсы)

Типы:
- spot price;
- TWAP / VWAP;
- oracle price.

Использование:
- расчёт PnL;
- оценка проскальзывания;
- контроль de-peg и резких отклонений.

Expected refresh rate: 30 секунд – 5 минут (зависит от источника).

### 3.2. Protocol Data

Типы:
- TVL;
- liquidity depth;
- APY / rewards;
- protocol parameters и лимиты;
- utilization rate (для lending).

Использование:
- whitelist-контроль;
- liquidity monitoring;
- стратегиям допускается использовать только whitelisted protocol data.

Expected refresh rate: 5 минут – 1 час (DeFiLlama-уровень).

### 3.3. Execution Data

Типы:
- gas price и его волатильность;
- статус транзакций;
- execution slippage;
- комиссии и fees;
- chain reorg detection.

Использование:
- execution cost model;
- decision flow;
- post-trade и post-mortem анализ.

Expected refresh rate: 12 секунд (block time Ethereum L1) или меньше.

### 3.4. Risk & Exposure Data

Типы:
- экспозиции по активам;
- экспозиции по протоколам;
- концентрации (включая лимиты по типу риска из Risk Policy 4.2);
- корреляции (индикативно).

Использование:
- контроль Risk Policy;
- safe-mode и блокировки.

Expected refresh rate: real-time (после каждой транзакции).

### 3.5. Off-chain Signals

Типы:
- audit reports;
- governance proposals;
- security alerts;
- community signals (ограниченно).

Правила:
- off-chain сигналы **никогда** не являются прямым триггером автоматических действий;
- используются только для контекста, мониторинга и эскалации.

### 3.6. Compliance Data

Типы:
- OFAC SDN list;
- EU restrictive measures;
- UN sanctions;
- внутренний blacklist (исключённые протоколы и адреса).

Использование:
- проверка перед добавлением в whitelist (см. Whitelist Policy 4.1);
- ежедневная сверка адресов whitelisted-протоколов и Tail Risk Reserve.

Expected refresh rate: ежедневно.

При попадании whitelisted-адреса в санкционный список → **немедленный** алерт SEV-1.

## 4. Источники данных и приоритеты

### 4.1. On-chain источники

Приоритет:
1) собственные RPC / индексаторы;
2) платные провайдеры (Alchemy / Infura / QuickNode);
3) публичные RPC;
4) сторонние агрегаторы (вспомогательно).

Правила:
- on-chain данные имеют приоритет над off-chain;
- расхождения между RPC трактуются как деградация качества;
- минимум 2 независимых RPC для каждой сети.

### 4.2. Oracle источники

Основные:
- Chainlink (primary);
- Pyth (если применимо, push-based confirmation);
- RedStone (отдельный сравнительный feed для cross-check).

Правила:
- минимум 2 независимых oracle для критичных цен;
- постоянное сравнение значений;
- при расхождении → downgrade качества данных;
- oracle failure → stop decision flow.

### 4.3. Off-chain источники

Типы:
- официальные каналы протоколов (X/Twitter, Discord, blog);
- аудиторы и security teams;
- trusted security feeds (BlockSec, PeckShield, Cyvers).

Ограничения:
- используются только для подтверждения контекста;
- не могут инициировать операции или ребалансы;
- минимум 3 независимых источника для подтверждения значимого off-chain сигнала.

### 4.4. Кандидаты в provider stack

(На момент v0.3 это рекомендации; конкретный stack утверждается через ADR.)

| Слой | Кандидат | Тип | Назначение |
|------|---------|-----|-----------|
| RPC primary | Alchemy / Infura / QuickNode | платный | основной on-chain доступ |
| RPC backup | публичный node + Ankr | смешанный | fallback при отказе primary |
| Indexer | The Graph (для DeFi subgraphs) | платный | агрегированные protocol data |
| Block explorer | Etherscan API | freemium | базовые tx-данные |
| Oracle primary | Chainlink price feeds | бесплатный (on-chain) | основные цены |
| Oracle confirmation | Pyth + RedStone | бесплатный | cross-check |
| TVL & APY | DeFiLlama API | freemium | protocol metadata, TVL |
| Historical | Dune Analytics + own archive | смешанный | paper trading, post-mortem |
| Security feeds | BlockSec, PeckShield, Cyvers (X/Twitter) | бесплатный | early warning |
| Compliance | Chainalysis / TRM (или free OFAC лист) | смешанный | санкционная проверка |

### 4.5. Multi-chain rules

Каждая поддерживаемая сеть имеет **свой полный provider stack** (RPC, indexer, oracle).

Правила:
- cross-chain данные синхронизируются с пометкой блока сети, не времени (timestamp differs across chains);
- сравнение метрик across chains запрещено без явной нормализации;
- bridge между сетями — отдельный риск (см. Risk Policy 7.6 и Whitelist Policy 3.4);
- L2-сеть не может использоваться для критичных операций без подтверждённой ликвидности bridge на L1.

### 4.6. Cost considerations

- на старте допустим **free tier** с явным пониманием rate limits;
- переход на **paid tier** обязателен после 4 недель live-эксплуатации;
- провайдер **не должен** быть единственным — обязательно резервный;
- бюджет на data infrastructure фиксируется в ADR; на момент v0.3 ориентир: $50-150/месяц для одной сети.

## 5. Качество данных и фолбэки

Уровни качества:
- **ok** — данные консистентны и обновляются с expected rate;
- **degraded** — есть расхождения, задержки выше expected, или один источник недоступен;
- **broken** — данные недостоверны, или все источники недоступны.

Правила:
- degraded → ограничение стратегий и Autopilot под вопросом;
- broken → Autopilot OFF + stop decision flow;
- fallback возможен только при сохранении уровня безопасности;
- отсутствие fallback = валидная причина ничего не делать.

Различение нормальной и аномальной латентности:
- латентность ≤ expected refresh rate × 2 → **ok**;
- латентность от × 2 до × 5 → **degraded**;
- латентность > × 5 → **broken**.

Это означает, что Compliance data (expected: 1 раз в день) не считается degraded из-за 6-часовой задержки, а Execution data (expected: 12 секунд) триггерит degraded уже после 30 секунд.

## 6. Сигналы и их интерпретация

Сигналы классифицируются как:
- **info** — информационные;
- **warning** — требуют внимания;
- **stop** — блокируют действия.

Принципы:
- сигнал **не является приказом**;
- сигнал — вход для Risk, Monitoring и Incident контуров;
- автоматические действия возможны только через Monitoring & Alerts.

---

## 7. Хранение и воспроизводимость данных

Требования:
- хранение **raw** данных;
- хранение **агрегированных** значений;
- временные метки (block + wall-clock);
- возможность восстановления состояния системы на любой момент времени;
- **audit trail для каждого сигнала**: какие значения метрик, какой источник, какая severity-классификация.

Данные используются для:
- аудита;
- анализа ошибок;
- post-mortem и обучения системы.

Reconstruct любого сигнала возможен через `alerts.log` + data archive.

### 7.1. Historical data

Для paper trading и анализа требуются исторические данные:

- минимальная глубина: **12 месяцев** на момент запуска paper trading;
- источники: Dune Analytics, DeFiLlama Pro API, дампы с archive node;
- исторические данные хранятся в **собственной базе** (не зависят от продолжающейся работы внешнего провайдера);
- исторические данные **не могут изменяться** задним числом — корректировки только через корректирующие записи (как в Accounting Model 11).

## 8. Ограничения документа

Этот документ:
- не описывает конкретные API endpoints и SDK (это уровень реализации);
- не описывает latency и SLA провайдеров (берутся из их публичной документации);
- не оптимизирует скорость принятия решений.

Он фиксирует **правила доверия к данным**, а не техническую реализацию.

---

## 9. Условия выхода в v1.0

Data & Signals переходит в v1.0 после того как:
- утверждён конкретный provider stack через ADR (раздел 4.4);
- получен опыт работы с реальной деградацией хотя бы одного источника;
- проведена проверка восстанавливаемости (можно ли по архиву данных reconstruct состояние системы);
- проведена проверка multi-chain stack (если используется более одной сети).
