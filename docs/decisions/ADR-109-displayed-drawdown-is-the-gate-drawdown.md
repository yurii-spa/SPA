# ADR-109 · Показываемая просадка считается той же функцией, что и допуск к деньгам

- **Статус:** Accepted (решение принято; реализация — отдельной задачей, см. «Последствия»)
- **Дата:** 2026-08-21
- **Автор/утвердил:** владелец (Telegram, 2026-08-21 09:37:39Z, **вариант A**);
  запись — цикл #331. Карточка: `own-2026-08-18-prosadka-v-otchete-eto-shov-dvuh-simulyatsii`.

## Контекст

Обе записи о деньгах — `equity_curve_daily.json` (трек) и `paper_evidence.json` (доказательная
база) — содержат один и тот же **синтетический кусок прогрева** в начале: 20 дней ровного
прироста 10.80/день, откат на 205 назад, ещё 11 дней по 10.81. Настоящие дни начинаются с
21 июня. Расходились не два писателя — оба брали искусственный кусок с разных мест; там, где
данные настоящие, обе записи совпадают до копейки.

Вредная часть — не сам прогрев (каждый день честно помечен), а то, что **итоговая строка
«максимальная просадка» считается по всем дням разом**, и шов между двумя симуляциями попадает
в неё как просадка **−0.2047 %**. Это не рыночное событие, это арифметика склейки (совпадение
до четвёртого знака). На настоящих днях просадка **0.00 %**.

Допуск к деньгам этим НЕ обманут: `golive_checker` намеренно не читает итоговую строку и считает
`track_evidence.real_max_drawdown_pct` строго по evidenced-дням; в его коде шов прямо назван
подделкой. Обманута **витрина**: в отчёт и на страницу уезжает именно итоговая строка. Рядом —
вторая неаккуратность: когда числа просадки нет вовсе, код подставляет ноль, и «не измерено»
выглядит как «просадки не было».

Владельцу предложены A (показывать по настоящим дням), B (оставить с подписью «включает
прогрев»), C (показывать оба числа). **Владелец выбрал A**, с оговоркой агента: рядом ставится
число реальных дней, чтобы ноль не читался как устойчивость.

## Решение

1. **Витринная просадка считается `track_evidence.real_max_drawdown_pct`** — той же функцией,
   которой пользуется go-live-проверка. Одно понятие — одна реализация.
2. **Отсутствие числа показывается словами** («не измерено»), а не нулём. Подстановка `0.0`
   при пустом входе убирается со всех витринных путей.
3. **Рядом с числом — количество реальных дней**, по которым оно посчитано.
4. **Историю трека никто не переписывает.** Она размечена по дням правильно; меняется только
   отображаемое число. Пороги, RiskPolicy, kill-switch и состав книги не затрагиваются;
   `golive_checker` не меняется — он уже считает верно.

## Последствия

**Что это даёт.** Витрина и гейт перестают считать одно понятие двумя способами. Отчёт покажет
`0.00 %` вместо `−0.20 %`, и это правда: за реальные дни трек не проседал. Расхождение витрины
и гейта опаснее самой цифры — именно оно и закрывается.

**Замер на живых данных 2026-08-21** (для реализации; сделан в цикле #331):
- баров всего **91**, evidenced — **59** (`PAPER_REAL_START` = 2026-06-10);
- `summary.max_drawdown_pct` в файле = **−0.2047** ← шов, уезжает на витрину;
- `summary.real_max_drawdown_pct` = **0.0** ← честное число, УЖЕ лежит в том же файле;
- `portal_data.build_equity_section` уже даёт **0.0** (считает по return-ряду без seed-бара)
  и уже отдаёт `None`, а не ноль, при отсутствии данных — **этот путь чинить не нужно**.

**Почему реализация вынесена отдельной задачей, а не сделана в этом же цикле.** Замер показал,
что витринное число берётся не из одного места, а как минимум из **шести**, и каждое читает
`summary.max_drawdown_pct` напрямую:

| файл | что делает |
|---|---|
| `spa_core/alerts/daily_report.py:199` | отчёт владельцу; при отсутствии — **подставляет 0.0** |
| `spa_core/monitoring/portfolio_health.py:139` | `…get("max_drawdown_pct", 0.0)` |
| `spa_core/compliance/audit_report_generator.py:226,356` | `float(… or 0.0)` |
| `spa_core/family_fund/api/routes/portfolio.py:135` | `…get("max_drawdown_pct", 0)` |
| `scripts/fund_api_server.py:87` | отдаёт как есть |
| `spa_core/golive/readiness_checker.py:179` | публичная готовность |

Починить часть из них — значит получить ровно ту болезнь, против которой принято решение: одно
понятие, посчитанное по-разному в соседних местах. Поэтому правка идёт одной задачей по всем
шести с общим помощником и тестом «ни один витринный путь не подставляет ноль».
Карточка: `agent-vitrinnaya-prosadka-schitaetsya-po-realnym-dnyam`.

**Оговорка честности, названная в карточке владельцем и агентом.** «0.00 % просадки» — слабое
утверждение: реальных дней мало. Поэтому пункт 3 (число дней рядом) — не украшение, а часть
решения.

**Инвариант #8** (каждая claim с evidence-level и датой) от этой правки только выигрывает:
исчезает число, у которого не было честного происхождения.
