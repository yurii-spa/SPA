# ADR-066 · Контур архитектурного соответствия и замыкание петли решений

- **Статус:** Accepted (направление утверждено владельцем в интерактивной сессии 2026-08-05; реализация фазами 0–4, каждая фаза — отдельная приёмка)
- **Дата:** 2026-08-05
- **Автор/утвердил:** сессия-архитектор (Claude) / владелец

## Контекст

Аудит 2026-08-05 (вопрос владельца «кто соблюдает архитектуру и кто читает отчёты?») показал
системный разрыв, измеренный фактами:

1. **За архитектурой агентов не следит никто.** `data/agent_registry.json` протух 19 дней
   (generated 2026-07-17), 2 живых агента (`artifact_freshness`, `swarm_dwell`) отсутствуют в
   реестре, реестр заявляет 80 known / 71 loaded — и ни один сторож не сравнивает
   launchd-флот ↔ реестр ↔ `docs/SYSTEM_MAP.md`. Спроектированные архитектуры (two-layer ADR-004,
   4-ролевый Head-of-Investment ADR-055) не имеют измерителя отклонения «факт vs проект».
2. **Отчёты инвест-офиса пишутся в никуда.** 12 агентов `io_*` ежедневно производят честный
   продукт; `io_chief_investment` корректно сводит его в house_view (конфликты surfaced, не
   усредняются). Дальше цепочка обрывается: единственный потребитель — дашборд
   `/admin/investment-os`, который никто не обязан открывать. Часовой оркестратор house_view
   **не читает** (нет в промпте `scripts/agent_orchestrator.sh`), карточки из находок аналитиков
   не рождаются, house_view с фактической аллокацией никто не сверяет, в daily digest он не входит.
3. **Класс дефекта уже известен и повторяется.** Fail-OPEN мониторы (#29–#38), aggressive_lab
   с ночным перетиранием forward-книги, analytics «90% спит» (owner-directive 2026-07): продюсер
   без обязательного потребителя деградирует молча. Это не единичные баги — это отсутствие
   архитектурного контура, который делает «у каждого продукта есть потребитель» проверяемым фактом.

Существующие сторожа отвечают на другие вопросы: `deployment_drift` — «тот ли код»,
`deployment_acceptance` — «способен ли стартовать», `agent_health` — «жив ли процесс»,
`rules_watchdog` — «соблюдены ли риск-правила». Ни один не отвечает на вопросы
**«соответствует ли флот спроектированной архитектуре?»** и **«замыкаются ли петли решений?»**.

## Принципы (обязательны для всей реализации)

- **P1. Детерминизм в контуре принуждения.** Манифест, сторож, реситы, мост находок — stdlib,
  без LLM (`LLM_FORBIDDEN`). LLM допустим только в синтезе/приоритизации внутри оркестраторской
  сессии (советующий слой) — как и сейчас.
- **P2. Честный UNCHECKED + старение слабых сигналов.** «Не измерено» ≠ «прошло» (инвариант 2),
  но слабый неизмеримый сигнал стареет и уходит из очереди (урок «irreversible UNCHECKED
  starves the queue»); fail-CLOSED навсегда — только для сильных сигналов.
- **P3. Положительный контроль обязателен.** Каждая проверка сторожа рождается с тестом,
  воспроизводящим РЕАЛЬНУЮ аварию из «Контекста» (правило `.claude/rules/deployment.md`).
  Проверка, не видевшая настоящей поломки, не принимается.
- **P4. Сторож сторожей — взаимный, не рекурсивный.** Новых «мета-мета» уровней не строим:
  conformance-агент объявлен в манифесте со своим SLO и виден `agent_health` (свежесть по plist)
  и `system_health` — существующие контуры смотрят за новым, новый — за ними.
- **P5. Не трогать money-path.** Контур ничего не двигает в капитале, RiskPolicy, kill-switch.
  Его выход — файлы-отчёты, карточки и алерты. Авто-ремедиация разрешена только для класса
  «безопасно и обратимо» (см. лестницу ниже).
- **P6. Файлы в git — источник правды; атомарные записи; карточки только через
  `orchestrator_queue.py`** (единственный мутационный API очереди).

## Решение — четыре контура

### Контур A. Машиночитаемая конституция: `architecture/manifest.json`

Первопричина разрыва №1 — архитектура живёт в прозе (SYSTEM_MAP, ADR), а прозу нельзя
диффать с реальностью. Вводится манифест — единый машиночитаемый источник архитектурного
намерения:

```json
{
  "schema_version": 1,
  "agents": [{
    "label": "com.spa.io_quant",
    "layer": "product",              // product | dev | infra
    "role": "analytics",
    "intent": "active",              // active | designed | retired
    "schedule": "daily",
    "produces": [{"artifact": "data/investment_os/quant.json", "slo_hours": 26}],
    "consumes": ["data/apy_ranking.json"],
    "consumer_required": true,        // продукт ОБЯЗАН иметь потребителя
    "governed_by": ["ADR-055"]
  }],
  "artifacts": [{
    "path": "data/investment_os/chief_investment.json",
    "producer": "com.spa.io_chief_investment",
    "consumers": ["orchestrator_protocol", "digest_daily"],
    "slo_hours": 26
  }]
}
```

Ключевое: поле `intent` делает «спроектировано, но не активировано» **явным статусом**, а не
молчаливым дрейфом. Манифест генерируется скриптом из plist'ов + реестра (механика) и
докуривается руками (намерение); дальше правится только через PR/ADR. `agent_registry.json`
остаётся runtime-снимком и сам объявлен в манифесте артефактом со своим SLO — его протухание
станет находкой сторожа, а не археологией. SYSTEM_MAP со временем рендерится ИЗ манифеста.

### Контур B. Детерминированный сторож: `spa_core/monitoring/architecture_conformance.py`

Запуск: launchd каждые 6 ч + обязательный прогон в `deployment_acceptance`-моменты
(до/после изменения дерева). Проверки:

| # | Проверка | Красное состояние (пример из аудита) |
|---|---|---|
| B1 | fleet ↔ manifest в обе стороны | загружен, но не объявлен (`swarm_dwell`); объявлен `active`, но не загружен |
| B2 | свежесть продуктов по SLO | `agent_registry.json` протух 19 дней |
| B3 | замыкание потребления: `consumer_required` ⇒ есть потребитель в манифесте И свежий ресит потребления | 12 `io_*` без единого потребителя |
| B4 | `designed`-архитектуры: ни одного живого процесса раньше активации | активация мимо ADR |
| B5 | согласованность ролей/слоёв (dev-агент не пишет в product-артефакты) | нарушение ADR-004 |

Семантика вердикта — как в `rules_watchdog`: `OK` только когда всё вычислено и прошло; иначе
`UNCHECKED` / `WARN` / `CRITICAL`; exit 0/1/2. Слабые UNCHECKED стареют (P2), сильные
(B1/B3 по money-path-смежным артефактам) — нет. Выход: `data/architecture_conformance.json`
(атомарно). Алерт — только через push_policy (единая push-авторитет, как threat_reactor).

**Реситы потребления** — инженерная основа B3, превращающая «кто-то читает» в факт:
потребитель, поглотивший артефакт, дописывает строку в `data/consumption_receipts.jsonl`
(append-only): `{"artifact": "...", "consumer": "...", "consumed_at": "...",
"producer_generated_at": "..."}`. Оркестраторская сессия, digest, gap-analyzer пишут реситы;
сторож проверяет их наличие и свежесть. Нет ресита при `consumer_required` — красный факт,
не мнение.

### Контур C. Замыкание петли решений

- **C1. `house_view_gap` (детерминированный, в дневном цикле):** сверяет house_view +
  RED/YELLOW сигналы аналитиков с фактической аллокацией и риск-постурой; расхождения
  («офис видит возможность X с evidence ≥ L3, книга её не держит и отказ не назван» /
  «офис RED по протоколу, книга держит») → `data/house_view_gap.json`. Только сверка,
  никаких действий.
- **C2. Мост «находка → карточка»: `scripts/findings_to_cards.py`.** Потребляет
  conformance-отчёт + house_view_gap + blocking-сигналы аналитики. Дисциплина против спама:
  стабильный ключ находки (dedup), гистерезис (карточка только на новую/эскалировавшую
  находку), rate-limit ≤ 5 карточек/сутки (остальное — в отчёт с пометкой «отложено», без
  молчаливого обрезания), авто-закрытие карточки при исчезновении находки (со ссылкой на
  эвиденс). Маршрутизация: CRITICAL → `needs-owner` + Telegram-notify; остальное →
  agent-backlog. Карточки — только через `orchestrator_queue.py create`.
- **C3. Протокол оркитратора (`docs/ORCHESTRATOR_PROTOCOL.md` + промпт
  `scripts/agent_orchestrator.sh`):** обязательный шаг цикла — прочитать
  `chief_investment.json`, `_health.json`, `architecture_conformance.json`,
  `house_view_gap.json`; записать реситы; взять ОДНУ карточку из авто-бэклога моста при
  отсутствии явных заданий. (Изменение мандата утверждено настоящим ADR.)
- **C4. Daily digest:** одна строка house_view (postура + топ-конфликт) + одна строка
  conformance (OK/WARN/CRITICAL + счётчики) — владелец видит работу петли в Telegram,
  не открывая админку.

### Контур D. Самовосстановление и самоулучшение

**Лестница ремедиации (строго по порядку, выше — только безопасное):**

| Ступень | Условие | Действие |
|---|---|---|
| R1 авто | реестр/снимок протух, генератор жив | перегенерировать снимок (read-only скан, обратимо) |
| R2 авто | агент мёртв | уже покрыто `self_heal` (не дублируем) |
| R3 карточка | нет потребителя / designed-дрейф / ролевое нарушение | карточка через мост C2 |
| R4 owner | ретайр агента, изменение SLO/порогов, активация designed-архитектуры | только `needs-owner` + ADR |

Ничто в лестнице не касается RiskPolicy/kill/капитала (P5).

**Петля самоулучшения (еженедельный `loop_retro`, детерминированный):**

- `data/loop_health.json` — метрики самой петли: находка→карточка→закрытие (латентность),
  доля повторных находок (рецидив = системная причина), доля карточек моста, взятых в работу.
- **Hit-rate аналитиков** — по образцу `shadow_trigger_eval`: RED-сигнал аналитика
  подтвердился ли последующей деградацией? возможность из house_view была ли реальной
  (по последующим evidenced APY)? Неоцениваемое — UNCHECKED, не угадываем.
- Еженедельный отчёт `data/loop_retro.json` + строка в digest: кандидаты на честный ретайр
  (аналитик, чьи сигналы за N недель ни разу не привели ни к действию, ни к подтверждению —
  ровно owner-directive «работать или честно закрыть»), рецидивные находки, калибровка.
  Все выводы ретро — карточками (R3/R4), никогда молчаливым действием.
- **Храповик:** пороговые базы петли (максимум допустимых orphan-продуктов, латентность)
  фиксируются файлом-базой и могут только улучшаться (по образцу `frozen_date_baseline`).

## Разобранные отказы (почему это не сломается привычным способом)

| Риск | Ответ конструкции |
|---|---|
| Спам карточек | dedup-ключ + гистерезис + rate-limit + авто-закрытие (C2) |
| Ложно-красный сторож | положительные контроли в ОБЕ стороны (P3); чинить сторожа, не глушить (deployment.md) |
| UNCHECKED-голодание очереди | старение слабых сигналов (P2) |
| Манифест сгниёт, как SYSTEM_MAP | манифест проверяется сторожем в обе стороны (B1): его протухание — CRITICAL, гнить молча не может |
| Слепая зона на самого себя | P4: conformance объявлен в манифесте, за его свежестью следит agent_health; за агентами — он |
| Конкурентные писатели очереди | единственный мутационный API `orchestrator_queue.py`, атомарные записи |
| Рост бюрократии | один сторож + один мост + два расчётных файла; новые «мета-уровни» запрещены P4 |

## Фазы реализации (каждая — отдельная карточка и приёмка)

- **Фаза 0** — схема манифеста + генератор + курированный manifest.json (все 71+9 агентов,
  intent проставлен честно). Приёмка: манифест полон, `designed` ≠ `active` явно.
- **Фаза 1** — сторож B1–B5 + тесты-репродукции сегодняшних находок + launchd-агент
  (деплой через gate, ≤3 агентов). Приёмка: на текущем проде сторож КРАСНЫЙ ровно по
  находкам аудита 2026-08-05 (положительный контроль на живой системе), после Фаз 2–3 — зелёный.
- **Фаза 2** — реситы потребления в первых потребителях (оркестратор-протокол C3, digest C4).
  Приёмка: B3 для `io_*` перестаёт быть красным честным путём.
- **Фаза 3** — house_view_gap + мост findings_to_cards + интеграция в цикл. Приёмка:
  искусственная находка проходит путь находка→карточка→закрытие без рук.
- **Фаза 4** — loop_health + hit-rate + weekly retro + храповик. Приёмка: первый ретро-отчёт
  с честными UNCHECKED и ≥1 обоснованным кандидатом-выводом.

## Последствия

- Плюсы: архитектура становится диффабельной и принуждаемой; «продукт без потребителя»
  ловится за часы, а не за месяцы; отчёты офиса получают обязательного читателя и путь в
  бэклог; петля меряет и улучшает сама себя; всё — детерминированно и тестируемо.
- Минусы (честно): +1 агент, +2 файла-протокола, дисциплина ресит-строк у потребителей;
  манифест требует курирования при каждом изменении флота (это цена явности намерения).
- Owner-gated остаётся: ретайр агентов, активация designed-архитектур, изменение SLO-порогов,
  любые изменения RiskPolicy — контур их не касается по построению.
- Затронуто: новые `architecture/manifest.json`, `spa_core/monitoring/architecture_conformance.py`,
  `scripts/findings_to_cards.py`, `spa_core/paper_trading/house_view_gap.py` (имена уточняются
  в фазах); правки `docs/ORCHESTRATOR_PROTOCOL.md`, `scripts/agent_orchestrator.sh`,
  digest. RiskPolicy/kill-switch/execution — не затронуты.
