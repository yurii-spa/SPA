# ADR-422 · У headless-запуска Claude не было срока, а у его потомков — владельца

- **Дата:** 2026-09-19
- **Владелец:** @yurii
- **Статус:** принято · **Phase 1 активна** (только `com.spa.orchestrator`)
- **Заказ:** решение владельца/ARB 18–19.09 (канарейка срока, фаза 1)
- **Область:** доставка кода · жизненный цикл агентов · владение процессами
- **Предшественники:** ADR-152 (зеркало origin для локальных сессий) · ADR-214
  (инструкции возятся в прод вместе с кодом) · ADR-347 (коды сторожа голода)

## Проблема

Часовой цикл звал `claude -p` **без срока**. launchd не поднимает второй экземпляр той же
метки, поэтому ОДНО зависание останавливало часовой такт навсегда и молча. Замер 18.09:
девять подряд прогонов заняли **20.9…80.2 мин**, все вышли `0` — у здоровой работы предел
есть, у зависания его нет.

Вторая половина проблемы вскрылась при разборе первой: **у потомков сессии нет владельца.**
Живые улики на машине в момент решения — два полных прогона `pytest` с `ppid=1` и
**собственными сессиями** (`sid=46977`, `sid=99172`), вожаки которых мертвы, и каждый держал
`git worktree` прод-репозитория своим рабочим каталогом, то есть писал в репозиторий.

## Что измерено (а не предположено)

| Вопрос | Ответ | Как измерено |
|---|---|---|
| Есть ли `timeout`? | **НЕТ** ни `timeout`, ни `gtimeout` | coreutils не установлен; `timeout N claude …` дал бы 127 и НЕ вызвал бы Claude вовсе — то есть выключил бы агента, оставив в логе код, похожий на сбой Claude |
| Годится ли группа процессов границей владения? | **НЕТ** | Claude Code запускает оболочку КАЖДОГО Bash-инструмента лидером СВОЕЙ НОВОЙ сессии (`pgid == sid == pid`) |
| Годится ли обход по `ppid`? | **НЕТ в одиночку** | у обоих сирот `ppid=1` уже при живом родителе-цикле |
| Видно ли окружение чужого процесса? | **частично** | `ps -E` отдаёт окружение **71 из 621** процесса: `python` и `node` да, `/bin/bash` и `/bin/sleep` нет, `git` НЕ ИЗМЕРЕНО. Дело не в размере окружения (проверено до 46 КБ) |
| `set -u` в bash 3.2 обрывает с нулём? | **нет, кроме одной формы** | `-c` → 127, файл-скрипт → 1, **внутри `$( … )` → скрипт НЕ обрывается вовсе и доходит до конца с кодом 0**, получив пустое значение |

## Решение

**Единый stdlib-прибор `scripts/claude_run_with_timeout.py`** (инвариант #4 соблюдён; LLM
внутри нет). Обе обёртки зовут Claude только через него.

**Граница владения — положительное доказательство**, объединение ЧЕТЫРЁХ приборов:
`tree` (обход `ppid`) · `group` (группа запуска) · `session` (сессия запуска) · `run_id`
(метка `SPA_RUN_ID` в окружении — единственная, что переживает `setsid`, переподчинение к
`init` и смену группы). Слепота `run_id` **названа в самом модуле**, а не подразумевается.

**Две ветки, намеренно несимметричные:**

- **НОРМАЛЬНЫЙ выход:** отделившихся потомков **НЕ убивать**; только снять улику и назвать
  аномалией. Замер, из которого это решение: цикл `cycle-80595` вышел `0` в 10:38 18.09 и
  ШТАТНО оставил живой полный прогон. Убить его молча значило бы менять протокол работы
  циклов под видом починки срока. Следствие: сбой переписи на этой ветке НЕ меняет код
  возврата.
- **TIMEOUT:** сначала **улика**, потом завершение ТОЛЬКО тех, чья принадлежность ЭТОМУ
  `RUN_ID` доказана; **SIGTERM → grace → SIGKILL**; неоднозначный или чужой процесс **не
  трогается никогда**.

**Коды возврата** (различимость исходов, инв. #17):

| Код | Значение |
|---|---|
| **124** | сорвано по сроку, владение закрыто ПОЛНОСТЬЮ |
| **125** | сорвано по сроку, но владение НЕ закрыто **либо** состояние не измерено |
| иной | код самого Claude, проброшен без изменений |

«Не измерено» никогда не выдаётся за «чисто»: 124 недостижим, если хоть один прибор отказал.

**Пороги — ручки окружения:** `SPA_ORCHESTRATOR_TIMEOUT_S` (14400 с = 4 ч, ≈3× измеренного
максимума и выше полного прогона тестов 2:42–2:58), `*_KILL_GRACE_S` (120 с), такт опроса
2 с одной константой на функцию и на CLI.

## Два дефекта, найденные ТЕСТАМИ, а не перечитыванием

1. Перепись «кого убивать» и перепись «закрыто ли владение» шли ОДНИМ набором приборов —
   при выключенном приборе метки прибор не видел того, кого не смог убить, и возвращал
   **124 «владение закрыто полностью»**. Вердикт теперь всегда меряется ПОЛНЫМ набором.
2. Зомби виден в `ps`, и `kill -0` по нему ПРОХОДИТ — недожатый потомок засчитывался бы
   выжившим и давал **ложный 125**. Зомби исключены, с контролем на синтетической таблице.

## Архитектурный факт (фиксируется отдельно)

**`origin/main` — authoritative source для кода рантайма.** Прод-дерево **сходится с ним
автоматически** через `scripts/code_sync_from_origin.sh` (шаг внутри `agent_template.sh`,
троттлинг 600 с; НЕ отдельный launchd-агент — метки `com.spa.code_sync` не существует).

**Ручная доставка файлов в прод НЕ является допустимым путём деплоя.** Это не мнение, а
замер 18.09: доставка четырёх файлов в прод в 12:19:18 была выровнена синком обратно к
origin **через 70 секунд** (12:20:28, whole-dir checkout). Уцелели только два файла, которых
origin не несёт, — синк удалять их отказывается и говорит об этом вслух. Итог такой доставки
— полусостояние, где прибор лежит в дереве, обёртка его не зовёт, а тест объёма краснеет.
Путь в прод лежит ЧЕРЕЗ origin, и другого нет.

## Правило наблюдения Phase 1

Наблюдаем **только `com.spa.orchestrator`**. Расширение на `com.spa.novel_edge_rnd` **не
делать**, если появится хоть одно: **rc 125** · **неожиданный TIMEOUT** · **утечка замка** ·
**новая регрессия мониторинга**.

**Лимит сессии Claude дефектом прибора НЕ считается.** Форма известна и измерена: цикл живёт
секунды и выходит `claude exit 1`, в логе дословно `You've hit your session limit · resets
<время>`. Пример: 18.09 18:01:44 → 18:01:50. Фиксировать фактический rc и лог, останавливаться
для ARB — не чинить.

## Чего это решение НЕ доказывает

**Ветка таймаута в проде ни разу не исполнялась** — здоровый цикл до срока не дошёл и не
должен был. Она покрыта 20 тестами (эскалация SIGTERM→SIGKILL на игнорирующем SIGTERM
дереве, отделившийся потомок с `ppid=1`, посторонние с чужой и с отсутствующей меткой,
отказ прибора состояния → 125 и никогда 124, улика до разрушения), но первое реальное
срабатывание впереди. Пороги 4 ч / 6 ч стоят на замере, который может сдвинуться: полный
прогон вырос 2:42:50 → 2:58:15 за сутки.

## Follow-up (записано, НЕ исправлено)

Каждый пункт заслуживает своей карточки; здесь — только фиксация, работы по ним не велось.

1. **Гонка `code_sync` за ссылку.** Два одновременных прохода: `cannot lock ref
   'refs/remotes/origin/main'` → один честно доложил `FETCH_FAILED`, соседний сошёлся.
2. **Бюджет свежести `novel_edge_rnd` — 26 ч при расписании вт/пт**, то есть КОРОЧЕ
   собственного такта агента (3.5 суток). Предупреждение `log stale 33.7h` — календарь, а не
   поломка.
3. **pre-commit красен на чистом `origin/main`:** `[1/7]` bare exceptions на
   `spa_core/monitoring/cio_outcome_independence.py:733,761`; `[4/7]` секреты — на
   документации паттернов и на собственном исходнике гейта. Гейт обрывается на первой
   проверке, поэтому 2–7 не исполнялись ни разу.
4. **Нет проверенной процедуры отката плохого коммита с origin.** Выделенного инструмента
   нет; `docs/DEPLOYMENT_POLICY.md` упоминает «git revert + restart launchd» одной строкой в
   38-строчном файле. Прод при этом защищён сам: пре-синк-снимок + импорт-проба → `ROLLED_BACK`.
5. **`scripts/git_autopush.sh` — спящий канал прод→origin** (`git add -A` + `--no-verify` +
   `git push HEAD:main`), не подключён ни к одному агенту. Подключат — утащит на origin любой
   локальный мусор прод-дерева.
6. **Давление памяти / `findings_bridge`.** Полный прогон убит системой на 83 %; в момент
   смерти `bitcoind` держал 5.2–8.4 ГБ, а `findings_bridge --run` — **2.1–4.0 ГБ за 54 минуты
   работы** и рос.
7. **Устойчивость к лимиту сессии Claude.** Сегодня цикл просто теряет свой час.
8. **Маршрутизация провайдера Claude Code:** Claude Subscription + Ollama Local — отдельное
   решение, здесь только помечено.
