# ADR-145 — «А прогон-то БЫЛ?» — сторож живости CI на PR

- **Статус:** Accepted
- **Дата:** 2026-08-26
- **Решение владельца:** 2026-08-26, дословно: «**почини это тоже сам**» (после того как я
  назвал находку двумя словами: «CI не запустился, а выглядело как проверено»). Закрытие
  карточки агентом — по [ADR-146](ADR-146-agent-may-close-cards.md).
- **Карточка:** `nimbalyst-local/tracker/owner-decision-ci-molcha-ne-zapustilsya-na-pr-zelenaya.md`
  — принят **вариант А** (сторож на отсутствие прогона) **плюс вариант Б** (ручной вход
  недостающим workflow), см. §5.
- **Связано:** инвариант #17 · `.claude/rules/deployment.md` («четыре вопроса — четыре разных
  сторожа») · ADR-129
- **Домен:** CI. Капитал не двигается, RiskPolicy не тронута, money-path не затронут.

## 1. Что случилось

У PR #46 событие `pull_request` **не создало ни одного прогона GitHub Actions**. Не «прогон
упал» — прогона не было вовсе. На странице PR стояла одна зелёная галочка Cloudflare, и PR
выглядел проверенным.

Замер:

| head | прогон `ci.yml` |
|---|---|
| `7543ba7`, `91f9c07`, `91eddc7`, `a4fd5f9`, `f1a5ef1` … | есть |
| **`c7586a5`** (PR #46) | **нет вообще** |

`paths-ignore` ни при чём: в диффе PR **пять `.py`-файлов**. Actions при этом жив — ручной
`workflow_dispatch` создал прогон сразу.

**Причина, по которой событие не сработало, НЕ УСТАНОВЛЕНА.** Из API её не видно, и выдумывать
её я не стал: ADR фиксирует то, что измерено. Поэтому решение — не «починить причину», а
**сделать этот исход видимым**, что ценно независимо от причины.

## 2. Почему это тот же класс, что мы чиним весь день

«Не измерено» стало неотличимо от «прошло» — и неотличимо **в успокаивающую сторону**. Ровно
то, что запрещает инвариант #17 у чисел. Только здесь молчит не число и не тест, а **весь CI**.

Третий случай одного класса за сутки:

1. утром — `test_no_new_agent_was_introduced` зеленел на **пустом glob'е** (другой CWD);
2. днём — `test_agent_may_close_cards.py` собрал **ноль тестов** (классы `The*` при
   pytest-умолчании `Test*`) и был зелёным;
3. вечером — событие **не создало прогона**, а страница PR осталась зелёной.

Общая форма: *«зелёный» — утверждение о том, что проверки ПРОШЛИ, а не о том, что они
ВЫПОЛНЯЛИСЬ.* Второе приходится утверждать отдельно, и до сегодня этого не делал никто.

## 3. Главное свойство решения: сторож НЕ ЖИВЁТ на событии, которое сторожит

Очевидное решение — проверка на самом PR — **не работает по построению**: не сработало событие,
значит не запустилась и проверка. Сторож обязан иметь **независимый вход**.

`.github/workflows/pr-ci-liveness.yml` — `schedule` (ежечасно) + `workflow_dispatch`, и **без
`pull_request`**. Это закреплено тестом отдельно: `test_it_does_not_trigger_on_pull_request`.
Ровно та ошибка, за которую проект уже платил: зелёный ответ на один вопрос не означает ответа
на другой.

Час выбран потому, что PR живут часами; сутки ожидания обесценили бы проверку.

## 4. Три исхода, а не два

`scripts/check_pr_ci_runs.py` (stdlib, сеть — вход, не окружение):

| исход | что значит | код возврата |
|---|---|---|
| `checked` | у head'а есть прогоны Actions, число названо | 0 |
| `no_runs` | прогонов **НОЛЬ** — PR не проверен | 1 |
| `unchecked` | измерить не удалось (нет токена, сеть, отказ API) | 2 |

Третий не выдаётся за успех: **молчание сторожа обязано отличаться от его одобрения.** Живой
замер из контейнера без токена: API отвечает `403`, сторож печатает `unchecked` и возвращает
**2**, а не 0.

**Сторонние галочки не считаются прогоном.** Это сердце аварии: галочка Cloudflare БЫЛА,
прогонов НЕ БЫЛО, и PR выглядел зелёным. Считай сторож любую проверку прогоном — он молчал бы
ровно в том случае, ради которого написан. Закреплено тестом.

**Красный прогон — это прогон.** Сторож отвечает на «прогон БЫЛ?», а не «прогон зелёный?»:
красный CI ловят другие проверки, а смешать два вопроса — значит получить сторожа, отвечающего
не на свой.

## 5. Вторая половина: ручной вход недостающим workflow

Когда событие не срабатывает, единственный **законный** способ добрать проверку — ручной
запуск: пустой коммит и «закрыть-открыть PR» запрещены прямо. Четыре workflow гейтили PR, но
ручного входа не имели: `generated-docs-integrity`, `spa-lint`, `numbers-lint`, `owner-gate`.
Добавлен `workflow_dispatch` каждому.

Сторожит это не список в чьей-то голове, а тест `test_every_pr_gating_workflow_can_be_dispatched`:
он перебирает **все** файлы `.github/workflows/*.yml`, и любой будущий workflow с
`pull_request:` без ручного входа покраснеет сам. Проверка отказывается проходить на пустом
списке файлов — урок утреннего пустого glob'а.

## 6. Приёмка

- `spa_core/tests/test_pr_ci_liveness.py` — **20 тестов + 11 subtests**. Положительный контроль
  воспроизводит аварию дословно: head `c7586a5`, единственная проверка — «Cloudflare Pages»
  ⇒ вердикт `no_runs`, код 1. Обратные контроли: настоящий прогон ⇒ `checked`; **красный**
  прогон тоже `checked`; ноль открытых PR — не дефект. Отсутствие замера: отказ сети на списке
  PR и на прогонах ⇒ `unchecked` (код 2), PR без `head_sha` ⇒ `unchecked`, а не «прогонов ноль»;
  найденный дефект не теряется за «не измерили соседа»; мусор из API не роняет сборщик.
- Тест на вход сторожа: `schedule` есть, `pull_request` **нет**, ручной вход есть,
  `actions: read` запрошен (без него сторож стал бы вечным `unchecked`).
- Живой прогон без токена: `403` ⇒ `unchecked`, код **2**.
- YAML всех пяти изменённых workflow разбирается; триггеры проверены поимённо.

## 7. Что этим решением НЕ сделано

- **Причина несработавшего события не найдена** и не выдумана. Сторож делает исход видимым —
  это ценно независимо от причины, но причиной не является.
- Сторож НАЗЫВАЕТ: он ничего не запускает и не перезапускает. Автозапуск при обнаружении —
  отдельное решение с отдельной ценой (он бы жёг раннеры на каждом ложном срабатывании).
- Проверка не блокирует PR и не может: блокировать нечего, если ничего не стартовало.
