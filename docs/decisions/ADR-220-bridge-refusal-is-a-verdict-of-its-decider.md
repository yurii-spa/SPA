# ADR-220 · Отказ моста «перенести нечем» — вердикт РЕШАТЕЛЯ, и у него есть срок годности

- **Статус:** Accepted
- **Дата:** 2026-09-03
- **Автор/утвердил:** цикл #471 (автономно по ADR-101, класс «сторож отвечает не на тот вопрос»)

## Контекст

Замер, живой, на настоящих файлах прод-дерева 03.09.2026:

| время (UTC) | что произошло |
|---|---|
| 11:46:08 | `findings_bridge` пишет отчёт: `ДОСТАВКА КАРТОЧЕК PARTIAL: уехало 2, ЗАСТРЯЛО 2`; по обеим карточкам `…gas-price-agent…` причина — «расхождение с origin не сводится к строке `status:` и следу `status_trail:` — перенести правку автоматически нечем; **сделать это вручную** из worktree на origin/main» |
| 16:04:31 | коммит `3425bd28` ([ADR-219](ADR-219-card-delivery-rebases-onto-an-ahead-origin.md), цикл #470) учит `card_delivery.rebase_onto_ahead_origin` везти РОВНО этот случай: origin обогнал прод по телу карточки и по захвату |
| 17:2x | обязательный шаг 0-офис печатает отчёт 11:46 дословно; цикл #471 объявляет владение карточками и начинает переносить их руками |
| 17:2x | перед самой правкой цикл #471 перемеряет основание: `rebase_card(local, remote)` строит кандидата для **обеих** карточек. Ручная работа была бы дублем поверх уже работающей автоматики; правка карточек откачена |

Возраст отчёта (5.6 ч) на этот вопрос не отвечает: он меряет, **давно ли ходил мост**, а не
**сменился ли под ним тот, кто выносит вердикт**. Ровно тот же класс, что цикл #337 закрыл для
конституции: тогда `architecture_conformance` три часа печатал `OK` о манифесте, который уже
сменился, и появилась проверка «ВЕРДИКТ О ПРЕЖНЕМ ПРЕДМЕТЕ» (`_subject_drift` в
`scripts/consume_office_reports.py`). Реестр предметов `_SUBJECT` с тех пор содержал **ровно один
вход** — и отчёт моста в него не входил.

Отличие этого случая от #337 в цене: там вердикт был ложно ЗЕЛЁНЫМ, здесь он ложно **приказывает
человеку работать руками** — то есть тратит цикл и, если приказ выполнить, гонит ручной коммит
наперегонки с автоматическим.

## Решение

1. **Предмет вердикта моста об отказе — сам решатель `spa_core/monitoring/card_delivery.py`.**
   Именно он отвечает «переносим» или «переносить нечем», и оба отказа отчёта (доставка карточек
   и доставка следа ответа владельца) приходят из него. Константа — `findings_bridge.DECIDER_REL`.
2. **`findings_bridge` пишет в отчёт блок `inputs`** с `sha256`/`mtime` решателя — в ТОЙ ЖЕ форме,
   что и `architecture_conformance`: обе стороны зовут одну функцию `subject_inputs(root, rels)`
   (у неё появился параметр путей). Вторая копия функции разъехалась бы с читателем молча.
3. **`_SUBJECT` в шаге 0-офис получает второй вход** — `findings_bridge_report.json` →
   `spa_core/monitoring/card_delivery.py`. Дальше работает уже существующий `_subject_drift`:
   сверка по СОДЕРЖИМОМУ, `mtime` — только для отчётов старого образца, нечитаемый предмет —
   «НЕ ИЗМЕРЕНО» вслух (fail-CLOSED, инвариант 2).
4. **Карточки предметом не объявляются.** Они — живое состояние, находку давал бы каждый прогон,
   и строка обесценилась бы (правило реестра `_SUBJECT`, введено #337). Решатель — код: 7 правок
   за 30 дней, то есть находка возможна примерно раз в четыре дня и живёт до ближайшего такта
   моста.

## Последствия

- **Плюс.** Читатель отличает «перенести нечем» от «уже есть чем»: обе стороны сравнения названы
  хэшами прямо в строке, и находка печатается ДО приказа «вручную» (порядок закреплён тестом —
  дошедший до слова «вручную» раньше уже встал и пошёл работать руками).
- **Минус, честно.** Любая правка `card_delivery.py` — включая косметическую — даёт находку до
  следующего прогона моста. Это осознанный обмен: тот же обмен принят для манифеста в #337, и
  сверка по содержимому (а не по `mtime`) снимает ложные срабатывания холостого синка, который
  переписывает файл байт-в-байт перед КАЖДЫМ запуском.
- **Что теперь нельзя.** Объявлять в `_SUBJECT` предмет, который является живым состоянием
  (`data/*`, карточки): проверка обесценится собственным шумом.
- **Затронуто.** `spa_core/monitoring/findings_bridge.py` · `spa_core/monitoring/architecture_conformance.py`
  (`subject_inputs` получил параметр, поведение по умолчанию не менялось) ·
  `scripts/consume_office_reports.py` · новый `spa_core/tests/test_office_verdict_about_previous_decider.py`
  (8 проверок; три мутации проводки — читатель не знает отчёта, мост не пишет `inputs`, писатель и
  читатель зовут разные файлы — краснят набор, восстановление зеленит).
  Ратчет `test_every_declared_subject_exists_in_this_repo` покрывает новый вход автоматически.
- **Инварианты не тронуты:** risk/kill/RiskPolicy не касается; тесты не ослаблялись (инвариант #16).
