# ADR-171 · Кэш-буфер сравнивается в центах: план РОВНО на 5 % — не нарушение

- **Статус:** Accepted
- **Дата:** 2026-08-29
- **Автор/утвердил:** архитектор; мандат владельца 29.08 («диагностика и починка»)
- **Затронуто:** `spa_core/risk/policy.py` — `RiskPolicy.check_new_position`, пункт 5

## Контекст

Трое суток подряд перераздача ADR-072 отклонялась повторным гейтом со словами

```
✗ After trade, cash buffer 5.0% < minimum 5.0%
```

и **33.7 % капитала стояли без работы**. Дневная доходность упала **4.21 % → 3.17 %** и
попала в трек. Книга при этом не самоисправлялась: цель совпадала с застрявшей книгой,
`traded: False`, `|Δ| = $0` — сколько бы циклов ни прошло.

Утверждение «5.0 % меньше 5.0 %» ложно как арифметика. Но воспроизвести отказ снаружи не
удавалось: **три независимые реконструкции** (по округлённым числам журнала, по точным
девятнадцатым долям, через сам класс `PortfolioState`) давали остаток `5000.000000000001`, а
вызов НАСТОЯЩЕГО гейта на восстановленной цели — `APPROVED`, нарушений ноль.

Разрыв закрыла запись отказа (мандат владельца): в журнал стала попадать сама поданная цель
без округления. И она сразу показала две вещи.

1. **Округление стирало улику.** Первая версия записи округляла ноги до центов, и по ней
   отказывать было не за что: сумма ровно `95000.00`, остаток ровно `5000.00`. Настоящие
   ноги — `22105.260000000006`, `6578.950000000001`: спор идёт о последних битах.
2. **Способ счёта решает.** `PortfolioState.cash_usd` это `капитал − sum(позиции)`, поэтому
   на каждой ноге остаток получается как `капитал − sum(предыдущие) − сумма`, а НЕ
   последовательным вычитанием. На реальных числах:

```
капитал − sum([37894.74, 22105.260000000006, 18947.37, 9473.68]) − 6578.950000000001
  = 4999.999999999996   →   доля 0.04999999999999996   <   0.05   ⇒ ОТКАЗ
```

Последовательное вычитание тех же чисел даёт ровно `5000.0`. То есть план, ложащийся **ровно
на обязательный буфер**, отвергался из-за ошибки в последних битах — и стоил трети капитала
каждый цикл.

Усилитель: отказ ОДНОЙ ноги отменяет перераздачу ЦЕЛИКОМ (`$28 684` из-за `$6 579`).

## Решение

Сравнивать буфер **в центах**, а не в долях:

```python
_min_cash_usd = state.total_capital_usd * self.config.min_cash_pct
if round(remaining_cash, 2) < round(_min_cash_usd, 2):
```

**Порог НЕ изменён.** `min_cash_pct` остаётся `0.05`, `RiskPolicy` остаётся `v1.0`. Изменена
только точность сравнения: деньги измеряются в центах, и полцента ниже буфера — не нарушение
буфера. Настоящее нарушение (на цент и больше) отвергается по-прежнему.

## Почему это не ослабление гейта

Инвариант #1 (`approved=False` не переопределяется) не затронут: гейт по-прежнему последнее
слово, изменилось лишь то, считает ли он нарушением шум последнего бита. Граница проверена в
ОБЕ стороны и закреплена мутациями:

| мутация | что краснеет |
|---|---|
| вернуть сравнение в долях | воспроизведение аварии 29.08 |
| допуск в доллар вместо цента | «на цент ниже» и «на доллар ниже» |
| снять проверку буфера | все три контроля настоящего нарушения |
| тихо снизить порог до 4 % | контроль неизменности порога |

`test_cash_buffer_boundary_in_cents.py` — положительный контроль на РЕАЛЬНЫХ числах прода из
записи отказа, плюс отдельный класс «правило не ослаблено» (цент / доллар / тысяча ниже
буфера — отвергаются; ровно на буфере — проходит).

## Следствия

Перераздача, упиравшаяся в границу, проходит; треть капитала возвращается в работу. Проверка:
`pre_cutover_gate` 17/17, весь риск-слой — **10 825 passed, 0 failed**.

Инструмент, которым найден дефект, остался в системе: `redistribution_refusal_record` пишет
поданную цель без округления, обе арифметики остатка и поимённую разницу с тем, что вернул
гейт. Отказ теперь воспроизводим по журналу до последнего бита.

## Урок

Отказ, который нельзя проверить по журналу, — отдельная проблема, даже если он верен. Три
вечера рассуждений не стоили одной записанной строки: гипотеза о плавающей точке была верной
с самого начала, но подтвердить её было нечем, и дважды она снималась как «опровергнутая» на
округлённых числах.
