# ADR-991 · §46 «Portfolio CIO»: носитель цели между Optimizer и Target Allocation переписывают 6 ступеней, которых в карте нет (трим ADR-850 среди них); Risk Gate зовётся до Target Allocation

- **Статус:** Accepted
- **Дата:** 2026-11-12
- **Автор/утвердил:** цикл #1109 (оркестратор, автономный мандат ADR-407; заказ G978 п. 1 карточки приказа
  `inbox-task-portfolio-cio-dynamic-capital-alloc`) — замер, код, батарея, мутации; цикл #1110 — чтение результата мутаций,
  три различающие сцены, доставка наследством
- **Предмет:** §46 ТЗ «Portfolio CIO» («Минимальный proposed component map»), третий вопрос раздела;
  соседи — ADR-253 (состав и связь, 07.09), ADR-989 (§43: девять ступеней между записью решения и ходом),
  ADR-850 (трим), ADR-986 (стадия)

## 1. Что спрашивал владелец и что уже было измерено

§46 ТЗ (карточка приказа, строки 1421–1443 с `origin`): десять ступеней в порядке владельца —
Opportunity Data → Portfolio State → Portfolio Optimizer → Target Allocation → Rebalance Evaluator → Risk Gate →
Execution Planner → Execution Agent → Post-Trade Monitor → Reporting — и инструкция: **«Не создавать новые
компоненты, если эквиваленты уже существуют».**

ADR-253 (цикл #515) задал §46 два вопроса и ответил на оба: **состав** — эквивалент есть у 10 ступеней из 10,
«строить нечего»; **связь** — стыков несут ход 3 из 9, `rebalance_trigger.json` остров, стык Post-Trade → Reporting
разорван. Живой артефакт `data/cio_component_map.json` от 29.10 тот же: CRITICAL 2 · WARN 1.

**Решение по INDEX — перемерять §46, а не идти к §47/§48.** Заказ G978 п. 1 назвал величины, которых 07.09 не было:
трим ADR-850 (28.10), стадия ADR-986 (12.11), зазор «решение ↔ исполнено» ADR-989 (12.11). ADR-989 нашёл, что между
записью решения и ходом цель переписывают **девять** ступеней цикла — и это утверждение о КАРТЕ: стык
«Portfolio Optimizer → Target Allocation» числится `WIRED_IN_PROCESS` (имя, рождённое `allocate()`, доходит до
`write_shadow_rationale`), но карта не спрашивала, **то ли самое значение** доходит. Вопрос третий: ТО ЛИ значение
доходит до следующей ступени, что произвела предыдущая, — и в каком порядке живой цикл зовёт ступени владельца.

## 2. Замер (дерево `origin/main` b455a5532, только чтение; разбор AST, живой `data/` не читается)

Прибор `spa_core/monitoring/cio_component_map.py` получил третью ось: `carrier_rewriters` (кто ПЕРЕСВЯЗЫВАЕТ
носитель между входом верхней ступени и входом нижней, в том же теле функции) и `stage_order` (порядок ПЕРВОГО
вызова входов на сквозном пути, приведённый к корню по графу вызовов).

| ось ADR-991 | живой замер 12.11 (`spa_core/paper_trading/cycle_runner.py`) |
|---|---|
| носитель стыка «Portfolio Optimizer → Target Allocation» | `target_usd` в `run_cycle`, строки **1574** (`allocate()`) … **2180** (`write_shadow_rationale`) |
| площадок пересвязывания | **9** — ровно те девять, что ADR-989 насчитал чтением строк (положительный контроль на живом дереве) |
| прописанная ступень не на своём стыке | **Risk Gate** — 2 площадки (`target_usd = dict(gate["target_usd"])`, `dict(_gate2[…])`): в карте владельца она стои́т через две ступени ниже |
| **СКРЫТЫЕ ступени** (в карте владельца нет) | **6** функций на **7** площадках: `apply_kill_switch_override` · `apply_soft_derisk_gate` (×2) · `_compliant_target` · `apply_rtmr_posture_gate` · `apply_pool_alias_gate` · **`apply_admissible_trim` (ADR-850)** |
| порядок на сквозном пути (корень `main`) | Portfolio State → Portfolio Optimizer → **Risk Gate** → Target Allocation → Rebalance Evaluator |
| инверсий против порядка владельца | **2**: «Target Allocation» после «Risk Gate»; «Rebalance Evaluator» после «Risk Gate» (вердикт тени пишется в `_run_smart_modules` после возврата `run_cycle` — тот же факт, что остров ADR-253, теперь измерен порядком) |
| ступень вне сквозного пути | **Reporting**: единственный вызов `generate_daily_report` — в ветке `if not live: … return` (строка 1380 → 523); на торговом пути цикла отчёт дня не производится этим оркестратором |
| не вызваны по имени входа | Opportunity Data (`run_orchestrator`), Post-Trade Monitor (`reconcile`) — не инверсия и не ноль, названы |
| прежние два вопроса | без изменений: эквивалент 10/10, стыков несут ход 3/9, остров `rebalance_trigger.json`, разрыв Post-Trade → Reporting |
| итог артефакта | CRITICAL **3** · WARN **4** · UNCHECKED 0 (было 2 · 1 · 0); положительный контроль 9/9 |

**Что это значит для инструкции владельца.** «Состав 10/10, строить нечего» (ADR-253) был ответом о ПРОПИСАННЫХ
ступенях. Между двумя прописанными живут шесть непрописанных, каждая переписывает цель, и одна из них создана
28.10 (ADR-850) — то есть компонент, которого в карте владельца нет, добавлен после инструкции «не создавать
новые компоненты». Эквивалент у трима есть по смыслу («сколько переложить» — Rebalance Evaluator решает «пора ли»),
но измерить это чтением нельзя; названо как вопрос владельцу в пакете карточки приказа, карточкой не множится.

**Три дефекта прибора, найденные НА СЕБЕ при замере** (каждый закреплён тестом): первое связывание производного
имени (`_policy_refusals = quantify_policy_refusals(...)`) читалось переписчиком — переписчик ПЕРЕсвязывает;
атрибутный вызов `_mod2.main()` замыкал граф вызовов в кольцо и делал корнем `_run_fundability_pack` — граф
строится по вызовам голым именем; ветка раннего выхода (`if not live: … return`) и хвостовой `return` функции
читались одинаково, и первая редакция объявила ВЕСЬ цикл «вне пути» — ранний выход есть ветка `if`, за которой в
том же блоке есть операторы.

## 3. Решение

1. **Третья ось §46 — часть прибора**, артефакт `data/cio_component_map.json` схемы **v2**: `hidden_stages`,
   `hidden_stage_sites`, `rewriters_unmeasured_edges`, `stage_order`, `order_inversions`, `stages_off_path`; у каждого
   стыка `rewriters` с исходами `measured` · `unmeasured` (причина) · `not_applicable` (файловый носитель).
2. **Положительный контроль расширен до девяти сцен** (К6/К7 переписчики, К8/К9 порядок); провал любой ⇒
   `overall=UNCHECKED`, как и прежде.
3. **Шаг 0-офис читает ось** именной веткой (`scripts/consume_office_reports.py`, `_READ_SCHEMA` +6 полей, база
   `office_schema_field_baseline.json`); артефакт схемы v1 печатается как «ось НЕ ИЗМЕРЕНА», а не как ноль скрытых.
4. **Находки:** скрытые ступени на стыке — `critical`; прописанная ступень не на своём стыке, инверсия порядка,
   ступень вне сквозного пути — `warn`; неизмеренное — `unchecked`. Ни одно число не выводится из отсутствия.

## 4. Что это НЕ делает

Ни одна ступень не переносится, не прописывается в карту и не снимается; порядок цикла не меняется; трим ADR-850,
стоп-кран, дерискинг, RTMR, псевдонимы и ADR-002 работают как работали. Всё это money-path — предмет №1 ADR-285.
Мера порядка — ПРОКСИ (первая строка вызова на сквозном пути): строка ≠ исполнение при ветвлении, позиции печатаются
целиком, и прибор говорит это вслух в поле `method`. Динамический замер потребовал бы запуска цикла против живого
`data/` — запрещено.

## 6. Исполнители (работа следующих циклов — заказ G979 карточки приказа)

(а) прод-артефакт `data/cio_component_map.json` обновить доставленным прибором с `--root <прод>` (ступень моста
`decision_loop` мертва) — сделано этим циклом, см. журнал; (б) вопрос владельцу о шести скрытых ступенях — прописать
их в карту §46 как ступени между Target Allocation и Risk Gate ЛИБО признать трим ADR-850 дублем Rebalance Evaluator —
предмет №1, идёт пакетом в карточке приказа, карточкой не множится; (в) Reporting на торговом пути: кто производит
`daily_report_{date}.json`, когда `cycle_runner` не зовёт его вне ветки «данных нет» — замер следующего цикла
(ADR-253 назвал продукт, не производителя на пути); (г) §47 перемер с величинами ADR-850/986/989 либо §48/§49 по INDEX.
