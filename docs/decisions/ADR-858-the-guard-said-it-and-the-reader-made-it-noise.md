# ADR-858 — Сторож сказал, а читатель превратил ответ в шум: число свободного места не доезжало до файловой поверхности сессии

- **Дата:** 2026-10-29 (цикл #975)
- **Статус:** Accepted
- **Класс:** ADVISORY — RiskPolicy v1.0 не правлена ни строкой, денежный путь не тронут, ACT 0
- **Предмет:** читаемость уже измеренного числа, а не новое измерение

## Что случилось

Сессия цикла #975 начала работу, прочитав всё предписанное `CLAUDE.md` §1:
`docs/SYSTEM_BRIEFING.md` (замер 08:16 UTC), `docs/STATE.md`, реестр решений.
Брифинг сказал: `Portfolio ✅ $101,848.49`, `Resilience (DR) ✅ OK`,
`Agents ⚠️ WARNING (90/92 healthy)` и две строки проблем:

```
- ⚠️ `com.spa.resource_guard` — last_exit=2
- ⚠️ `com.spa.site_freshness` — last_exit=1
```

В этот момент на машине оставалось **2.4 ГиБ** свободного места из 460, и
скорость расхода была такова, что до полного отказа записи оставалось около
**28 минут**. Узнать это из предписанных файлов было НЕЛЬЗЯ: сессия нашла аварию
только потому, что независимо набрала `df -h /`.

## Чего в этой истории НЕТ: молчащего сторожа

Первое прочтение («`last_exit=2` ⇒ `resource_guard` сломан») было НЕВЕРНЫМ, и
это важнее самой аварии. `com.spa.resource_guard` (ADR-551) отработал
**безупречно**. Его собственный журнал за тот час:

```
[08:38:16Z] CRITICAL: disk 4.8 GB free; memory pressure 1, swap 94.6%  → EXIT code=2
[08:43:17Z] CRITICAL: disk 4.4 GB free; memory pressure 2, swap 92.0%  → EXIT code=2
[08:48:18Z] CRITICAL: disk 3.4 GB free; memory pressure 1, swap 91.7%  → EXIT code=2
[08:53:19Z] CRITICAL: disk 2.6 GB free; memory pressure 2, swap 91.1%  → EXIT code=2
```

Он мерил каждые пять минут, называл ЧИСЛО, верно ранжировал вердикт и
**запушил владельцу в Telegram**: `push_state.resource_critical` =
`{"state": "bad", "entry_pushed": true, "fingerprint": "disk:CRITICAL|mem:WARN"}`.
Код выхода 2 — это его ОБЪЯВЛЕННЫЙ вердикт (`0 OK · 1 WARN · 2 CRITICAL или NOT
MEASURED`), а не его поломка.

**Дефект — у читателя.** Сводка агентского здоровья печатает РОД кода выхода и
не печатает величину вовсе, поэтому «агент сломался» и «агент докладывает
аварию» в ней имеют ОДНУ форму. Строка про диск, которому осталось 2.6 ГБ, и
строка про `site_freshness` с кодом 1 отличались только именем агента и цифрой
кода. Это ровно тот класс, который репозиторий знает под именем «зелёный ответ
сторожа на СВОЙ вопрос не есть ответ на нужный» (`.claude/rules/deployment.md`),
но повёрнутый на 180°: здесь сторож ответил на НУЖНЫЙ вопрос, а читатель
понизил ответ до шума.

## Замер: один файл против всего остального

| ось | замер 2026-10-29 |
|---|---|
| журналов агентов в `/private/tmp/spa_*.log` | **536** |
| их суммарный размер | **9.91 ГиБ** |
| из них ОДИН файл `spa_decision_loop.log` | **9.82 ГиБ** |
| самый большой из остальных 535 (`spa_analytics_tier_b.log`) | **11.0 МБ** |
| измеренная скорость роста того файла (окно 60 с) | **87.58 МиБ/мин** = 123 ГиБ/сут |
| свободно до усечения / после | **2.4 ГиБ → 12 ГиБ** |

**Наивный вывод «журналам агентов нужна ротация» ЗАМЕРОМ ОПРОВЕРГНУТ.** 535
журналов из 536 не превышают 11 МБ; класса «логи растут» не существует.
Существует ОДИН патологический писатель. Это различение не косметическое: оно
меняет починку с фронтальной (предел размера всем 536, то есть правка
`scripts/agent_template.sh` — входной точки всего флота) на точечную.

## Что было сделано с аварией

Журнал `spa_decision_loop.log` **усечён** (`: > файл`), не удалён: inode и
открытый дескриптор писателя целы (обёртка пишет через `>> "$LOG"`, то есть
`O_APPEND`), агент не остановлен и не выгружен, pid 38197 продолжил работу.
Улика сохранена до усечения — голова и хвост по 400 КБ
(`/tmp/spa_c975_evidence/`). Высвобождено 9.82 ГиБ, свободное место 2.4 → 12 ГиБ.

Почему это сделано САМО, а не карточкой владельцу: до отказа записи на всей
машине оставалось ~28 минут; `/tmp` — предписанное место журналов агентов
(инв. #12), очищаемое при перезагрузке, то есть не «данные»; трек, `data/`,
git и состояние агентов не тронуты. Действие НАЗВАНО здесь, в журнале цикла и в
карточке владельцу — молчаливым оно не является.

## Главное: владелец уже закрыл этот вопрос, и его посылка опровергнута

`owner-decision-disk-mac-mini-zabit-pod-nol-odin-zhurnal` (создана 26.09,
ровно про ЭТОТ файл, тогда 7,1 ГБ) закрыта владельцем **27.10**:

> **Вариант закрыть** — закрыть как устаревшую: свободно 43 ГБ из 460, журнал
> 7,1 ГБ не причина

Посылка решения — «свободно 43 ГБ» — через **48 часов** перестала быть верной, а
вторая его часть («журнал не причина») замером опровергнута прямо: тот же файл
составлял 9.82 ГиБ из 9.91 ГиБ всех журналов, и его усечение одно вернуло
машину из 2.4 ГиБ в 12 ГиБ. Шаг 3 той же карточки («у журналов агентов нет ни
усечения, ни предела размера… иначе это повторится») владелец не взял — и
повторилось за два дня.

Это НЕ «владелец ошибся»: на 27.10 при 43 ГБ запаса решение было разумным.
Это «решение принято на числе, которое дрейфует», и такое решение обязано
пересматриваться замером, а не памятью. Поэтому карточка владельцу заводится
НОВАЯ, с опровергающим замером в теле, а не реанимируется старая.

## Решение

Число свободного места получает **файлового читателя** —
`scripts/update_system_briefing.py`:

1. `resource_state(d, *, now=None)` — разбор `data/resource_health.json` с
   **тремя различимыми исходами** (инв. #17): измерено · измерено и помечено
   просроченным · **НЕ ИЗМЕРЕНО** с названной причиной. `free_gb` отсутствует ⇒
   `NOT_MEASURED`, и **никогда** ноль: ноль здесь означал бы «диск полон», то
   есть аварию, противоположную по смыслу молчанию прибора.
2. `resource_header_cell(st)` — строка `| Диск · память (ADR-858) |` в сводке
   «at a glance», с ЧИСЛОМ.
3. `build_resource_section()` — секция `## 💽 Ресурсы машины` с числом, порогами
   производителя, памятью и swap, и — на критической сцене — прямым объяснением,
   что `last_exit=2` есть вердикт, а не поломка.

**Порог здесь НЕ вычисляется.** Вердикт (`disk.state`) и пороги
(`warn_free_gb` / `critical_free_gb`) берутся у производителя как есть;
пересчёт создал бы ВТОРОЕ место для порога — ровно запрет
`.claude/rules/site-numbers.md`. Отсюда и третий исход: вердикта в документе нет
⇒ `NOT_MEASURED`, а не «посчитаем сами».

Ячейка и секция читают ОДНО состояние одной функцией — две поверхности с двумя
копиями карты расходятся (урок F9/#197, `resilience_header_cell`).

## Приёмка

- `spa_core/tests/test_briefing_resource_section.py` — **14 тестов + 5 subTest**,
  зелены. Каждый — положительный контроль аварии 29.10, включая дословную сцену
  «2.6 ГБ / CRITICAL».
- **Отрицательный контроль** — `test_the_old_surface_carried_no_number`
  воспроизводит дословные две строки прежнего брифинга и показывает, что они
  отличаются только именем агента и цифрой кода: величины в них нет ни в одной.
- **Проводка ГОНЯЕТСЯ, а не грепается** (урок ADR-835): тест поднимает настоящий
  `main()` на подменённых `DATA_DIR`/`OUTPUT` и спрашивает ИСХОД — несёт ли
  снятый документ число, ячейку и секцию.
- **Мутации по дельте** (`docs/mutations/ADR-858.json`, прибор
  `scripts/delta_mutation_run.py` в ОТДЕЛЬНОМ дереве): применено 8 · **убито 8** ·
  выжило 0 · не применено 0 · сломали сборку 0.
  Первый прогон дал **7 из 8**, и выживший был НАСТОЯЩЕЙ дырой, а не
  эквивалентным мутантом: проверка «число есть в документе» одна пропускала
  снятие СЕКЦИИ, потому что то же число стоит в ячейке сводки. Две поверхности —
  два требования; тест усилен, мутант убит.

## Чего это НЕ закрывает (названо, не умолчано)

1. **ПРИЧИНА не устранена.** `com.spa.decision_loop`
   (`spa_core.monitoring.findings_bridge --run`) продолжает писать: за время
   цикла журнал заново дорос с 0 до **1.2 ГиБ**. Источник печати —
   `RiskPolicy.check_portfolio_health` (`spa_core/risk/policy.py:1220`,
   `log.warning`), зовомый в цикле из `paper_trading/trim_admissibility.py:278`
   (ADR-855, доставлен в этот же день). Починка правит risk-логику либо
   денежный путь — **прямой запрет автономному мандату**, поэтому карточка:
   `inbox-odin-agent-pishet-123-gib-v-sutki-v-svoi`.
2. **Ресит потребления (B3) остаётся открытым.** `data/resource_health.json`
   объявлен `consumer_required`, а `scripts/consume_office_reports.py` не
   упоминает его НИ РАЗУ (замер: 0 вхождений) ⇒ 0 реситов, и аудит архитектуры
   честно называет это «отчёты в никуда». Брифинг — читатель СЕССИИ, ресит пишет
   шаг 0-офис; это разные читатели. Карточка:
   `inbox-resource-health-json-obyavlen-consumer-r`.
3. **Пределов размера у журналов агентов по-прежнему нет.** Замер выше говорит,
   что класса «логи растут» не существует, поэтому фронтальная правка
   `agent_template.sh` НЕ предлагается; вопрос — за владельцем (шаг 3 его
   карточки 26.09, не взятый).
4. **Градиента у отпечатка тревоги нет.** `fingerprint` =
   `"disk:CRITICAL|mem:WARN"` не меняется, пока род вердикта тот же, поэтому
   push ушёл ОДИН раз, а 4.8 → 2.6 ГБ прошли без нового. Это ЗАМЕР свойства
   edge-триггера, а не обвинение: так он и задуман против спама. Назвать стоит,
   потому что «становится хуже» по этому каналу невидимо.
5. **Диск ниже порога предписанного прогона.** 12 ГиБ против 20 (ADR-551) ⇒
   полный набор по-прежнему отказан кодом 75; приёмку набора спрашивать у
   `scripts/ci_control_verdict.py`.
