## 1. Контекст

ADR-070 §9 (07.08) поставил замок «один цикл оркестратора одновременно» — на тот момент
верно: захват карточки ловил столкновение уже ПОСЛЕ самой дорогой части цикла, а два
одновременных пушера шли в `origin/main` наперегонки без общей защиты замка. С тех пор
очередь `nimbalyst-local/tracker/` выросла: за неделю 20-26.08 создавалось ~20-25
карточек/день против ~20 закрытых/день — разгрузка не поспевала за наполнением.

## 2. Проверено перед решением (safety-ревью 26.08, полный отчёт не в git — только вывод)

Проверено НЕ гипотезой, а прямым чтением кода шести конкретных мест:

1. **Сам замок** (`scripts/orchestrator_cycle_lock.py`) — исходно защищал именно от
   гонки пушеров, а не от коллизии карточек (та уже закрыта отдельно 30.07,
   `check_card_claim.py`).
2. **Захват карточки** — атомарен (журнал `session_changes.jsonl` O_APPEND ДО правки
   фронтматтера + `O_EXCL`-лок на саму правку). Безопасен и для разных карточек, и для
   гонки за одну.
3. **`docs/STATE.md`/`docs/journal/*`** — append-only, `push_to_github.rebase_append`
   сливает непересекающиеся добавления двух сессий; на настоящем конфликте — громкий отказ
   (`DivergenceRefused`), не молчаливая перезапись.
4. **`_BOARD.md`** — при столкновении получает тот же громкий отказ (не тихий клобб);
   в худшем случае непушнутый цикл пересобирает доску заново на следующем прогоне.
5. **Push в GitHub** (`push_to_github.py`) — Contents API с sha-оптимистичной конкурентностью
   и встроенным ретраем на 409 (переполучить sha → повторить). Гонка двух пушеров уже
   покрыта.
6. **Telegram-уведомления владельцу** — **единственный найденный незакрытый риск**:
   `guard_outbound` (дедуп/лимит потока) читает историю ДО фактической отправки, а
   фиксирует запись ПОСЛЕ; при двух параллельных отправителях оба видят «повторов нет»
   и оба шлют — дубль владельцу. Тот же класс жалобы, что уже чинили 09.08 и 13.08.

## 3. Решение

**Два независимых изменения, каждое — само по себе безопасное дополнение:**

### 3.1 Закрыт риск (обязательное условие, сделано первым)

`spa_core/alerts/telegram_client.outbound_lock()` — межпроцессный `flock`, держит
последовательность guard-решение → HTTP-отправка → запись в историю АТОМАРНОЙ для ЛЮБОГО
числа параллельных отправителей (обе двери — `telegram_client._post_message` и
`TelegramBot.send_message`/`edit_message_text`). Доказано НЕ юнит-имитацией, а РЕАЛЬНЫМ
прогоном двух ОС-процессов (`test_telegram_outbound_lock_concurrent.py`) — критические
секции не пересекаются по времени; мутация (лок отключён) ловится тем же тестом.

### 3.2 Замок ADR-070 §9 научился пускать N держателей

`scripts/orchestrator_cycle_lock.py`: `slot_lock_dir`/`acquire_any_slot`/
`release_any_slot`/`status_all` — N независимых однослотовых замков (тот же формат,
что и раньше: `mkdir` + `holder.json`, та же семантика mine/busy/abandoned/stale).
**При `--max-concurrent 1` (умолчание) — байт-в-байт то же поведение, что до этой
правки**: слот 0 — тот же путь без суффикса, `main()` вызывает исходные `acquire`/
`release`/`status` напрямую, ни один из 71 существующего теста цикла-лока не изменён.

`scripts/agent_orchestrator.sh`: флаг `--max-concurrent "${SPA_ORCHESTRATOR_MAX_CONCURRENT:-1}"`
пробрасывается в acquire/release; свой лог-файл на инстанс через
`SPA_ORCHESTRATOR_LOG_SUFFIX` (иначе два процесса чередовали бы строки в одном
`/tmp/spa_orchestrator.log`).

`launchd/com.spa.orchestrator2.plist` (новый) — ТОТ ЖЕ `agent_orchestrator.sh`, сдвинут
на :30 каждого часа (`StartCalendarInterval`, не намеренная одновременность с :00),
`SPA_ORCHESTRATOR_MAX_CONCURRENT=2` на обоих агентах.

## 4. Приёмка

- Telegram-лок: 17 тестов (15 существующих без изменений + 2 новых, включая настоящий
  двухпроцессный прогон), плюс широкий смежный набор (bot/telegram/owner-queue,
  849 тестов) — 0 регрессий.
- Cycle-lock слоты: 71 существующий тест цикла-лока — без изменений, 15 новых
  (`test_orchestrator_cycle_lock_slots.py`), включая явную регрессию «N=1 не
  создаёт второй слот и не отличим от кода до правки».
- `plistlib.load` подтверждает валидность обоих `.plist`; `bash -n` — валидность правки
  обёртки.

## 5. Последствия

- **Плюс (ожидание, не измерение):** такт разгрузки очереди — раз в 30 мин вместо раза
  в час при том же общем числе циклов/сутки (тот же бюджет Claude, просто чаще).
- **Минус (честно):** два параллельных цикла означают два одновременных потребителя
  лимитов Claude в моменты пересечения — при уже узком бюджете это может ускорить
  исчерпание лимитов внутри дня (см. отдельную карточку `inbox-ischerpanie-limitov-claude-nevidimo-tsehu`
  про видимость топлива). Не измерено этим решением — назвать вслух, не молчать.
- **Что НЕ активировано этим ADR:** установка `com.spa.orchestrator2.plist` на хосте
  (`launchctl bootstrap`) и перезагрузка изменённого `com.spa.orchestrator.plist`
  (`launchctl bootout` + `bootstrap`, изменение `EnvironmentVariables` не подхватывается
  без перезагрузки) — **действие владельца**, код сам по себе ничего не меняет до этого
  шага (при `max_concurrent=1` по умолчанию поведение прежнее).
- **Откат:** `launchctl bootout gui/$(id -u)/com.spa.orchestrator2` — один цикл в час,
  как было; код отката не требует (флаг живёт только в `EnvironmentVariables` второго
  плиста).
