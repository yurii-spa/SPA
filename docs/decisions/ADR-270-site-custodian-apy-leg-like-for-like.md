# ADR-270 · Кастодиан сайта сравнивает APY «как с как»: трековый APY из цепочки, а не APY одного дня

- **Статус:** Accepted
- **Дата:** 2026-09-09
- **Автор/утвердил:** агент (ночная смена 08→09.09 по приказу владельца «работать без остановки до 11:00») / применяет решение владельца 2026-07-15 (карточка `owner-decision-20260715-212059-apy`, вариант «а»)

## Контекст

08.09 в 21:38Z кастодиан сайта (`scripts/site_freshness_monitor.py`, ADR-YL-011), запущенный
гейтом установки агента `com.spa.site_freshness`, поставил на публичный сайт табличку
«живые данные временно недоступны» (`degraded: true`, коммит `41a516853`) и разбудил владельца
тревогой `OVERSTATED_METRIC: track shows APY 5.3% > live API 5.0586%`.

Замер показал, что табличка ложная. Сайт публикует **трековый** APY — сложный годовой процент
от якоря 22.06 до последнего доказанного бара за 77 реальных дней (формула
`scripts/generate_track_snapshot.py`). Кастодиан же брал из API поле `apy_today_pct` —
годовую ставку **одного дня** — и клал его под тем же именем `paper_apy_pct`. Живая цепочка
API (`/api/rates-desk/full-chain/equity_track`: якорь 100 150.66 $ → 101 251.32 $, 77 дней)
воспроизводит **ровно 5.3177 %** — число снимка. Завышения не было; была разница определений.

Этот же класс владелец уже разбирал 2026-07-15: ветку `SNAPSHOT_BEHIND_API` по APY тогда
сняли как «ошибку категории» с оговоркой «включать APY-сравнение только как с как». Две
соседние ветки того же файла — проверка `OVERSTATED_METRIC` и **kill-rule** — остались на
старом сравнении (обе написаны 17.07, тем же коммитом `b9cf63fb5`, что и оговорка). Семь
недель они молчали случайно: APY дня держался выше трекового. Ночью 08.09 он впервые оказался
ниже (5.06 < 5.32), и правило честности сработало против честного числа.

Побочная находка: точка цепочки отдаёт **JSONL**, а читатель ждал JSON — поэтому
`api.last_bar` был `null` всегда и ветка `STALE_API` ничего не измеряла с июля.

## Решение

1. `api_headline()` выводит `paper_apy_pct` **как с как** — из доказанной цепочки той же
   формулой, что и снимок (`track_apy_from_chain`: якорь `evidenced_anchor`, дни
   `real_track_days`). APY дня сохраняется отдельно как `apy_today_pct` и в сравнениях
   не участвует.
2. Нет цепочки / меньше двух баров / нет `real_track_days` ⇒ **третий исход**: `paper_apy_pct = None`,
   `apy_source = "unmeasured:<причина>"`, в отчёте `apy_leg = "unmeasured"`. Ветки по APY не
   зеленеют и не краснеют — они названы неизмеренными; ветка 48-часовой протухлости работает как прежде.
3. Читатель цепочки понимает JSONL (`_parse_jsonl`, битые строки пропускаются, не угадываются);
   `last_bar` снова измеряется.
4. Порог `APY_TOL_PP`, kill-rule по завышенному снимку и правило «сайт не показывает APY выше API»
   **не ослаблены**: положительный контроль `test_snapshot_above_the_chain_apy_still_degrades`
   (снимок 6.1 % при цепочке 5.3177 % — табличка ставится); контроль ложной таблички
   `test_snapshot_equal_to_the_chain_apy_is_not_overstated_and_not_degraded` (числа ночи 08.09 —
   молчит).

## Последствия

- Табличку снимает сам кастодиан ветвью восстановления при первом запуске с Мака
  (в CI «снять отсюда нечем» — по построению, 14.08); тревога владельцу 08.09 — ложная,
  об этом сказано в утреннем отчёте.
- Инвариант #16: тесты не ослаблены, добавлены; изменение поведения kill-rule зафиксировано
  здесь и в `docs/journal/2026-W37.md`.
- Открыто: у API нет **объявленного** поля трекового APY — кастодиан его выводит. Если формула
  снимка изменится, обе стороны надо менять вместе (держит тест на равенство 5.3177).
