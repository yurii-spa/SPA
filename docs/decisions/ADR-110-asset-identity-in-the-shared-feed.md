# ADR-110 · Общий фид обязан опознавать пул по личности актива, а не по трём строкам

- **Статус:** Accepted (решение принято; доставка — **после показа владельцу списка потерь**,
  это его собственное условие, см. «Последствия»)
- **Дата:** 2026-08-21
- **Автор/утвердил:** владелец (Telegram, 2026-08-21 09:36:53Z, **вариант A**);
  запись — цикл #331. Карточка:
  `own-2026-08-18-dva-proizvoditelya-apy-opoznayut-pul-po-raznomu`.

## Контекст

Доходность каждого протокола считают ДВА куска кода, и они опознают «наш» пул по разным
признакам.

- `spa_core/bee/defillama_feed.py:286` — с 09.08 проверяет **личность актива**: адрес токена в
  пуле (`underlyingTokens`) обязан совпасть с тем самым USDC.
- `spa_core/adapters/defillama_feed.py` (`get_pool`, стр. 134–151) — этой проверки **не имеет**:
  сверяет три строки (`project` / `symbol` / `chain`) и берёт пул с бо́льшим TVL. Именно его
  число попадает в ранжирование капитала.

«Побеждает больший» — не признак правильности; это просто чей пул на этой неделе крупнее.

**Замер на записи настоящего скана 09–10.08, без сети:** на ОДНОМ наборе пулов первый источник
отвечает **3.29 %** (настоящий USDC), второй — **4.79 %** (токен с адресом `0xD4fa…D23E`,
который тоже называется «USDC», но им не является). Подделка платит БОЛЬШЕ настоящего — значит
дефект выглядит как удача и систематически толкает решение в сторону входа, а не отказа. Это та
самая пара 4.80 против 2.36, из-за которой «40 % под 2.7 %» выглядело абсурдом.

Отдельно: у `pendle` третий источник — родное API Pendle, и его 14.01 % — честный живой замер,
но он берёт МАКСИМАЛЬНЫЙ по доходности подходящий рынок, а `adapter_status.json` про `pendle`
не знает вовсе (там константа 8.0 без объяснения, почему живого числа нет). Две правды об одном
протоколе, обе честные, и ни одна не отвечает на вопрос «сколько платит то, чем мы владеем».

Читательская половина уже сведена к одному определению наблюдения (`status_reader.live_apy`
+ окно свежести 36 ч) и закрыта тестами. Осталась половина, двигающая капитал.

Владельцу предложены A (перенести проверку личности в общий фид), B (отказываться от протокола
при расхождении источников больше N бп), C (не менять). **Владелец выбрал A.**

## Решение

Проверка личности актива переносится в общий фид `spa_core/adapters/defillama_feed.py`: пул
считается «нашим», только если адрес базового токена совпадает с объявленным адресом актива.
Оба производителя опознают пул одинаково.

Протокол, для которого адрес актива ещё не объявлен, получает честное **«не наблюдали»** вместо
сегодняшнего числа неизвестного происхождения. Ранжирование станет уже — и перестанет опираться
на чужой пул.

Реализация — money-path: изолированное рабочее дерево, `pre_cutover_gate`, тесты написаны
заранее. Пороги RiskPolicy не меняются.

## Последствия

**Условие доставки, поставленное САМИМ владельцем в карточке** («…показываю тебе список
протоколов, которые останутся без числа, и только потом доставляю»): пока список не показан,
правка не уезжает. Это не осторожность агента, а часть принятого решения, поэтому цикл #331
записывает решение и НЕ доставляет код. Карточка исполнения:
`agent-lichnost-aktiva-v-obschem-fide-adr-110`.

**Что даёт.** Закрывается путь, по которому ранжирование капитала опиралось на APY чужого
актива, причём незаметно: расхождение сегодня нечем поймать — второй источник читают другие
потребители.

**Цена, честно.** Часть протоколов временно останется без живого числа. Это сужение, и оно
намеренное: узкое честное ранжирование лучше широкого, часть которого приходит с пула, которым
мы не владеем. Величина сужения — ровно тот список, который надо показать владельцу.

**Не сделано и не угадано.** Вариант B («отказ при расхождении больше N бп») владелец не
выбирал, и агент рекомендовал его как страховку «до A». Ставить B молча — значит исполнить
невыбранное решение; поэтому B не делается. Если A задержится, вопрос про страховку задаётся
отдельной карточкой, а не решается за владельца.

**Связанное.** Пункт D6 карточки `agent-tuner-constraints-drift-and-feed-divergence` фиксирует
СЛЕДСТВИЕ по `pendle` (13.94 против литерала 8.0) и требует детерминированного приоритета
источников. ADR-110 называет ПРИЧИНУ другой половины расхождения. Оба нужны; ни один не заменяет
другой.
