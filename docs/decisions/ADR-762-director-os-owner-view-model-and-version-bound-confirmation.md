# ADR-762 · Пульт владельца: детерминированное представление над Company Truth и граница защиты подтверждения

- **Статус:** предложено · 2026-10-09 (DIRECTOR-OS-UX-02, задача владельца). Принимается после ARB-ревью эпика.
- **Связано:** ADR-552 (Mission Control), ADR-571 (Director OS v2), ADR-285 (три предмета владельца),
  ADR-630 (версионная подпись публикации), ADR-660 (проценты и время), инв. #14 и #17.
- **Аудит:** `docs/director_os_ux02/AUDIT.md`. **RFC:** `docs/rfcs/RFC-690-director-os-ux02.md`.

## Контекст

Пульт сегодня рисует `mission.json → truth` напрямую в `app.js`. Подписи состояний, порядок блоков, перевод машинных
кодов и выбор, что показать на первом уровне, размазаны по 1 600 строкам рендера; часть решений принимает браузер
(`app.js:410` подставляет «$0» при отсутствии суммы). Новая структура из пяти разделов (Обзор / Решения / Работа /
Деньги / Защита) требует, чтобы один и тот же факт выглядел одинаково везде и чтобы «не измерено» никогда не
становилось нулём или «всё в порядке».

Подтверждение владельца живёт в одном месте — `spa_core/owner_queue/owner_answer.py` (кнопка в Телеграме,
проверка личности внутри писателя). Ответ **не привязан к версии** карточки: если текст карточки поменяли после
ответа, запись этого не видит. Версионная подпись в репозитории есть только у публикации сайта (ADR-630).

## Решение

1. **Представление владельца — детерминированный слой ПОВЕРХ Company Truth, без своего хранилища.**
   Модуль `spa_core/studio_os/owner_view.py` (чистые функции, stdlib) собирается вместе с бандлом и кладёт в
   `mission.json` ключ `owner_view`: пять разделов, у каждого показателя — `source`, `measured_at`, `updated_at`,
   `unit`, `confidence` (`MEASURED · STALE · NOT_MEASURED · PARTIAL · INTERPRETATION_PROBLEM`) и человеческая
   подпись из словаря. Тот же вход ⇒ тот же выход (тест на детерминизм); никакой второй памяти, реестра решений
   или кэша. Браузер только рисует `owner_view` и не решает за модель, что показать.
2. **Неизвестное остаётся неизвестным.** Отсутствие, ошибка, UNKNOWN ⇒ «Не измерено» с причиной; нераспознанный
   статус ⇒ `INTERPRETATION_PROBLEM` («Не удалось понять статус — это проблема отображения»), никогда не успех.
   Частично проверенное ⇒ `PARTIAL`, а не «всё в порядке». Снимки разных версий в одном экране не смешиваются:
   у раздела одна отметка `computed_at`, и показатель с другой отметкой помечается.
3. **Реальные деньги — только из канона.** Сумма берётся из `capital.real_capital` (`usd`, `state`, `basis`,
   `observed_at`); подпись называет основание («режим исполнения: бумажный»). Литерала «$0» в коде нет.
4. **Пульт по-прежнему ничего не подтверждает сам.** Подтверждение — только существующим механизмом
   (`owner_answer.py` через Телеграм). Открытие карточки не одобрение; в пульте нет кнопки, меняющей состояние.
5. **Граница защиты (исправлено по ARB 09.10).** Пульт показывает у карточки владельца **отпечаток видимого в
   пульте текста** (`sha256` полей `id, title_ru, reason_ru, action_ru, done_when_ru, subject_key, status`, как их
   отдаёт Company Truth — тексты там сокращены до 400 символов). **Это не версия полного решения**: правка в
   невидимой части карточки отпечаток не меняет. Блок «Не готово к ответу» (нет обязательных разделов инв. #15,
   нет предмета ADR-285, нет ссылки на действующий механизм) и подсказка «текст изменился после просмотра —
   перечитайте» (последний прочитанный отпечаток хранится только в браузере этого зрителя) — **помощь при чтении,
   а не проверка**: ответ даётся в Телеграме, и пульт его не проверяет. Каждый путь ответа в пульте несёт одну и
   ту же фразу: «Пульт не проверяет ответ в Телеграме; защищённого подтверждения точной версии сейчас нет».
   Гарантии подтверждения точной версии **нет**, пока не принято «Дополнение» ниже.

## Последствия

- Новый ключ `owner_view` рядом с `truth` (контракт v2 не ломается; тесты контракта получают дополнительный блок).
- `app.js` рендерит пять разделов из `owner_view`; старые рендеры остаются за «Техническими подробностями», пока
  инвентарь функций (`AUDIT.md §6`) не закрыт по каждой строке.
- Отдельный вопрос владельцу (предмет №3 — необратимые действия и подтверждения): записывать ли отпечаток
  версии в `owner_answer.py`. Без этого «повторное подтверждение изменённой карточки» блокируется только
  отображением, а не записью.

## Отвергнуто

- Перенести решения в сам пульт (кнопки «Одобрить»): меняет механизм разрешений и поверхность атаки публичного
  слушателя — запрещено заданием.
- Новый фреймворк/сборщик для UI: запрещено заданием, выигрыша для 5 экранов нет.
- Хранить «отвечено» в браузере: вторая память. (Последний прочитанный отпечаток в `localStorage` — удобство
  чтения одного зрителя, не запись решения и не источник правды; это различие названо в п. 5.)

## Дополнение: защищённое подтверждение — предложение владельцу

> Конкретный план изменения (объект решения, версия, проверка при записи, защита от повторов, журнал
> ответов, миграция, тесты, откат, риски): [`docs/director_os_ux02/ADR762_CHANGE_PLAN.md`](../director_os_ux02/ADR762_CHANGE_PLAN.md).
> **Не реализовано; требует отдельного решения владельца.** Статус ADR-762 — «предложено».

> **Не реализовано.** Это изменение механизма разрешений (`owner_answer.py`, кнопки Телеграма) — отдельное решение
> владельца. До него действует безопасный вариант п. 5: просмотр решений без обещания защищённого подтверждения.

**Как работает сегодня (замер 09.10, код origin).** Ссылка из пульта `https://t.me/<бот>?start=od_<префикс имени
карточки>` (`mission_control.py:474`) → бот находит карточку по имени (`telegram/bot.py:1440`) → для `needs-owner`
шлёт полный вид с кнопками (`owner_queue/notify.notify_needs_owner`) → кнопка несёт `act:od:<pid>:<вариант>`, где
`pid` — хеш **имени файла**, а не содержимого (`telegram/owner_decisions.py:1311`) → `record_owner_answer`
(`owner_queue/owner_answer.py:170`) проверяет личность владельца и пишет `owner_choice`, `owner_answered_at/by/via`.
Повтор того же варианта идемпотентен; **другой вариант перезаписывает** прежний ответ (вытесненный уходит в
`owner_choice_superseded*`). Версия текста, на который отвечали, нигде не записывается и не сверяется.

**1. Полный объект решения** (канонизируется из файла карточки, а не из сокращённого текста пульта):
`card_id` (имя файла без `.md`), `subject` (предмет ADR-285), `title`, тело разделов «Что случилось…», «Что от
тебя нужно» (включая варианты), «Как понять, что готово», «Что будет после», поля `scope`/`approves`/`rollback`,
если есть, `author`/`source`, `created`, `updated`. Служебные поля ответа (`owner_choice*`, `owner_answered_*`,
`status`, журнал переходов) в объект **не входят** — иначе сам ответ менял бы версию.

**2. Версия.** `decision_version = sha256(канонический JSON объекта)` (ключи по алфавиту, UTF-8, без пробелов);
в интерфейсах — первые 12 знаков. Пишется во frontmatter карточки при каждой правке содержимого
(`decision_version:`), сверяется сторожем с пересчётом (расхождение ⇒ находка, а не молчаливая подмена).

**3. Проверка актуальности при ответе.** Сообщение с кнопками фиксирует версию в момент отправки: журнал
`data/telegram_owner_decisions.json` хранит `(pid, decision_version)`. При нажатии `record_owner_answer`
пересчитывает версию ТЕКУЩЕГО файла и сравнивает с версией сообщения; не совпало ⇒ **отказ** с текстом «Карточка
изменилась после отправки — вот новая версия» и повторной отправкой. Записывается `owner_answered_version:`.

**4. Защита от повторной записи.** Один ответ на пару `(card_id, decision_version)`: повтор того же варианта —
идемпотентен (как сейчас); другой вариант на ту же версию — **отказ** «ответ на эту версию уже записан»; новый
ответ возможен только на новую версию (после правки карточки), и прежний ответ уходит в `superseded` с её версией.

**5. Где путешествует версия.** `callback_data` Телеграма ≤ 64 байта: в кнопке остаётся `act:od:<pid>:<вариант>`,
версия — в серверном журнале по `pid` и номеру сообщения (`message_id`), не в кнопке. Пульт показывает те же 12
знаков `decision_version` (из Company Truth, которому версия передаётся вместе с карточкой) — тогда «вы читали
версию X» в пульте и в Телеграме совпадают по построению.

**6. Отказы и сбои (fail-CLOSED).** Файл не читается / версия не считается / журнал без версии для `pid` ⇒ ответ не
записывается, владелец получает объяснение. Старые сообщения без версии в журнале после миграции ⇒ отказ с
повторной отправкой карточки, а не запись «вслепую».

**7. Миграция.** Посчитать `decision_version` для всех открытых `needs-owner`; переотправить открытые вопросы
(`orchestrator_queue.py resend-open`); старые кнопки начинают отвечать отказом с новой отправкой.

**8. Тесты (положительный контроль на каждое звено).** Правка тела после отправки ⇒ отказ; правка служебного поля
ответа ⇒ версия не меняется; повтор того же варианта ⇒ идемпотентно; другой вариант на ту же версию ⇒ отказ;
`callback_data` ≤ 64 байт; журнал без версии ⇒ отказ; пульт и бот показывают одинаковые 12 знаков.

**9. Дополнение ARB 09.10 (предложение, не реализовано).** Проверка версии и запись — одна критическая секция под
блокировкой файла карточки с перечитыванием под блокировкой (compare-and-swap); одновременные ответы — один
писатель и явный отказ проигравшему; повторная доставка Телеграма — ключ идемпотентности `callback_query.id` +
токен; восстановление после сбоя — журнал впереди записи (`pending` → `committed`/`aborted`) со сверкой при старте;
журнал — источник правды об ответе, расхождение с карточкой показывается словами и блокирует кнопку. **Откат
только отключает запись** (флаг fail-CLOSED, просмотр остаётся) и никогда не возвращает ответ без проверки
версии. Подробности: `docs/director_os_ux02/ADR762_CHANGE_PLAN.md` §2a–2d, §8. Статус ADR — «предложено»; нужно
отдельное решение владельца.
