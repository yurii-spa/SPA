# ADR-106 · Автопочинщик кода обезоружен: библиотека остаётся, точки запуска нет

- **Статус:** Accepted
- **Дата:** 2026-08-21
- **Автор/утвердил:** владелец (Telegram, 2026-08-21 09:39:14Z, **вариант 2**);
  реализация — цикл #331. Карточка: `own-56-avtopochinshchik-ostalsya-bez-vyzyvayushchih`.

## Контекст

`spa_core/devtools/auto_fixer.py` просит Claude переписать прод-код, применяет правку, прогоняет
тесты и пушит на GitHub. Владелец называл эту петлю «самая рискованная в системе» и списал
сторожа `telegram_watcher`, который её запускал (карточка `own-55`).

Опасным было не существование модуля, а то, что он оставался **в одной строке от запуска**:

```
python3 -m spa_core.devtools.auto_fixer --alert "..."
```

Модуль без вызывающих, но с прикреплённым триггером — ровно тот класс, на котором мы уже
обожглись на `bot_commands`. Формулировка владельца была про петлю целиком, но решение названо
поимённо про сторожа, поэтому предыдущий цикл модуль НЕ тронул: удалять боевой код по догадке
о намерении — не право агента. Отсюда вопрос и три варианта (1 — удалить, 2 — обезоружить,
3 — оставить как есть с записью в ADR).

## Решение

**Вариант 2.** Из `spa_core/devtools/auto_fixer.py` убраны `main()` и блок
`if __name__ == "__main__"`. Ни одна функция не удалена: `run_auto_fix` и всё, что выше, на
месте и ведёт себя как прежде. Запустить модуль как программу больше нечем.

`main()` убран вместе с охранником намеренно: снять только `if __name__` означало бы оставить
`python3 -c "from … import main; main()"` — триггер с лишним шагом, а не снятый триггер.

Возврат авто-починки — осознанное действие (написать вызывающего под присмотром владельца),
а не однострочник.

## Последствия

**Плюсы.** Единственный способ запустить LLM-переписывание прод-кода закрыт. «Кто-то переписал
файл и запушил» перестаёт быть возможным сценарием по этому пути.

**Честный остаток — НЕ закрыт этим решением и НЕ замаскирован.** Замер 2026-08-21:
- `spa_core/monitoring/telegram_watcher.py` по-прежнему импортирует `run_auto_fix`
  **внутрипроцессно** (не через subprocess) — то есть библиотечная половина петли достижима
  оттуда;
- `launchd/com.spa.telegram_watcher.plist` в репозитории есть, **но агент НЕ загружен**
  (`launchctl list` — отсутствует);
- списание сторожа (`own-55`) на `main` **не доставлено**: и решение, и код остались на ветке
  `work-status-check-xfnbew`, удалённой по ADR-100.

Значит петля на `main` закрыта не наполовину, а по одной двери из двух. Вторая — отдельный
вопрос владельцу (`own-55` переспрашивается), и до ответа сторож не удаляется: это его решение,
а не наше.

**Затронутые файлы и тесты.**
- `spa_core/devtools/auto_fixer.py`.
- Новый `spa_core/tests/test_auto_fixer_disarmed.py` — 4 теста: нет `__main__`-охранника,
  нет `main()`, **запуск модуля в дочернем процессе ничего не делает** (эффект меряется, а не
  выводится из исходника), и — отдельно — библиотечная поверхность ЦЕЛА. Последний нужен, чтобы
  набор не позеленел от удаления файла: это был бы вариант 1, которого владелец не выбирал.
  Мутация «вернуть `main()` и охранник» краснит 3 теста из 4.
