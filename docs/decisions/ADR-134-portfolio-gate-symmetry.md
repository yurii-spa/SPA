# ADR-134 — Проверка книги доложена до симметрии с проверкой перед сделкой

- **Статус:** Accepted
- **Дата:** 2026-08-26
- **Решение владельца:** 2026-08-25, «**все одобряю**» по сводке из 17 решений — по этой карточке
  принят **вариант А**: доложить проверку книги до симметрии с проверкой перед сделкой.
  Пороги НЕ меняются — меняется только охват. Отдельно закреплено: **выход из позиций не
  блокируется никогда.**
- **Карточка:** `nimbalyst-local/tracker/owner-decision-proverka-knigi-slabee-proverki-pered-sde.md`
- **Связано:** ADR-050 (RiskPolicy → governance, two-tier) · ADR-048/034 (SOFT −5 % / HARD −10 %) ·
  ADR-019 (T2 cap 50 %) · ADR-055 (тир динамический) · ADR-062 (охват `policy_enforcer`) ·
  ADR-129 / инвариант #17
- **Домен:** **money-path** — меняется, какая книга объявляется нарушающей, и что за этим следует.
  RiskPolicy version остаётся **v1.0**: ни одно значение порога не тронуто.

---

## 1. Что было измерено

Два момента, когда политика смотрит на деньги: **перед сделкой** (`check_new_position`) и
**на всей книге** (`check_portfolio_health`). Второй проверял заметно меньше первого.

Замер на этом дереве (не по карточке — карточка описывала ветку, которой на `main` нет:
ни `T2_TOTAL_WARN`, ни характеризационного теста здесь не существовало):

```
книга $100k: T1 aave_v3 35 % + три T2 по 20 %
  перед сделкой -> approved=False  ✗ Total T2 allocation 60.0% would exceed limit 50.0%
  на книге      -> approved=True   violations=[]  warnings=[]
```

Одна и та же книга: перед сделкой отказ, на книге — «здорова, нарушений нет».

Полный положительный контроль, снятый на `origin/main` (`pos_control.py`, 8 книг —
каждая нарушает ровно один порог, который перед сделкой блокирует):

| книга | `origin/main` | после ADR-134 |
|---|---|---|
| T2 суммарно 60 % | **молчит** | нарушение |
| L2 суммарно 60 % | **молчит** | нарушение |
| одна сеть 95 % | **молчит** | нарушение |
| кэш-буфер 1 % | **молчит** (было предупреждение) | нарушение |
| APY удерживаемой 55 % | **молчит** | нарушение |
| APY удерживаемой 0.4 % | **молчит** | нарушение |
| TVL пула $1 млн | **молчит** | нарушение |
| pnl = NaN | **молчит** | fail-closed кил |

**8 из 8 не ловилось.** После правки — 0 из 8.

**Цена на живой книге — ноль.** `data/current_positions.json` (`generated_at`
2026-08-02): deployed 80 %, кэш 20 %, T2 20 %, L2 5 %, ethereum 75 % →
`approved=True`, `violations=[]`. Ни одна сегодняшняя позиция нарушением не стала.
Оговорка честности: копия `data/` в контейнере отстаёт от рабочего Mac — число описывает книгу
на дату генерации файла, а не сегодняшнюю.

## 2. Что теперь проверяется на книге

Пороги читаются из того же `RiskConfig`, что и во входном гейте — ни одно число не введено
в код проверки книги отдельной константой (тест `ThresholdsUnchanged` держит это в обе стороны:
сдвиг конфига обязан двигать ОБА гейта).

| порог | значение | было на книге | стало |
|---|---|---|---|
| T2 совокупно | 50 % | — | нарушение |
| L2 совокупно | 50 % | — | нарушение |
| одна сеть | 90 % | — | нарушение |
| кэш-буфер | 5 % | предупреждение | нарушение |
| коридор APY | 1…30 % | — | нарушение (попозиционно) |
| пол TVL | $5 млн | — | нарушение (попозиционно, по `tvl_map`) |

Почему это не теория: **тир динамический** (ADR-055). Куратор двигает протокол T1→T2, и книга
нарушает суммарный потолок **без единой сделки** — входной гейт такую книгу не увидит никогда,
он смотрит только на прибавку.

### Не сделано намеренно (названо, а не забыто)

`max_protocols` (≤ 8), `max_total_t3_allocation` (15 %) и `BASE_CHAIN_CAP` (20 %) на книге
по-прежнему не проверяются — но их **не проверяет и входной гейт**, так что симметрия здесь уже
есть. Это отдельная дыра (потолок, который не гейтит нигде), и закрывать её надо своим решением,
а не под видом «доложили до симметрии».

## 3. Отсутствие наблюдения ≠ нарушение (инвариант #17)

Два новых попозиционных порога опираются на данные, которых может не быть. Молча считать их
пройденными нельзя — но и объявлять нарушением молчание фида нельзя тоже.

* **APY.** Производитель числа сам грешит инвариантом #17:
  `engine._load_portfolio_state` пишет
  `current_apy = snap["apy_total"] if snap else (net_apy_annualized or 0.0)` — отсутствие снимка
  приходит в гейт **нулём**. Судить по такому нулю «ниже 1 % ⇒ нарушение» значило бы объявить
  нарушением молчание фида. Поэтому неположительное / нефинитное APY — **отдельный исход**
  (`APY_UNCHECKED`, предупреждение), а нарушением становится только измеренное значение вне
  коридора.
* **TVL.** У книги нет своего TVL — его приносит вызывающий в `tvl_map`. Нет карты (или нет
  записи по протоколу) ⇒ `TVL_FLOOR_UNCHECKED` с поимённым перечислением, а не «порог пройден».

## 4. Ответ на нарушение — не распродажа

Это вторая половина решения, и без неё вариант А был бы опасен.

**Замер:** `engine.rebalance` закрывал книгу целиком по `if not health.approved`. То есть
**любое** нарушение книги означало выход в кэш — включая SOFT-тир просадки, в тексте нарушения
которого дословно написано «NOT all-cash» (ADR-050). ADR-050 исполнялся только на словах:
вердикт сообщал SOFT, а потребитель закрывал всё.

```
просадка 6 % -> approved=False, drawdown_tier=SOFT_DERISK,
                violations=['SOFT DE-RISK ... hold/reduce/withdraw only (NOT all-cash).']
             -> engine.rebalance(): close_position(ВСЕ, reason='kill_switch')
```

Расширение охвата без этой правки превратило бы просевший APY удерживаемой позиции в
принудительный выход в кэш — при том, что forced-sell по просевшему пулу у нас прямо запрещён
(`.claude/rules/risk-engine.md`: заморозка per-pool, cap-at-held / drop).

**Развязка:** `approved` («книга в пределах политики?») и `required_response` («что с этим
делать?») стали разными вопросами.

| `required_response` | когда | действие |
|---|---|---|
| `NONE` | нарушений нет | — |
| `HALT_NEW` | SOFT-тир, концентрация, **весь новый охват** | не покупать / не наращивать; держать, снижать долю и выходить — можно |
| `ALL_CASH` | HARD-кил, критический депег, fail-closed guard'ы | полный выход в кэш |

`approved` своего смысла НЕ меняет — ни один существующий потребитель не видит другого ответа
на свой вопрос. Меняется только триггер ликвидации в `engine.rebalance`:
`required_response == ALL_CASH` вместо `not approved`.

Книга с нарушением, не требующим распродажи, теперь возвращает видимое действие
`HALT_NEW` с перечнем нарушений и `exit_allowed: True` — иначе она дошла бы до конца функции и
отчиталась `NO_OP: portfolio_healthy`, то есть нарушение выглядело бы здоровьем (инв. #17).

## 5. Выход не блокируется никогда — условие владельца

Сегодня выход структурно нигде не гейтится: `close_position` риск-политику не спрашивает.
Условие закреплено двумя утверждениями, а не устной договорённостью:

* `RiskCheckResult.blocks_exit` — константа `False` с проверкой на каждом отказном вердикте
  (HARD, SOFT, охват);
* структурный тест: в исходнике `close_position` нет ни `check_new_position`, ни
  `check_portfolio_health`. Он покраснеет в тот день, когда кто-нибудь загейтит выход.

## 6. Побочная находка: NaN-просадка читалась как «просадки нет»

Найдена замером при написании тестов, закрыта здесь же (правка строго fail-CLOSED).

Fail-closed guard в `check_portfolio_health` обещает в собственном комментарии поймать
«pnl corrupted to NaN» — и **не срабатывал никогда**: `total_drawdown_pct` возвращает
`max(0.0, -pnl / capital)`, а `max(0.0, nan)` в Python равен **0.0** (сравнение с NaN всегда
`False`, начальное значение остаётся). Испорченный pnl доходил до гейта как «просадки нет» —
инвариант #17 наизнанку.

Теперь нефинитность спрашивается и у **исходных** величин (`total_pnl_usd`,
`total_capital_usd`), а не только у производной. Тест фиксирует и само свойство
(`total_drawdown_pct == 0.0` на NaN), чтобы правка свойства не прошла молча.

## 7. Приёмка

- `spa_core/tests/test_risk_policy_gate_symmetry.py` — **27 тестов + 3 subtests**, включая:
  * каждый порог прогоняется через **ОБА** гейта на одних числах (тест сверяет их друг с другом,
    а не с записанной в него константой);
  * обратный контроль — здоровая книга остаётся `approved`, пустая книга не нарушение,
    ровно на потолке зелено, потолок + 0.1 п.п. красно;
  * положительные контроли на инвариант #17 (измеренное вне коридора — нарушение);
  * `HARD` по-прежнему требует `ALL_CASH` (кил не ослаблен);
  * `engine.rebalance` закрывает книгу на `ALL_CASH` и НЕ закрывает на `HALT_NEW`.
- Положительный контроль на `origin/main`: 8 из 8 книг проходили молча; на этой ветке — 0 из 8.
- Живая книга: `approved=True`, нарушений ноль.
- Полный набор командой CI: **109 588 passed**, 42 failed — все 42 воспроизводятся
  **идентично на `origin/main`** (тот же файловый набор: main 42 failed / 249 passed после
  правки, до неё 42 + 2 моих). Это дыры окружения контейнера, а не регрессия: нет `fastapi`,
  `mypy`, `pyflakes`, а проверки прав запускаются из-под root. Своих красных нет.

### Намеренная правка двух чужих тестов (инвариант #16)

`tests/test_engine_production.py::TestRebalanceKillSwitch` — два теста собирали вердикт **руками**
и описывали просадку **6.5 %**, то есть SOFT-тир, требуя при этом полного закрытия книги.
Они закрепляли ровно тот дефект, который чинит §4.

Что сделано: **утверждение сохранено дословно** («кил закрывает всё», «причина `kill_switch`») —
изменилась только фикстура: она теперь требует `ALL_CASH` явно, как настоящий HARD-кил, и текст
нарушения переписан с 6.5 % на 12 %. Плюс **добавлен** тест на SOFT-случай, которого у файла не
было вовсе: 6.5 % не ликвидирует, отдаёт `HALT_NEW` с `exit_allowed`, и не смеет отчитаться
`NO_OP: portfolio_healthy`. Набор усилен, а не ослаблен: было 81 passed, стало 82.

Ни один вердикт не выводит `ALL_CASH` сам: вручную собранный отказ достраивается до `HALT_NEW`
(`__post_init__`, безопасная сторона), а распродажу можно только **потребовать явно, назвав
причину**.

## 8. Что этим решением НЕ сделано

- `policy_enforcer` по-прежнему определяет тир по записанному руками списку имён и слеп к
  переезду тира куратором (вариант В карточки) — **отдельная задача**, здесь не трогали.
- Режим «заморозить позицию с просевшим пулом» не строился: нарушение пола TVL даёт `HALT_NEW`,
  а не продажу — этого достаточно, чтобы не покупать дальше, и недостаточно, чтобы называть
  заморозку реализованной.
- Пороги RiskPolicy не менялись; `version` остаётся `v1.0`.
