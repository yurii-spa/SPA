# План изменения: защищённое подтверждение решения владельца (к ADR-762)

**Статус:** предложение. **Не реализовано.** Это изменение механизма разрешений (как владелец
отвечает на карточку решения), поэтому оно требует **отдельного решения владельца**. До этого решения
механизм подтверждений не меняется, а пульт показывает решения только для чтения и прямо пишет:
«Пульт не проверяет ответ в Телеграме; защищённого подтверждения точной версии сейчас нет».

## 0. Как работает сейчас (замер кода, origin `61b5d0958`)

- Кнопка в Телеграме несёт `act:od:<pid>:<вариант>` (`spa_core/telegram/owner_decisions.py`,
  `CALLBACK_PREFIX = "act:od:"`). `pid` — хеш имени файла карточки, а не её содержимого.
- Запись — `spa_core/owner_queue/owner_answer.py::record_owner_answer(path, choice_num, choice_label,
  actor_chat_id, …)`: проверяет, что отвечает владелец (`is_owner`), пишет `owner_choice`,
  `owner_answered_at`, `owner_answer_via`, `owner_answered_by` во frontmatter и переводит статус.
- Тот же вариант повторно — идемпотентно. Другой вариант — новый ответ; прежний переносится в поля
  `owner_choice_superseded*` (`SUPERSEDED_FIELDS`), то есть хранится только ОДИН прежний ответ.
- На какой текст карточки дан ответ — **не записывается**. Если карточку изменили между отправкой и
  нажатием, ответ ляжет на новый текст.

## 1. Полный объект решения

Из файла карточки `nimbalyst-local/tracker/<id>.md`, а не из сокращённого текста пульта.

| Поле | Откуда | Входит в версию |
|---|---|---|
| `card_id` | имя файла | да |
| `title` | frontmatter | да |
| `subject_key` (предмет ADR-285) | frontmatter | да |
| `question` / `requested_action` | frontmatter / раздел «Что от тебя нужно» | да |
| варианты (номер → текст) | раздел «Что от тебя нужно» | да |
| «Что случилось и почему это важно» | тело | да |
| «Как понять, что готово» | тело | да |
| «Что будет после» | тело | да |
| объём, ограничения, откат (если есть разделы) | тело | да |
| `created`, `author`/`source` | frontmatter | да |
| `status`, `status_trail`, поля ответа `owner_*`, `*_superseded*`, служебные отметки цикла | frontmatter | **нет** — меняются при ответе и не относятся к тому, ЧТО решается |

**Каноническая сериализация.** Объект собирается в словарь с фиксированным набором ключей. Тексты
нормализуются: переводы строк → `\n`, пробелы по краям срезаны, Unicode NFC. Затем
`json.dumps(obj, sort_keys=True, ensure_ascii=False, separators=(",", ":"))` в UTF-8.

**Версия:** `decision_version = sha256(канонический JSON)`, полные 64 hex. Короткий вид (первые 12) —
только для показа.

## 2. Проверка актуальности при записи

Где: `spa_core/owner_queue/owner_answer.py`.

- Новая функция `decision_object(path) -> dict` и `decision_version(path) -> str` (чистые, без записи).
- `record_owner_answer(..., expected_version: str)` — новый **обязательный** параметр для ответов
  через кнопку. Перед любой записью:
  1. перечитать файл карточки;
  2. посчитать `decision_version`;
  3. не совпало с `expected_version` ⇒ `raise DecisionChanged` и **ничего не писать**.
- Сообщение владельцу в Телеграме: «Карточка изменилась после того, как вам её прислали. Ответ не
  записан. Новая версия отправлена отдельным сообщением — ответьте на неё.» И бот сразу
  переотправляет карточку (`resend-open`) с новой версией.
- Любая ошибка чтения или подсчёта ⇒ отказ без записи (fail-CLOSED).

## 2a. Карточка не может измениться между проверкой и записью (ARB 09.10)

Проверка версии и запись ответа — **одна критическая секция** под одной блокировкой:

1. взять эксклюзивную блокировку карточки: `fcntl.flock` на файле-замке `<карточка>.md.lock`
   рядом с карточкой (stdlib, тот же каталог); не взята за 5 с ⇒ отказ «карточка занята, повторите»,
   ничего не пишется;
2. **под блокировкой** перечитать файл карточки и посчитать `decision_version` (compare-and-swap:
   сравнивается хеш ровно того содержимого, которое сейчас лежит на диске, а не прочитанного раньше);
3. не совпало с `expected_version` ⇒ `DecisionChanged`, запись в журнал `REFUSED_CHANGED`, выход;
4. совпало ⇒ записать журнал (п. 2c) и frontmatter, не отпуская блокировку;
5. отпустить блокировку.

Все писатели карточки (агентская очередь `orchestrator_queue.py`, `record_owner_answer`, переотправка)
берут **ту же** блокировку. Писатель, который её не берёт, — дефект; сторож: тест, который правит
карточку параллельно с ответом и требует, чтобы победитель был ровно один (п. 7, тест 12).

## 2b. Одновременные ответы и повторная доставка Телеграма

- **Конкурентные ответы** (два нажатия, два устройства): блокировка из п. 2a делает писателя
  единственным. Детерминированный победитель — тот, кто первым взял блокировку; второй под
  блокировкой видит уже записанный ответ на эту версию и получает явный отказ
  `REFUSED_ALREADY_ANSWERED` («на эту версию уже дан ответ …») или `IDEMPOTENT`, если вариант тот же.
- **Повторная доставка** (Телеграм присылает тот же `callback_query` повторно, бот перезапустился
  посреди обработки): ключ идемпотентности = `callback_query.id` + `token`. Журнал хранит ключ; при
  повторе с тем же ключом ничего не пишется, бот отвечает тем же текстом, что и в первый раз
  (`outcome` берётся из журнала).

## 2c. Восстановление после сбоя — журнал впереди записи

Порядок внутри критической секции:

1. дописать в `owner_answers.jsonl` строку `state: pending` (ключ идемпотентности, карточка, версия,
   вариант) и `fsync`;
2. обновить frontmatter карточки (`atomic_save`, `os.replace`);
3. дописать строку `state: committed` с тем же ключом и `fsync`.

При старте бот сверяет журнал и карточки: `pending` без `committed` ⇒ если frontmatter уже несёт этот
ответ (та же версия и вариант) — дописать `committed`; если нет — дописать `aborted` и считать ответ
незаписанным (владелец получает сообщение «ответ не записан из-за сбоя — ответьте ещё раз»).
Состояние «ответ есть в карточке, но нет в журнале» или «committed в журнале, а в карточке другое»
никогда не исправляется молча: это расхождение (п. 2d).

## 2d. Журнал и показанное состояние

- Источник правды о том, отвечена ли карточка, — **журнал** (`committed`); frontmatter — его проекция.
- Пульт (через Company Truth, только чтение) выводит «ответ записан» только при согласии журнала и
  карточки. Несогласие показывается словами: «Расхождение журнала и карточки — ответ не считается
  записанным; нужна проверка», и кнопка ответа не появляется.
- Сторож в цикле сверяет журнал и карточки раз в такт и называет расхождения (без исправления).

## 3. Защита от повторной записи

**Правило:** один ответ на пару (карточка, версия).

- Тот же вариант на ту же версию повторно — идемпотентно: ничего не пишется, бот отвечает «Ответ уже
  записан <время Мадрид>».
- **Другой вариант на ту же версию — отказ**: «На эту версию уже дан ответ <вариант, время>. Чтобы
  изменить решение, нужна новая версия карточки». Обоснование: ответ на конкретную версию —
  подтверждение; молча заменять его значит превращать подтверждение в черновик. Смена решения — явное
  действие: агент создаёт новую версию карточки (например, раздел «Пересмотр»), владелец отвечает уже
  на неё, и в истории видны оба ответа.
- Ответ на старую версию после появления новой — отказ по п. 2.

## 4. История ответов — только дописывание

- Журнал `data/owner_answers.jsonl` (append-only, писатель — только `record_owner_answer`): по строке
  на ответ: `card_id`, `decision_version`, `choice_num`, `choice_label`, `actor` (идентификатор
  владельца, без секретов), `via`, `answered_at_utc`, `answered_at_madrid`, `outcome`
  (`RECORDED` / `IDEMPOTENT` / `REFUSED_CHANGED` / `REFUSED_ALREADY_ANSWERED`). Строки не
  переписываются и не удаляются; запись атомарная (`atomic_save` на хвост через временный файл).
- Во frontmatter карточки: `owner_choice`, `owner_answered_at` (как сейчас) + `owner_answer_version`
  (полный sha256) + `owner_answers_log: data/owner_answers.jsonl`. Прежний ответ больше не
  «вытесняется» в одно поле `*_superseded`: история — в журнале.
- Копия журнала уходит в ежедневный бэкап (класс CRITICAL).

## 5. Кнопка Телеграма ≤ 64 байт

`act:od:<pid>:<вариант>` уже на пределе. Версия в кнопку не кладётся. Вместо этого:

- при отправке карточки бот пишет в серверную карту `data/owner_decision_sends.json` запись
  `token → {card_id, decision_version, sent_at, message_id}`; `token` — 8 символов base32 случайного
  значения;
- кнопка: `act:od2:<token>:<вариант>` (≤ 24 байт);
- при нажатии бот берёт версию из карты по `token` и передаёт её как `expected_version`;
- неизвестный или просроченный `token` ⇒ отказ «Кнопка устарела — карточка отправлена заново».

## 6. Миграция

- **Открытые карточки:** при включении бот один раз переотправляет все открытые карточки владельца уже
  с `act:od2:` и записанной версией; старые кнопки `act:od:` с этого момента отвечают «кнопка устарела —
  ответьте на новое сообщение» и ничего не пишут.
- **Уже отвеченные карточки:** версия ответа задним числом **не придумывается**. Их ответы попадают в
  журнал строкой `outcome: LEGACY_UNVERSIONED`, `decision_version: null`; пульт показывает «версия
  ответа не записана (ответ дан до включения проверки)».
- Пульт (DIRECTOR-OS-UX-02) читает `owner_answer_version` и журнал через Company Truth и только тогда
  меняет формулировку на «ответ записан на версию …»; до этого — нынешняя честная фраза.

## 7. Тесты (до включения)

1. `decision_version` детерминирована; служебные поля её не меняют; правка текста варианта меняет.
2. Запись с совпавшей версией — `RECORDED`, журнал + frontmatter.
3. Карточку изменили после отправки — `DecisionChanged`, файл не тронут, журнал `REFUSED_CHANGED`.
4. Тот же вариант дважды — `IDEMPOTENT`, одна строка `RECORDED`.
5. Другой вариант на ту же версию — `REFUSED_ALREADY_ANSWERED`, исходный ответ цел.
6. Новая версия → ответ — обе строки в журнале, frontmatter указывает на последнюю.
7. Не владелец — `NotTheOwner` (как сейчас), журнал `REFUSED_NOT_OWNER` без данных отправителя.
8. Кнопка `act:od2:` укладывается в 64 байта; неизвестный token — отказ без записи.
9. Старая кнопка `act:od:` после миграции ничего не пишет.
10. Ошибка чтения файла/журнала — отказ без записи (третий исход, не «успех»).
11. Пульт: при `owner_answer_version` показывает версию ответа; без неё — «версия ответа не записана».
12. Параллельная правка карточки и ответ: победитель ровно один; проигравший — явный отказ, файл и
    журнал согласованы.
13. Два одновременных ответа на одну версию: один `RECORDED`, второй `REFUSED_ALREADY_ANSWERED`
    (или `IDEMPOTENT` при том же варианте).
14. Повтор того же `callback_query.id`: ничего не пишется, ответ бота тот же.
15. Сбой между шагами п. 2c (имитация `kill` после `pending` и после замены карточки): после старта
    сверка приводит к `committed` или `aborted`, без молчаливых правок.
16. Расхождение журнала и карточки: пульт пишет «расхождение», кнопки ответа нет.
17. Флаг `off` и повреждённый флаг: ни одна кнопка ничего не пишет; просмотр работает.

## 8. Откат

Откат **никогда не возвращает ответ без проверки версии**. Флаг `owner_answer.versioned_write`
(конфигурация бота) работает только в одну безопасную сторону:

- `on` — запись через `act:od2:` с проверкой версии (п. 2–2d);
- `off` (откат) — **запись ответов из кнопок отключена**: бот показывает карточки и пишет «приём ответов
  временно выключен — решение можно передать агенту в чате, он оформит его карточкой», ничего не
  записывая; старые кнопки `act:od:` тоже ничего не пишут;
- флаг не прочитан или повреждён ⇒ поведение `off` (fail-CLOSED).

Просмотр остаётся: пульт и бот показывают карточки, журнал и историю ответов. Журнал
`owner_answers.jsonl` не удаляется; карточки с `owner_answer_version` читаются старым кодом без ошибок.
Возврат к прежнему `act:od:` без проверки версии этим планом **не предусмотрен** — для этого нужно
отдельное решение владельца.

## 9. Риски

- Частая правка карточки агентом во время ожидания ответа даст серию отказов — нужно правило «не
  менять смысловые разделы открытой карточки без переотправки».
- Долгоживущий процесс бота держит старый код до перезапуска — включение требует перезапуска бота
  (действие владельца, `.claude/rules/deployment.md`).
- Две копии карточки (origin и прод-дерево) уже бывают разными (`find_answer_copies`); версия должна
  считаться по той копии, которую бот прислал, — это фиксируется в `owner_decision_sends.json`.
