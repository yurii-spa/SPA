# S2 · задача 04 — фактический запуск из проверенного релиза, переход A → B и откат B → A на изолированном стенде (E5.5/E5.6, частично)

**Статус:** пакет зафиксирован ДО кода (этот коммит); реализация — следующим коммитом той же ветки.
**Основание:** ADR-882 (решение ARB 31.10): «доказать фактическое исполнение проверенного релиза и откат в
изолированном окружении, используя существующую реализацию».
**Граница по каноническому плану:** `docs/tasks/studio-autonomy-01-2026-10-29.md` (ветка `autonomy/s1`, `976862fb0`):
«Пять поставок и порядок» → S2 = E4–E5; эта задача касается только E5.5 (измерение реального запуска) и E5.6
(откат) **на стенде**. E4 ею не закрывается и не подменяется. Наблюдение за живой канарейкой — E8.4 (S5).
**Режим исполнителя:** «патч для разбора», worktree `s2_release`; без root, без launchd, без прод-данных, без сети,
кроме git. Production не активируется.

## Что используется из существующей реализации (без изменения правил)
- `release_launcher.main(service, root=…, python=None, active_path=…)` — настоящий путь исполнения: проверка
  одобрения → `exec_root` (состав по проверенному дереву коммита) → роль из `studio_release_agents.json` релиза →
  интерпретатор из `runtime.json` → запись `active` → `os.chdir(release)` + **`os.execv`**. Флаги `-E -s`.
- Одобрение — как у установщика: `approved_release.json` = `{"approved_sha": <sha>}` (только SHA, никакой команды).
- `release_activation.materialise_release` — подготовка релиза; `release_state.active_from_process` — замер ACTIVE по
  живому процессу (cwd → `releases/<sha>` → `.release_sha`) через штатный `_default_release_procs` (pgrep + lsof).

## Сцена (одноразовая, всё под временным каталогом теста)
- Тестовый git-репозиторий: коммит **A** и коммит **B**. В КАЖДОМ коммите — модуль роли `spa_core/probe_role.py`
  (своя метка версии) и манифест `studio_release_agents.json` `{"probe": "spa_core.probe_role"}`; манифест входит в
  коммит ДО материализации и одобрения, задним числом в релиз ничего не добавляется.
- Роль безвредна: читает ТОЛЬКО переменную `STUDIO_PROBE_STATE` (каталог сцены); без неё — выход без записи; пишет один
  файл-пульс (метка версии, pid, cwd, `__file__`, `sys.path[0]`) в этот каталог, ждёт файл `stop` (не дольше 60 с) и
  выходит 0. Не порождает детей, не открывает сеть, не читает секреты и рабочие данные.
- «Доверенный корень» стенда — обычный каталог пользователя (НЕ root-owned): `approved_release.json`,
  `runtime.json` (`app_python` = текущий интерпретатор, `trusted_repo` = тестовый репозиторий), `releases/`.
- Запуск — как launchd запускал бы установленный лаунчер: ОТДЕЛЬНЫЙ процесс `python3 -I` грузит копию
  `release_launcher.py` из проверяемого дерева и зовёт `main("agent:probe", root=<стенд>, active_path=<стенд>)`;
  при отказе — код 3, как в `__main__`. Обёртка нужна только потому, что `__main__` намеренно не даёт сменить
  корень; правила лаунчера не меняются.
- Каждый шаг пишет запись состояния в `<стенд>/state/transitions.jsonl` (шаг, одобренный sha, вердикт/код
  лаунчера, pid, измеренный ACTIVE, пульс).

## Критерии приёмки (до работы; исполнитель их не правит)
| # | Критерий |
|---|---|
| D1 | процесс, запущенный лаунчером при одобренном A, — это тот же pid, что у процесса лаунчера (`execv`, а не дочерний), его пульс несёт метку **A**, `cwd` = `releases/<A>`, `__file__` внутри `releases/<A>`; `active_from_process` по живому процессу — `active_sha = A`, `active_verified = True` |
| D2 | при этом рабочее дерево тестового репозитория изменено (незакоммиченная правка роли с меткой `WORKTREE`), и `PYTHONPATH` указывает на него — запущен всё равно A |
| D3 | нет одобрения ⇒ код 3, `DEPLOYMENT_APPROVAL_REQUIRED`; одобрен sha без релиза ⇒ код 3, `APPROVED_RELEASE_MISSING`; одобрен повреждённый релиз ⇒ код 3, `APPROVED_RELEASE_CORRUPT`. Во всех трёх — ни пульса, ни нового процесса, запись `active` не создана и не изменена |
| D4 | пока A работает: кандидат B подготовлен и **повреждён**, одобрение переключено на B ⇒ лаунчер отказывает (код 3); A продолжает работать, `active_from_process` = A, запись `active` = A |
| D5 | переход A → B: A остановлен, B подготовлен заново из коммита (повреждённая копия СОХРАНЯЕТСЯ рядом под другим именем, не удаляется), одобрен B, запуск ⇒ пульс **B**, замер ACTIVE = B, запись `active` = B |
| D6 | откат B → A: B остановлен, одобрен A, запуск ⇒ пульс **A**, замер ACTIVE = A; каталог релиза A побайтно тот же, что до перехода (сверка состава с деревом A + хеш всех файлов) |
| D7 | после каждого шага и в конце: у теста нет живых процессов (каждый запущенный pid завершён и собран, группа процессов сессии пуста), ни один процесс не держит cwd в каталоге релизов стенда |
| D8 | рабочие службы и данные не изменены: файл `ACTIVE_MARKER_PATH` по умолчанию (`~/Documents/SPA_Claude/data/active_release.json`) и каталог `/Library/Application Support/StudioOS` до и после — то же наличие и `mtime`; тест не зовёт launchctl, не пишет в прод-дерево |
| D9 | `transitions.jsonl` содержит запись каждого шага D1–D6 с измеренными значениями; сохранённые записи сцены — в доказательствах |
| D10 | контроль в обе стороны: мутация «лаунчер исполняет без проверки состава» краснит D3/D4; мутация «лаунчер берёт sha из штампа каталога, а не из одобрения» краснит D5/D6; мутация «роль из рабочего дерева» краснит D2 |

## Что стенд НЕ доказывает (NOT MEASURED, сохраняется)
- установку доверенного root-owned bootstrap (права root:wheel, запрет записи пользователю) — стенд работает от
  пользователя в его каталоге;
- живую активацию: ни одна служба launchd не перенаправляется и не перезапускается;
- E4 целиком.
