## Что связано (всё — существующие части)
`mission_intake.submit` (запись) → приём → `cockpit_dispatch.dispatch` (обычная запись ⇒ честное «не взято в работу»)
→ **явный** `python -m spa_core.studio_os.memory prepare-record` (= `arch_review.prepare_record`, task-prep на том же
role-pack и контракте) → `mission_control.cockpit_records(task_prep_root=…)` → `owner_view.my_records` → UI «Работа →
Мои записи». Новое: `request_text_of`, `prepare_record`, `preparation_state`, `preparation_runs`; поле
`MCInputs.task_prep_root` (по умолчанию `None` ⇒ в production блока нет); блок `preparation` в строке; рендер в UI.

## Гарантии (тесты `test_task_prep_record.py`, 14; мутации 6/6)
- обычная запись без пробы получает видимый план/вопрос; исполнение показано отдельно и честно;
- подготовка НЕ пишет карточку, НЕ ставит `acceptance_probe`, НЕ захватывает, НЕ меняет статус — диспетчер после неё
  по-прежнему отвечает `no_probe`;
- повтор при тех же входах — `unchanged`, без вызова и без нового каталога, даже при другом времени;
- изменённый текст поручения или любой источник контекста ⇒ «план устарел»: свежесть считает ЧИТАТЕЛЬ по карточке и
  файлам, перечитанным сейчас (сохранённые хеши — только то, с чем сравнивают); старый каталог сохраняется;
- неполный ответ, квота, отказ провайдера ⇒ «подготовка не удалась», плана нет;
- читающее представление ничего не готовит, никого не зовёт и ничего не пишет;
- текст модели идёт строкой и кладётся текстовыми узлами; в `app.js` нет `innerHTML`/`outerHTML`/
  `insertAdjacentHTML`/`document.write`/`eval(`.
