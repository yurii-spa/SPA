# Замер: два пути APY дают разные числа по одному протоколу (ADR-089 п.3)

- **Статус:** ЗАМЕР. Кода не менял ни строки — ни `spa_core/risk/`, ни `spa_core/allocator/`,
  ни `cycle_runner`. Документ называет механизм и предлагает починку; починка — отдельная задача.
- **Дата замера:** 2026-08-15
- **Предмет:** `aave_v3` — **4.80 %** в одном пути и **2.36 %** в другом (наблюдение владельца
  10.08, `owner-decision-sistema-ostanovlena-avariinym-vyklyuchat.md`; раньше в ту же минуту
  00:52 было **14.05 %** против **2.36 %**). Плюс `pendle` 14.01 % при `live_apy: null`.
- **Данные замера:** git-снимок `data/` этого дерева. **Он НЕ содержит пары 4.80/2.36** —
  см. раздел «Чего не хватает». Механизм расхождения измерен по коду и по зафиксированным
  фикстурам реального скана; конкретная пара 4.80/2.36 воспроизведению офлайн не поддаётся,
  и я её НЕ достраиваю (инв. 2, fail-CLOSED).

## 1. Главный вывод в трёх строках

Расхождение — **не единицы измерения** (проверено численно, п. 4) и **не арифметика**.
Это **два разных производителя наблюдения, у которых разные правила опознания пула**, плюс
**два разных поля** в одном файле, одно из которых доказывает наблюдение, а другое — нет.
Прав тот путь, который читает `live_apy` у производителя с проверкой личности актива: это
**2.36 %**. Число **4.80 %** приходит из матчера **без** такой проверки и совпадает с
зафиксированной в тестах доходностью пула ЧУЖОГО актива (**4.79338 %**).

## 3. Путь Б — отчёт и начисление

### Б1. Дневной отчёт, строка позиции («40 % под 2.7 %»)

`spa_core/reporting/daily_telegram_report.py`:

- `_adapter_meta` (**160–174**) читает `adapters[key]["apy"]` — **поле `apy`, не `live_apy`**;
- `format_daily_message` (**453–459**) печатает это число рядом с долей позиции;
- `_live_apy` (**217–228**) для Base-адаптеров: `apy_pct` → `apy` → **литерал из
  `_BASE_ADAPTERS_REGISTRY`** (строки 91–94, например `aave_v3_base: 4.5`);
- **проверки возраста файла нет вообще** — `generated_at` в этом модуле не читается.

### Б2. «Paper APY» в шапке отчёта — это другая величина

`daily_telegram_report.py:429–432` берёт `apy_today_pct`, который пишет
`cycle_runner.py:2084–2089`:

```
weighted_apy = sum(usd * apy_map[p] for p, usd in positions) / prev_equity
```

Знаменатель — **вся equity, включая кэш** (комментарий строки 2083: «cash drags»).
Рядом, в `cycle_runner.py:2209`, живёт ВТОРАЯ величина с тем же смыслом, но
знаменателем `deployed`. Это два разных числа под одним именем «APY» — отдельная ось путаницы,
не относящаяся к `aave_v3`, но обязательная к разведению (п. 6.4).

### Б3. Карта начисления `apy_map`

## 4. Гипотеза единиц измерения — ПРОВЕРЕНА И ОТВЕРГНУТА

`.claude/rules/adapters.md` предупреждает: старые адаптеры (aave/yearn/euler/maple) отдают
decimal, новые — percent. Проверял, потому что это самая дешёвая версия. Она неверна.

**Арифметика.** 4.80 / 2.36 = **2.034**. Ошибка единиц даёт ровно ×100 или ×0.01, но никак
не ×2.03. Пара 14.05 / 2.36 = 5.95 — тоже не степень десяти.

**Замер на данных `data/` этого дерева** (единственный протокол с живым замером в снимке —
`compound_v3`):

| Величина | Значение |
|---|---|
| `adapter_orchestrator_status.json` → `compound_v3.apy_pct` | `5.2` (проценты) |
| `_load_evidenced_apy(...)` (путь А) | `{'compound_v3': (0.052, 'orchestrator_live')}` (decimal) |
| decimal × 100 (`allocator.py:908`) | `5.2` |
| `_live_apy_map(...)` (путь Б) | `{'compound_v3': 5.2}` (проценты) |

**Дрейф единиц = 0.** Оба пути конвертируют ровно один раз и в одну сторону: адаптер отдаёт
decimal (`spa_core/adapters/apy_contract.py` — канонический контракт: `get_yield_info().apy`
это ДЕСЯТИЧНАЯ доля), оркестратор умножает на 100 однократно
(`spa_core/orchestrator/adapter_orchestrator.py:192`), аллокатор делит на 100 и умножает обратно.

**Вывод: единицы — не причина.** Гипотезу закрываю.

## 5. ГДЕ ИМЕННО ОНИ РАСХОДЯТСЯ — четыре оси

### Ось 1 (главная для 4.80 против 2.36): **разные матчеры пула у двух производителей**

`adapter_status.json` и снимок оркестратора пишутся **разным кодом с разными правилами
опознания пула**:

| | `adapter_status.json` | снимок оркестратора / прямой вызов адаптера |
|---|---|---|
| Кто пишет | `spa_core/monitoring/adapter_status_generator.py` | `spa_core/orchestrator/adapter_orchestrator.py` → `AaveV3Adapter.fetch()` → `spa_core/adapters/defillama_feed.py` |
| Разрешение пула | пин по UUID (`:562–567`), затем hint `_hint_pool` (`:460–530`) | `DeFiLlamaFeed.get_pool` (`:115–159`) |
| Проверка личности актива | **ЕСТЬ** — `underlyingTokens` обязан совпасть с `_CANONICAL_UNDERLYING` (`:490–517`), иначе отказ + `pool_match_refused` | **НЕТ** — совпадение project/symbol/chain, дальше «побеждает больший TVL» (`:153–157`) |

Проверку личности актива поставил цикл **#188** (карточка
`inbox-nechetkoe-sovpadenie-otdaet-apy-chuzhogo.md`) — и поставил **только в генераторе**.
Проверка: `_CANONICAL_UNDERLYING` и `pool_match_refused` встречаются во всём `spa_core/`
ровно в `monitoring/adapter_status_generator.py` и трёх тест-файлах. В `defillama_feed.py`
их нет — общий фид, из которого читают ВСЕ адаптеры, остался незащищённым.

**Смыкание с числом 4.80.** Фикстура реального скана 2026-08-09/10 лежит в
`spa_core/tests/test_feed_hint_asset_identity.py:79–84`:

| Пул | symbol | `underlyingTokens` | TVL | APY |
|---|---|---|---|---|
| настоящий (`:44–49`) | `USDC` | `0xA0b8…eB48` (Circle USDC) | $178.7M | **3.29338 %** |
| самозванец (`:79–84`) | `USDC` | `0xD4fa…D23E` (не USDC) | $64.8M | **4.79338 %** |

`4.79338 ≈ 4.80` — то самое число, которое снимок оркестратора показал 10.08 в 02:30.
Symbol у самозванца **буквально `USDC`**, поэтому даже строгий `symbol_mode="exact"` в
`get_pool` его пропускает: единственное, что их различает — `underlyingTokens`, и именно
это поле незащищённый матчер не читает. Правило «побеждает больший TVL» — не свойство
правильности, а свойство текущих чисел: как только самозванец крупнее, он выигрывает молча.

### Ось 2: **разные поля одного файла** — `live_apy` против `apy`

Контракт уже написан и уже принят — `ADR-063`, воплощён в
`spa_core/adapters/status_reader.py` (докстрока, строки 16–25):

> `adapters[<protocol>].live_apy` — явное «я это наблюдал». `null` значит НЕ наблюдал, и тогда
> соседнее поле `apy` просто повторяет `fallback_apy`. Поэтому `apy` из этой секции **НИКОГДА
> не читается**: оно не отличает замер от литерала.

Кто соблюдает контракт: аллокатор (`allocator.py:365`), адаптеры sdai/sfrax/frax/spark/susde
(через `status_reader.read_live_apy_pct`).
Кто нарушает: `daily_telegram_report.py:172` и `:223–228`, `cycle_runner.py:1051` (MP-413).
Ни один из трёх не импортирует `status_reader`.

### Ось 3: **разная свежесть**

- Путь А: окно **36 ч** по `live_apy_as_of` (`allocator.py:334–354`), протухшее наблюдение
  свидетельством не является.
- Путь Б: **окна нет**. Отчёт напечатал бы число из файла возрастом 11 суток без единой пометки.

### Ось 4: **разная база у портфельного APY** (к `aave_v3` не относится, но путает читателя)

`apy_today_pct` от `cycle_runner:2084–2089` — по ВСЕЙ equity (кэш разбавляет);
`cycle_runner:2209` — по `deployed`; `last_approved_allocation.json → apy_today_pct`
(в снимке — `4.8117`) — ожидаемая доходность цели, а не реализованная. Три разных величины,
одно имя. Именно поэтому «40 % под 2.7 %» и «ожидаем 4.8 %» встречаются в одном дне.

### Чем расхождение НЕ является

- Не единицы (п. 4).
- Не разный ключ протокола: обе стороны используют один `aave_v3`.
- Не gross/net: ни один из путей не вычитает комиссии — оба берут `pool["apy"]` DeFiLlama
  как есть (`defillama_feed.py:169`, `adapter_status_generator.py:336`).
  Заметить стоит другое: это **суммарный** APY (`apy`, включая `apyReward`), а не `apyBase`;
  ни один из путей это не различает, и на протоколе с наградами оба будут завышать одинаково.

## 6. Какой путь прав и что чинить в источнике

### 6.1. Кто прав по числу

**Прав `adapter_status.json` — 2.36 %**, при выполненном условии `live_apy != null` и возрасте
наблюдения в окне. Основание: только у этого производителя пул опознаётся по личности актива
(`underlyingTokens`), и только у него отказ называется вслух (`pool_match_refused`).
**4.80 % — число, полученное матчером без проверки личности**, и оно совпадает с
зафиксированным APY чужого актива. Самозванец всегда платит БОЛЬШЕ настоящего — поэтому
дефект выглядит как удача, а не как поломка, и поэтому же он опасен: он двигает ранжирование
в сторону входа.

### 6.2. Кто прав по правилу

**Прав аллокатор** — как дисциплина, не как число. Он один требует доказательства наблюдения
(`live_apy`), окна свежести и явного отказа при их отсутствии. Отчёт и MP-413 называют число
там, где наблюдения нет вовсе, — это ровно тот класс дефекта, ради которого написан ADR-063.

**Обе половины вывода нужны одновременно:** правило аллокатора верное, но он ходит и в
незащищённый источник (`_default_live_apy_provider` → адаптер → `DeFiLlamaFeed.get_pool`),
поэтому «прав по правилу» не спасает его от «неправ по числу».

### 6.3. Одно определение на репозиторий — что чинить

1. **Один матчер пула.** Перенести проверку `underlyingTokens` (`_CANONICAL_UNDERLYING`) из
   `adapter_status_generator.py` в общий `spa_core/adapters/defillama_feed.py::get_pool`, чтобы
   оба производителя опознавали пул одинаково. Пока этого нет, любые «сведения путей» на уровне
   потребителя косметические: расходятся не потребители, а источники.
   **Это money-path** ⇒ отдельная задача, `pre_cutover_gate`, изолированный workspace.
2. **Одно поле наблюдения.** `live_apy` (+ `live_apy_as_of`) — единственное. Все читатели идут
   через `spa_core/adapters/status_reader.read_live_apy_pct`. Правки: `_adapter_meta` и
   `_live_apy` в `daily_telegram_report.py`, MP-413 в `cycle_runner.py:1039–1061`.
   Нет наблюдения ⇒ отчёт печатает «—» и называет причину, а не литерал.
3. **Одно окно свежести.** `_EVIDENCE_MAX_AGE_H` — единственная константа на репозиторий;
   отчёт обязан ей подчиняться.
4. **Одно имя на одну величину.** Развести `expected_apy_deployed_pct` (цель аллокатора, база —
   размещённое), `realized_apy_equity_pct` (факт трека, база — вся equity) и
   `pool_apy_pct` (доходность протокола). Сегодня все трое зовутся «APY».
5. **Тай-брейк — fail-CLOSED, а не «свежее выигрывает».** `allocator.py:373–381` при
   расхождении двух производителей берёт свежего и лишь ЛОГИРУЕТ разницу. Пока матчеры разные,
   расхождение >N б.п. должно означать ОТКАЗ по протоколу (инв. 2), а не выбор по часам:
   сейчас личность пула, на который ранжируется капитал, определяется тем, какой файл записан
   последним.

### 6.4. Чего чинить НЕ надо

Показывать оба числа рядом — владелец этот вариант отверг (карточка): он лечит читателя,
а не решение. Ранжирование всё равно останется на одном из них.

## 8. Чего не хватает для окончательного утверждения (fail-CLOSED, инв. 2)

Механизм назван и подтверждён кодом. **Конкретная пара 4.80 / 2.36 офлайн не воспроизводится**,
и я её не достраиваю. В git-снимке `data/` этого дерева:

- `adapter_orchestrator_status.json` — от **2026-06-21**, `aave_v3` в нём `status: error`,
  `apy_pct: None`;
- `adapter_status.json` — от **2026-08-04**, `aave_v3.live_apy: null`;
- ни одного живого замера `aave_v3` ни с одной стороны.

**Чтобы утверждать окончательно, нужно ровно одно и оно недоступно из репозитория:**

1. **Ответ DeFiLlama `/pools`, снятый в момент расхождения** (10.08, ~02:30 UTC) или свежий
   одномоментный снимок — чтобы прогнать через ОБА матчера в песочнице и назвать
   **UUID пула и `underlyingTokens`**, которые каждый выбрал.
2. **`pool_match` / `pool_match_refused` для `aave_v3`** из прод-`adapter_status.json` того
   момента (пин или hint) — генератор это поле пишет (`adapter_status_generator.py:825–832`),
   в git-снимке оно отсутствует, потому что снимок старше правки #188.

Без (1) я утверждаю: **числа приходят из матчеров с разными правилами, и 4.80 совпадает с
зафиксированным APY чужого актива**. Я НЕ утверждаю: «оркестратор 10.08 взял именно пул
`0xD4fa…D23E`». Это проверяется за один прогон в песочнице и не проверяется рассуждением.

Отдельно и тем же способом проверяется `pendle` **14.01 %** при `live_apy: null` — это тот же
класс: один путь называет число, второй честно молчит. По `pendle` вдобавок есть своя ловушка,
уже описанная в коде (`adapter_status_generator.py`, `_PT_BUY_PREFIX`): PT и LP на Ethereum
несут одинаковый symbol и одинаковый TVL при APY 4.26 % против 12.39 %, и различает их
ТОЛЬКО `poolMeta`. Правило «побеждает больший TVL» выбирает между ними монеткой — а
`DeFiLlamaFeed.get_pool` не читает `poolMeta` вовсе.

## 10. Перемер 2026-08-18 — своим прогоном, и что после него сведено

Замер 15.08 (разделы 1–9) перепроверен прогонами в контейнере. Сеть НЕ трогалась: только
`FakeFeed`/инъекции и записанные фикстуры живого скана (`.claude/rules/adapters.md`).
Все числа ниже — вывод прогонов этой итерации; там, где перемерить нельзя, это сказано прямо.

### 10.1. Оба пути на живом `data/` — дословный вывод

```
PATH A  _load_evidenced_apy() entries: 1
PATH A  aave_v3: None  pendle: None
PATH A  full: {'compound_v3': (0.052000000000000005, 'orchestrator_live')}
EVIDENCE_MAX_AGE_H = 36.0
adapter_status.json generated_at: 2026-08-17T11:07:33.148588+00:00
adapter_orchestrator_status.json generated_at: 2026-06-21T01:23:22.080149+00:00
live_apy non-null: [] of 34
apy != fallback_apy: []
tvl_source live: []
```

Ноль наблюдений из 34, и `apy` **ни у одного** протокола не отличается от `fallback_apy` —
то есть все 34 числа были эхом константы реестра. Что при этом печатал отчёт ДО правки
(перемерено чтением того же поля, которое читал старый `_adapter_meta`):

```
ДО правки отчёт назвал бы число для 34 из 34 протоколов
   aave_v3 = 3.5  pendle = 8.0  compound_v3 = 5.2
   при этом live_apy non-null: 0
```

### 10.2. Несимметричное окно свежести внутри пути А — новая находка

В замере 15.08 этого не было. Окно 36 ч (`_within_window`, `allocator.py:334–354`) стоит
**только** на ветке `adapter_status`. Ветка «оркестратор» (`allocator.py:311–318`) проверки
возраста не имеет вовсе — поэтому единственное сегодняшнее «свидетельство»,
`compound_v3 = 5.2 %`, взято из снимка `generated_at 2026-06-21T01:23:22Z`:

```
возраст снимка оркестратора, суток: 58.8
```

58.8 суток проходят как свидетельство при объявленном окне 36 часов. Это
`spa_core/allocator/` — money-path, в этой задаче не трогалось (вынесено карточкой).

### 10.3. Гипотеза единиц измерения — отвергнута повторно, ЗАМЕРОМ

Одна вселенная фида (записанный скан 09–10.08, `test_feed_hint_asset_identity.py:44–84`),
два производителя:

```
записанный скан 09-10.08: настоящий TVL = 178734645.0 apy = 3.29338
                          самозванец TVL = 64767732.0 apy = 4.79338
ПРОИЗВОДИТЕЛЬ 1 (adapter_status_generator):
   live_apy    = 3.2934  pool_match = hint
ПРОИЗВОДИТЕЛЬ 2 (DeFiLlamaFeed.get_pool):
   pool        = 6f00d46b-8735-49ae-9ced-2a0fccc56ad0  underlying = ['0xD4fa2D31b7968E448877f69A96DE69f5de8cD23E']
   apy         = 0.0479338 -> 4.79338 %

ОДНА ВСЕЛЕННАЯ ФИДА -> ДВА ОТВЕТА: 3.2934 против 4.79338
отношение: 1.4555
```

**Что значит 1.4555.** Ошибка единиц (decimal против percent) даёт РОВНО ×100 или ×0.01 —
множитель, который ни от каких данных не зависит. 1.4555 не степень десяти и вообще не
константа: это отношение доходностей ДВУХ РАЗНЫХ ПУЛОВ, и завтра оно будет другим. Значит
расходятся не единицы, а **предмет измерения**. `.claude/rules/adapters.md` предупреждает про
непоследовательные единицы, и это самая дешёвая версия — здесь она неверна, и отвергнута
числом, а не рассуждением. (Замер 15.08 отверг её на паре 4.80/2.36 → 2.034; тот же вывод.)

### 10.4. Почему производители разошлись: проверка личности актива стоит только у одного

```
=== где живёт проверка личности актива (вне тестов) ===
spa_core/monitoring/adapter_status_generator.py:87   _CANONICAL_UNDERLYING = {...}
spa_core/monitoring/adapter_status_generator.py:627  expected = _CANONICAL_UNDERLYING.get((chain_l, sym_u))
spa_core/monitoring/adapter_status_generator.py:990  "pool_match_refused": match_refused
=== вхождений "underlyingTokens" в spa_core/adapters/defillama_feed.py ===
0
```

Генератор обязывает `underlyingTokens` совпасть с объявленным активом и **называет отказ вслух**
(`pool_match_refused`). Общий `DeFiLlamaFeed.get_pool` (`defillama_feed.py:115–159`) сверяет три
строки — project / symbol / chain — и дальше берёт пул с бо́льшим `tvlUsd`
(`:153–157`); поле `underlyingTokens` он не читает ни разу. Символ у самозванца буквально
`USDC`, поэтому даже строгий `symbol_mode="exact"` его пропускает.

«Побеждает больший TVL» — не свойство правильности, а свойство чисел этой недели. И именно этот
незащищённый матчер кормит money-path: `allocator._default_live_apy_provider` → адаптер →
`DeFiLlamaFeed`.

**Правильное число — то, что даёт производитель с проверкой личности** (пул
`aa70268e…`, `underlyingTokens 0xA0b8…eB48`, Circle USDC). 4.79338 ≈ 4.80 приходит с пула
`0xD4fa…D23E`, который называется «USDC», но им не является. Подделка платит БОЛЬШЕ настоящего —
поэтому дефект читается как удача и двигает решение в сторону входа.

### 10.5. Честная оговорка про это воспроизведение (fail-CLOSED, инв. 2)

В записанном скане **настоящий пул крупнее** самозванца ($178.7M против $64.8M), поэтому
правило «больший TVL» на нём выбирает верно. Чтобы получить 4.79338, я поднял TVL самозванца до
$200M — это перечислено выше в самом выводе прогона, чтобы никто не прочитал результат как
снимок продакшена.

Следствие строгое: **доказан МЕХАНИЗМ** (матчер без проверки личности отдаёт APY чужого актива,
как только тот крупнее), и **не доказано**, что 10.08 в ~02:30 оркестратор взял именно пул
`0xD4fa…D23E`. Для второго нужен ответ DeFiLlama `/pools` того момента и поля
`pool_match` / `pool_match_refused` из прод-`adapter_status.json` того часа. Сети из контейнера
нет; я это не достраиваю.

### 10.6. `pendle` 14.01 % — это НАБЛЮДЕНИЕ, а литералом была вторая половина пары

```
hint для 'pendle': None | всего подсказок: 15
протоколов в реестре: 34 | из них с подсказкой: 15
ПРОИЗВОДИТЕЛЬ A (adapter_status.json), пул 14.01 % прямо во входе:
   {'live_apy': None, 'apy': 8.0, 'fallback_apy': 8.0, 'pool_match': None, 'pool_match_refused': None}
ПРОИЗВОДИТЕЛЬ B (PendleAdapter -> Pendle V2 REST API):
   get_apy()     = 0.1401 (decimal)
   apy_pct       = 14.01
   пустой ответ API -> get_apy() = None
```

Три факта, каждый перемерен:

1. **Ключа `pendle` нет в `_DEFILLAMA_HINTS` вовсе** (15 подсказок на 34 протокола реестра).
   Прогон генератора с подходящим пулом ПРЯМО ВО ВХОДЕ всё равно даёт `live_apy: None` — и,
   что хуже, `pool_match_refused: null`: отказ даже не назван. `apy: 8.0` — чистое эхо
   `fallback_apy`. **Литералом, выдающим себя за наблюдение, была именно эта половина пары**,
   а не 14.01.
2. **14.01 % — честный живой замер** от третьего производителя: `PendleAdapter` →
   `pendle_pt.get_top_markets()` → родное API Pendle V2, мимо DeFiLlama и мимо генератора.
   Подстановки литерала на этом пути нет: пустой ответ API ⇒ `None` ⇒ оркестратор пишет
   `live_data: false` (fail-CLOSED).
3. **Но это МАКСИМУМ, а не наша позиция.** `get_top_markets` сортирует по убыванию доходности и
   отдаёт лучший рынок: в прогоне выбран рынок с TVL $8.24M и 14.01 % при наличии рынка с TVL
   $50M и 4.26 % — выбран НЕ крупнейший, а доходнейший. Это «лучшее, что сейчас предлагает
   Pendle», а не «сколько платит то, чем мы владеем» — третья величина под именем «APY»
   (ось 4 раздела 5). Ловушка PT-против-LP (`_PT_BUY_PREFIX`) к этому пути не относится: он
   берёт маркеты Pendle API, а не пулы DeFiLlama.

### 10.7. Что сведено к одному определению

Читательская половина (не money-path):

* `spa_core/adapters/status_reader.py` — **канонический дом** правила. К уже существовавшему
  `observed_apy_pct_from_block` (ЧТО такое наблюдение — только `live_apy`) добавлены
