### Что оказалось за ошибкой типов

Ошибка mypy назвала настоящую дыру, а не стилистику. `json.loads` возвращает `Any`, поэтому
аннотация `-> dict` не проверяла НИЧЕГО, а `try` в `_read` накрывал только чтение и разбор — но
не ФОРМУ разобранного. Валидный JSON, который просто не является объектом, шёл насквозь.
Воспроизведено на чистом `origin/main` `49d0d1122` — **шесть падений**:

```
orch = []            -> AttributeError: 'list' object has no attribute 'get'
orch = "text"        -> AttributeError: 'str' object has no attribute 'get'
orch = 5             -> AttributeError: 'int' object has no attribute 'get'
orch adapters = 5    -> TypeError: 'int' object is not iterable
status = []          -> AttributeError: 'list' object has no attribute 'get'
status adapters=[1,2]-> AttributeError: 'list' object has no attribute 'items'
```

Докстринг `_load_evidenced_apy` при этом обещает: «Never raises: any unreadable/invalid input
contributes nothing». Обещание неверно, а вызов в аллокаторе (`allocator.py`, блок ADR-061)
**не обёрнут** — исключение улетало наружу, в money-path шаг аллокации дневного цикла. Это тот
же класс, что #29/#31/#35–#38: контракт утверждает свойство, которого измерение не даёт.

**Фикс (fail-CLOSED, инв. #2):** не-объектный документ = такой же нечитаемый вход, что и битые
байты — лог + `{}`, причём фактический тип цитируется **вербатим**, иначе тихий `{}`
неотличим от «продюсеры ничего не наблюдали». Та же дыра этажом ниже закрыта для контейнера
`adapters` у обоих продюсеров (`_as_list` / `_as_map`). Пустой/отсутствующий контейнер —
не дефект и не логируется.

**Осознанное отличие:** мэппинг в `adapters` оркестратора теперь отвергается явно. Раньше он
итерировался по КЛЮЧАМ (строки), `isinstance(a, dict)` их отбрасывал ⇒ доказательств всё равно
не появлялось. Исход не изменился — появилась только видимая причина.

### Найдено сверх задачи: инструмент доставки молча продублировал секцию журнала

Второй пуш журнала за цикл приземлился на origin с **дублем целой секции** «Подтверждено реальным
Actions», а инструмент отчитался `OK … pushed=1, skipped=0`. Поймала это обязательная побайтовая
сверка с origin после пуша (`git show origin/main:<файл> | cmp - <файл>`), а не сам инструмент.

Механизм разобран точно: `push_to_github.py::rebase_append` берёт `base` из **git HEAD рабочего
дерева**, а не из того, что мы сами уже доставили. При двух пушах одного файла за цикл
`base = B`, `remote = B+S1` (мой же первый пуш), `local = B+S1+S2` ⇒ `tail = S1+S2` ⇒
`remote + tail = B+S1+S1+S2`. Оба `startswith(base)` истинны, поэтому отказа нет — случай
классифицирован как безопасное «чистое дописывание». На `STATE.md` (правка в середине) это дало бы
честный отказ; на журнале (дописывание в конец) даёт тихую порчу общей памяти.

Условия срабатывания — норма протокола, а не экзотика: §3.4 требует изолированный worktree, а
«Шаг 3» требует каждый цикл дописывать STATE и журнал; цикл, который дописывает журнал дважды
(сделал → потом подтвердил прогоном CI), попадает в них по построению.

**Исправлено на origin здесь же:** доказано, что origin без этих 19 строк побайтово равен моей
версии (чужих правок в файле нет — все три коммита в файле мои), после чего содержимое
восстановлено `--allow-overwrite`; сверка после — `cmp` чисто, вхождений заголовка ровно 1.
**Сам пушер НЕ правил** (мандат: одна задача за заход) → карточка бэклога
`agent-task-povtornoe-dopisyvanie-faila-v-odnom-tsik` с точным механизмом, предложением
(считать хвост от самого длинного известного префикса: `local.startswith(remote)` ⇒ результат =
`local`) и обязательным положительным контролем «настоящее параллельное дописывание двумя
сессиями по-прежнему сохраняет ОБЕ записи».

  обрабатывает `None` явно (`if val is not None`), после чего уходит на `canonical_apy_pct`;
* внутри самого spark каждый путь уже fail-CLOSED и согласован с ADR-063: `is_eligible()` →
  `False`, `health_check()` → `"degraded"`, `vs_morpho_gap()` → `None`, `get_yield_info()`
  пробрасывает `None`;
* `DEFAULT_APY_PCT` у spark **не читает ни одна строка кода** — только докстринги.

⇒ Потребителя, зависящего от подстановки, НЕТ. Красный тест — про себя, а не про дыру.

**Смежное, НЕ моё:** `morpho_steakhouse_adapter.get_apy_pct()` действительно возвращает литерал
6.5 % и никогда не `None` (поэтому арифметика на нём не падает) — но это ДРУГОЙ, уже
отслеживаемый домен (`agent-apy-evidence-provenance`,
`owner-decision-allokator-ranzhiruet-puly-na-vydumannom-tvl`, money-path). Не трогал.

### Что сделано

* тесты строят адаптер на **объявленном** входе (`data_dir` с герметичным JSON), а не читают
  окружающий `data/adapter_status.json`;
* **два положительных контроля** — `..._is_none_without_data` и `..._is_none_when_live_apy_null`;
* докстринги адаптера (модуль / класс / `get_apy`), обещавшие «fallback = 5.5 %», приведены к
  действующему поведению — это был третий пункт acceptance-критериев, и обе мёртвые сессии его
  **не сделали**: они правили только тест, а лгал ещё и сам адаптер. Константа `DEFAULT_APY_PCT`
  **сохранена** (удаление публичного атрибута шире задачи), но помечена «НЕ подстановка» со
  ссылкой на тест, который покраснеет при её возврате.

### Инвариант #16 — соблюдён механически, а не на слово

В диффе против `origin` **ноль** удалённых строк, содержащих `assert`: те же
`assertIsInstance(float)` / `assertGreater(0.0)` / `assertIsInstance(bool)`, правки строго
аддитивные. Сбор тестов в файле: **61 → 63 = ровно +2**, ни один не удалён и не заскипан.
Диффа поведения в адаптере нет вовсе — только докстринги и комментарии.

**Контроль доказан мутацией, а не заявлен.** Вернул fake-fallback в `get_apy()`
(`return _v if _v is not None else self.DEFAULT_APY_PCT`) — покраснели ровно два новых теста
(`AssertionError: 5.5 is not None`), при этом два ИСХОДНЫХ теста остались зелёными, что и
доказывает: они больше не зависят от окружающего файла. После отката — снова 62 passed.
