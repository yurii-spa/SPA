# Director OS Phase 1 — Owner Briefing

Утром владелец открывает одну страницу и за несколько минут получает пять ответов: на
какой момент у нас достоверная картина, что существенно изменилось, что требует внимания
и почему, что может потребовать его решения, и чего система пока не знает.

В этой фазе Director OS — **наблюдатель и составитель отчёта**. Он не управляет агентами,
не исполняет предлагаемые действия и не является новым источником истины.

## Архитектура (четыре слоя, граница между ними — жёсткая)

| Слой | Что делает | Чем реализован |
|---|---|---|
| **A. Capture** | единственный шаг, который НАБЛЮДАЕТ машину; read-only | существующий `snapshot.py` (Phase 0A/0B) |
| **B. Interpretation** | доказуемые изменения и карта источников | существующие `diff.py` + `source_of_truth.py` (Phase 0C) |
| **C. Owner Briefing** | пять разделов для владельца, ничего не наблюдает сам | новый `owner_briefing.py` |
| **D. Presentation** | Markdown и один статический HTML из ТЕХ ЖЕ данных | новый `render.py` |

B–D работают **offline**: ни production, ни Git, ни launchd, ни сеть, ни модель. Ни один
из этих модулей не импортирует `subprocess`, `socket` или `urllib`, и это проверяется
тестом — и структурно (AST), и поведенчески (прогон с закрытыми дверями).

### Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| Расширить `scripts/update_system_briefing.py` | Это writer прода под LaunchAgent, читающий живые источники. Нарушает и offline-требование, и запрет писать в production. `SYSTEM_BRIEFING.md` остаётся живым оперативным статусом — он отвечает на другой вопрос. |
| Слать сводку через `morning_work_digest.py` | Шлёт в Telegram; отправка сообщений запрещена. Предмет тоже другой: активность разработки, а не наблюдение системы. |
| Заводить карточки решений владельца | Инвариант #14: агент не создаёт и не закрывает решения владельца. Кандидаты в сводке — производные наблюдения с устойчивыми ID, и они ничего не создают. |
| Единый health score | Принятого контракта для него не существует. Поле есть, оно `null`, и рядом написано почему: любое единое число было бы сильнее имеющихся evidence. |
| Автовыбор baseline по последней папке | Молчаливый выбор запрещён. Автовыбор существует, но включается явным флагом и записывается в манифест вместе со списком кандидатов. |

## Три команды

```bash
cd ~/studio-os-scratch/cartographer-mvp
P=/Users/yuriikulieshov/miniconda3/bin/python3
SNAP=~/studio-os-snapshots

# 1. OFFLINE: сводка из двух ЯВНО названных сохранённых наборов
$P scripts/cartographer/brief.py \
   --old  $SNAP/<ранний набор> \
   --new  $SNAP/<поздний набор> \
   --output $SNAP/directoros-$(date +%Y%m%d-%H%M%S)

# 2. ONE-SHOT: новый read-only capture → сравнение с ЯВНО названным baseline → сводка
$P scripts/cartographer/brief.py \
   --capture --capture-into $SNAP \
   --old  $SNAP/<baseline> \
   --output $SNAP/directoros-$(date +%Y%m%d-%H%M%S)

# 3. ПЕРВЫЙ ЗАПУСК: baseline нет, сравнение не выдумывается
$P scripts/cartographer/brief.py \
   --new $SNAP/<набор> --first-run \
   --output $SNAP/directoros-$(date +%Y%m%d-%H%M%S)
```

Дополнительно: `--diff <каталог>` переиспользует готовое сравнение, но только если его
записанные хеши входов совпадают с переданными наборами; `--baseline-latest-in <каталог>`
— явно запрошенный автовыбор.

## Что получается

| Файл | Содержание |
|---|---|
| `index.html` | та же сводка страницей: открывается с диска двойным щелчком |
| `owner_briefing.md` | короткая сводка на русском |
| `owner_briefing.json` | данные, evidence и происхождение |
| `run_manifest.json` | входы, хеши, версии схем, выполненные проверки, список выходов |
| `diff.json` · `changes.md` | доказуемые изменения (нет в режиме первого запуска) |
| `source_of_truth.json` · `.md` | какой источник отвечает за какой род факта |

Каждый запуск пишет в **новый** каталог вне production и вне наблюдаемых worktree. Входные
наборы не изменяются. Незавершённый запуск остаётся в `<output>.incomplete` и не выглядит
опубликованной сводкой.

## Ограничения, которые страница соблюдает

- Возраст наблюдения показывается числом, а порог — `POLICY_UNDEFINED`: порога свежести
  наблюдения в репозитории не объявлено, и выдумывать SLA нельзя.
- Устаревшая сводка ≠ неисправная система, и это написано на самой странице.
- Внимание поднимается только для правил, у которых записано практическое значение;
  остальные UNKNOWN идут в раздел «чего не знаем», а не в тревоги.
- Критичность и срок у кандидатов решений — `POLICY_UNDEFINED`: политики приоритетов нет.
- Страница статическая: ни одной сетевой загрузки, ни одного скрипта, ни одной кнопки,
  что-либо запускающей.
- `HEALTHY` и `PRODUCING_OUTPUT` остаются неизвестными; свежесть файла не доказывает, кто
  его записал; отсутствие изменений между двумя снимками не доказывает непрерывной
  доступности между ними.

## Чего в этой фазе НЕТ намеренно

Планировщика, демона, уведомлений, удалённой доставки на телефон, управления агентами,
исполнения предлагаемых действий и сводной оценки здоровья.
