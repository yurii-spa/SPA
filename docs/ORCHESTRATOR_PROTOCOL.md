# Протокол оркестратора (ENV_SETUP_BRIEF_v3 · Этап 3)

> Точный, упорядоченный чеклист, который оркестратор (headless-сессия Claude Code на
> LaunchAgent, либо ручной прогон) исполняет **каждый цикл**. Механические шаги — через
> детерминированный `scripts/orchestrator_queue.py`; шаги-суждения — сам оркестратор.
> Источник правды — файлы в git. LLM здесь допустим (это project-management, НЕ
> risk/execution/monitoring — там LLM по-прежнему запрещён).

## ▶️ НАЧАЛО ЦИКЛА

**Шаг 0 — контекст.** Прочитать `docs/STATE.md`, `docs/decisions/INDEX.md`,
`docs/SYSTEM_BRIEFING.md`. Свериться с открытыми вопросами и активными задачами.

**Шаг 0a — «объявил → доставил?» (ОБЯЗАТЕЛЬНО, до выбора задачи).**
`python3 scripts/check_undelivered_work.py` (read-only, stdlib, без сети) — сверяет объявленную
в `data/session_changes.jsonl` работу с `origin/main` во всех рабочих деревьях репозитория.
**Зачем:** 30.07 работа ЧЕТЫРЁХ сессий подряд (#41–#43) осталась в `/tmp`-worktree, а `STATE.md`
уже отчитывался о доставке — каждый раз это находила следующая сессия вручную, пофайлово.
Коды возврата: **0** — всё измерено и доставлено; **1** — есть находки; **2** — что-то не
измерено (fail-CLOSED). Находка — **сигнал к ручной сверке**, а не команда: рабочее дерево не
подписано, атрибуцию к сессии инструмент не выдумывает, авто-доставки чужой работы нет.
Перед подъёмом чужой работы — как и раньше: `ps -p <pid>`, announce-лог, и НЕ принимать отчёт
умершей сессии на веру (перепроверять прогонами).

**Шаг 0a-bis — «а не лежит ли работа в ветке-черновике?» (ОБЯЗАТЕЛЬНО, вместе с 0a).**
`python3 scripts/checkpoint_deliver.py list` (read-only). **Зачем:** шаг 0a ищет недоставленное по
`/tmp`-worktree живой машины — он бессилен, если рабочего дерева уже нет, и требует ручной
пофайловой археологии. Чекпойнт даёт работе второе место жизни на `origin` (ветка `wip/<сессия>`),
поэтому недоставленное видно ОДНОЙ командой. Вердикты: `undelivered` — содержимое отличается от
`main`, кандидат на подъём (порядок тот же: `ps`, announce-лог, перепроверка прогонами — отчёт
мёртвой сессии на веру не принимать) · `delivered` — всё побайтово совпало с `main`, ветку можно
снять `drop` · `unmeasured` — **измерить не удалось, это НЕ «доставлено»**. Коды возврата:
0 / 1 / 2 (fail-CLOSED).

**Шаг 0b — «эту карточку уже кто-то взял?» (ОБЯЗАТЕЛЬНО, перед взятием карточки).**
`python3 scripts/check_card_claim.py check <карточка> --files <файлы, которые собираюсь править>`
(read-only, stdlib, без сети). **Зачем:** 30.07 две автономные сессии независимо взяли ОДНУ
карточку `agent-ci-ignores-golive-gate-tests` (`pid6621` 14:04Z и `pid17579` 15:16Z), проделали
одну и ту же работу и правили одни и те же `ci.yml`/`test.yml`; доставлена одна, вторая осталась
в `/tmp`-worktree. Шаг 0a на этот вопрос НЕ отвечает — он про доставку, а не про занятость.
Проверка читает `claimed_by`/`claimed_at` карточки и объявления, относящиеся к ней (поле `card:`
· файл карточки в объявленном владении · упоминание идентификатора в тексте), и измеряет
активность объявившей сессии тем же кодом, что шаг 0a.
Вердикты: `free` — брать можно · `claimed` — **НЕ брать, взять следующую** · `stale` — кандидат
на ручной подъём осиротевшей работы (порядок шага 0a, авто-захвата нет) · `unchecked` —
занятость не измерена, брать нельзя. Коды возврата: 0 / 1 / 1 / 2 (fail-CLOSED).
Свой идентификатор сессии передавать флагом `--session <id>` (из своего же объявления) —
иначе собственное объявление читается как чужой захват.

**Активность сессии — измерение, а не догадка (цикл #62, карточка `agent-durable-session-id`).**
Сессия с долгоживущим процессом объявляет его переменной `SPA_SESSION_PID` (обёртка
`scripts/agent_orchestrator.sh` делает это сама: `SPA_SESSION_PID=$$` + `SPA_SESSION_ID=cycle-$$`,
т.е. все записи цикла несут ОДИН идентификатор). Тогда каждая запись журнала несёт `session_pid`
+ время старта, подтверждённые `ps` в момент записи, и шаги 0a/0b используют их как **основной
критерий** активности; возраст объявления остаётся запасным. Совпадение времени старта отличает
живую сессию от переиспользованного ОС pid. Записи без этих полей (и старые) разбираются как
раньше — по pid из идентификатора, а `cycle49`-подобные id без pid остаются «не измерено».

**`ЗАНЯТА` по НЕИЗМЕРИМОМУ признаку — повод для ручной сверки, а не запрет (цикл #63).** Если
захват держится записью, про активность которой инструмент сам говорит «не измерено»
(`идентификатор сессии не содержит pid`), то `claimed` не несёт информации о том, жива ли
сессия, и по построению держится до истечения окна — так осиротевшая работа #62 чуть не осталась
лежать второй цикл подряд. Тогда действовать по порядку шага 0a: **сначала доказать состояние
сессии НЕЗАВИСИМО от инструмента** (таблица процессов: есть ли вообще другой `claude -p` /
обёртка цикла; announce-лог; рабочее дерево), и только при доказанной смерти поднимать работу —
с полной перепроверкой прогонами и записью доказательства в журнал. **Это не право
игнорировать `claimed`:** признак, который инструмент ИЗМЕРИЛ (живой процесс, своя сессия),
остаётся запретом, а «не смог доказать смерть» = не брать (fail-CLOSED, инв. #2).

**Отчёт о занятости — не захват (цикл #67, карточка `agent-fresh-weak-mention-deadlocks-queue`).**
Голое упоминание карточки в тексте объявления (слабый признак) само по себе больше НЕ блокирует —
ни свежее, ни старое; оно уходит в раздел «история». Причина измерена: шаг 0b обязывает называть
карточки поимённо, поэтому честная фраза «карточку X НЕ беру» содержала её идентификатор и
засчитывалась как захват X; циклы идут раз в час, окно свежести — 3 ч ⇒ каждый отчёт перезаряжал
замок раньше, чем истекал предыдущий. 01.08 замок сработал на обеих (и единственных) оставшихся
карточках бэклога, включая ту, чью осиротевшую работу предыдущий цикл СПЕЦИАЛЬНО оставил соседней
сессии. Цена, измеренная по журналу (цикл #70): цикл `cycle66i` из-за этого не взял ни одной
карточки, а циклы #68 и #69 продолжили работу, только **отменив вердикт инструмента вручную** по
правилу #63 — то есть блокирующий ответ шага 0b перестал быть авторитетным и требовал ручной
перепроверки КАЖДЫЙ цикл. Блокируют по-прежнему: любой признак от подтверждённо ЖИВОЙ сессии, все
три СИЛЬНЫХ признака (`card:` · файл карточки во владении · `claimed_by`) и — независимо от
карточки — **пересечение по `--files`**, поэтому флаг `--files` перестал быть необязательным по
смыслу: он и есть защита от сессии, работающей в обход инструмента.

Взяв карточку — пометить её: `python3 scripts/check_card_claim.py claim <карточка>`
(пишет `claimed_by`/`claimed_at`, видно в `_BOARD.md`); в объявлении указывать
`--card <карточка>`, а по завершении — `--card <карточка> --card-state done` (снимает захват;
он и так не действует после `done`/`ingested`).

**Общее состояние сессий живёт в ГЛАВНОМ рабочем дереве (цикл #54, 31.07).** `data/` в
`.gitignore`, поэтому раньше объявление, сделанное из обязательного по §3.4 worktree, уезжало в
`<worktree>/data/session_changes.jsonl` и умирало вместе с деревом (так осиротел цикл #52 —
объявление он СДЕЛАЛ), а шаги 0a/0b, запущенные оттуда же, читали тот же пустой файл и отвечали
«НЕ ИЗМЕРЕНО» о любой карточке. Теперь и запись, и чтение разрешаются в главное дерево
(`check_undelivered_work.shared_log`) — **флаг `--log` из worktree больше не нужен**, а `claim`
сам пишет объявление о захвате (не смог → карточка НЕ берётся). Следствие: захват, сделанный в
`/tmp`-worktree, виден занятым из хост-репо СРАЗУ, без пуша.

**Шаг 1a — ПРОВЕРКА ИСТОРИИ (ОБЯЗАТЕЛЬНО, до создания карточки; owner-directive 2026-07-16, §6.6).**
Перед тем как из задания/идеи создать карточку, оркестратор ОБЯЗАН поискать по ВСЕЙ памяти —
карточки во всех статусах (`nimbalyst-local/tracker/`), `docs/ideas/`, ADR-решения (`docs/decisions/`),
`docs/STATE.md`, `docs/journal/` (+ при нужде `git log`): **не делали ли мы это уже, не делаем ли
сейчас, не отказались ли осознанно.** Механизм — `spa_core.owner_queue.history_check.history_check(text)`
(детерминированный сбор кандидатов из памяти + семантический вердикт через `ask_router`/claude).
Действие по вердикту:
- **DONE** (уже сделано) → карточку-дубль НЕ создавать; Telegram-ответ по-человечески: «Это уже сделано
  тогда-то, вот результат: …» (со ссылкой на коммит/файл/карточку). Закрыть inbox-карточку `done`.
- **IN-PROGRESS** (уже в работе) → дубль НЕ создавать; ответ: «Уже в работе, вот карточка: …».
- **REJECTED** (осознанно решили не делать) → дубль НЕ создавать; ответ: «Мы решили это не делать
  тогда-то (ADR-XXX), причина: … Хочешь пересмотреть решение?». Если владелец отвечает «да, пересмотреть»
  → создать карточку с пометкой «**пересмотр решения ADR-XXX**» + ссылкой на старое решение.
- **PARTIAL / сомнительно** → карточку СОЗДАТЬ, но в теле и в Telegram-ответе написать: «похоже на
  <то-то>, проверь» (со ссылкой на возможное совпадение).
- **NEW** (совпадений нет) → обычная классификация (см. ниже).
**Каждый такой ответ (DONE/IN-PROGRESS/REJECTED/PARTIAL) — записать в `docs/journal/<неделя>.md`**
(что пришло, какой вердикт, на что сослались). Дубли не плодить — источник правды один.

Для каждой `new` inbox-карточки (прошедшей Шаг 1a как NEW или PARTIAL) классифицировать (амендмент §6.3):
- **ЗАДАЧА** (есть конкретное действие) → создать задачу с acceptance-критериями (см. «Правила задач»),
  перевести карточку в `in-progress` (`set-status <path> in-progress`), вписать ссылку на порождённую
  задачу. Telegram-ответ владельцу: «создал задачу: …».
- **ИДЕЯ** (мысль / наблюдение / «а что если») → сохранить в `docs/ideas/<дата-slug>.md` с датой,
  **задачу НЕ создавать** (инвариант «идея ≠ инструкция»). Telegram-ответ: «записал как идею».
- **НЕПОНЯТНО** или **конфликт с инвариантами** (risk-политика, refusal-first, no-solicitation …) →
  создать карточку `own-*` `needs-owner` (`create --type owner-decision …`, формат §2.4) с уточняющим
  вопросом / объяснением конфликта + `notify`, **не исполнять молча**. Telegram-ответ: «есть вопрос — смотри карточку».
- **§6.4 — закрыть исходную карточку со ссылками:** после обработки допиши в тело inbox-карточки ссылки
  на порождённые задачи/идею/`own-*` и переведи её в `done` (`set-status <path> done`) — владелец всегда
  проследит судьбу задания.

## ⚡ Событийный интейк (owner-approved 2026-07-15) — мгновенно, не раз в 3ч

Два триггера, каждый под свой источник (надёжность):
- **Сообщения бота** (текст/голос) → **in-process** в боте (`bot.py::_classify_route` + `ask_router`) —
  мгновенно, атомарно с приёмом. Классифицирует вопрос/задача/непонятно → отвечает / карточка / переспрос.
- **Заметки Obsidian в `inbox/`** → LaunchAgent `com.spa.inbox_watch` (`WatchPaths`) → `agent_inbox_intake.sh`
  → `spa_core/owner_queue/intake.py::run_note_intake`.

**Интейк ЖЁСТКО ограничен (детерминированный Python):** ТОЛЬКО классификация (Claude через `ask_router`),
создание/маршрутизация карточки (задача→`in-progress`+критерий / идея→`docs/ideas/` / непонятно→`own-*`
`needs-owner`), и Telegram-ответ. **НИКАКОГО кода, git/push, деплоя, исполнения, правок тестов** — модуль
их не вызывает. Защита: debounce 60с + atomic-mkdir lock + coord-log + fail-safe (упал → карточка `new`,
подхватит полный цикл). **Исполнение задач продолжает ПОЛНЫЙ цикл** (`com.spa.orchestrator`).
**«срочно» в заметке → интейк сразу `kickstart` полного цикла** (явная команда владельца, разрешённое исключение).

## 🤖 Автономный рабочий мандат (owner-approved 2026-07-15, «управляемая автономия»)

Владелец хочет, чтобы система двигалась сама (не простаивала) — НО под контролем. После разбора
очереди (шаги 0–2), если явных заданий нет, оркестратор берёт **ОДНУ безопасную задачу** сам и
доводит до конца под протоколом. **Это НЕ «no questions, no stops» — это работник под правилами.**

**РАЗРЕШЕНО автономно (scope: очередь + hardening + мелкие фичи):**
- разбор очереди (inbox / owner-done); hardening (тесты, доки, чистка CI, мелкие фиксы);
- **мелкие НЕ-owner-gated** пункты backlog/roadmap (напр. SEO-страницы, changelog, мелкий UI) — по одной.

**ЗАПРЕЩЕНО автономно → только карточкой Needs Owner (не делать молча):**
- RiskPolicy / kill-switch / risk-логика; живой go-live трек (`data/equity_curve_daily.json`);
  деплой/выгрузка агентов; числа/нейминг/legal на сайте; всё «owner-gated» или спорное;
  **ослабление/отключение тестов** (инвариант #16).

**КАЖДЫЙ автономный заход:**
1. Прочитать STATE + очередь + `data/session_changes.jsonl` (кто чем владеет) и прогнать
   шаг 0a (`scripts/check_undelivered_work.py`) — не осиротела ли работа прошлых циклов.
2. Объявить владение файлами (`log_session_change.py --card <карточка>`) — не трогать чужое;
   перед взятием карточки — шаг 0b (`scripts/check_card_claim.py check`), занята → взять следующую.
3. Одна задача → изолированный worktree → **тесты зелёные до пуша** → пуш: **КОД** через
   `push_to_github.py`; **ЛЮБОЙ файл сайта `landing/**` — ТОЛЬКО через `scripts/safe_site_push.py`**.
   **Чекпойнт (рекомендуется, как только работа готова, ДО полной верификации):**
   `python3 scripts/checkpoint_deliver.py push --files <abs...>` — работа уезжает в ветку
   `wip/<сессия>` на `origin` и переживает смерть сессии. **Это НЕ доставка и НЕ замена §3.4:**
   объём проверок не сокращается ни на один тест, в `main` работа уезжает только после зелёного
   полного среза; меняется лишь момент, начиная с которого её нельзя потерять. `landing/**` и живой
   трек чекпойнт ОТКАЗЫВАЕТСЯ принимать (owner-gate обойти нельзя). Доставив в `main` — снять ветку
   `drop` (снимается только при вердикте `delivered`).
4. Отчёт в journal + announce. Спорное → карточка. Ничего «в воздухе».

**🔒 Owner-gate авто-шипа сайта (ADR-OWN-2026-07-autoship, owner-approved full auto-ship).**
Оркестратор пушит БЕЗОПАСНЫЕ правки сайта в live сам, но owner-gated классы (числа доходности,
нейминг тиров, расшифровка «SPA», legal/disclaimer, solicitation, удаление honesty-токенов) НИКОГДА
не уезжают сами — `scripts/check_owner_gate.py` их ловит, `safe_site_push.py` создаёт карточку
`needs-owner` + notify, пуш не происходит. Детерминированный interlock в `push_to_github*.py` (активен
при `SPA_AUTONOMOUS=1`, ставит `agent_orchestrator.sh`) не даёт обойти гейт «забыв» wrapper (fail-closed).
Гейт — кооперативный контроль (см. ADR риск). Полный гайд: `docs/OWNER_GATE.md`.

**Контроль владельца:** arming-flag `SPA_ORCHESTRATOR_ARMED` (вкл/выкл одной командой; заодно снимает
`SPA_AUTONOMOUS` → interlock и авто-шип отключены); кадэнс — несколько раз в день (пересмотр
~2026-07-17 по расходу токенов).

## 📏 Правила задач (§3.4)

Каждая техническая задача:
- **acceptance criteria** прописаны в теле;
- работа в **изолированном git worktree** (не пачкать основную ветку параллельных процессов);
- **тесты до закрытия** (код-изменения без зелёных тестов не закрываются).

## 🚦 Инварианты протокола

1. Агент **никогда** не ставит `owner-done` (только владелец; `set_status` бросает `OwnerDoneForbidden`).
2. Конфликт задания с risk-инвариантами → `needs-owner`, не исполнять молча.
3. Идея ≠ инструкция: `docs/ideas/` и `docs/rules-draft/` не исполняются без промоушена (`#promote` / явная карточка).
4. Новые вопросы владельцу — только карточки `needs-owner` + Telegram-уведомление.
