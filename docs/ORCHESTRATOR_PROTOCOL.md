# Протокол оркестратора (ENV_SETUP_BRIEF_v3 · Этап 3)

> Точный, упорядоченный чеклист, который оркестратор (headless-сессия Claude Code на
> LaunchAgent, либо ручной прогон) исполняет **каждый цикл**. Механические шаги — через
> детерминированный `scripts/orchestrator_queue.py`; шаги-суждения — сам оркестратор.
> Источник правды — файлы в git. LLM здесь допустим (это project-management, НЕ
> risk/execution/monitoring — там LLM по-прежнему запрещён).

## ▶️ НАЧАЛО ЦИКЛА

**Шаг 0-замок — «а цикл уже не идёт?» (ADR-070 п.9, решение владельца 2026-08-07).**
Замок берёт САМА обёртка `scripts/agent_orchestrator.sh` — до вызова сессии, сразу после
гейта взведения. Занят живой сессией ⇒ обёртка вежливо выходит с кодом 0, Claude не
вызывается вовсе. **Перед РУЧНЫМ прогоном** посмотреть, свободно ли:

```bash
python3 scripts/orchestrator_cycle_lock.py status      # 0 — свободно · 3 — «подожди ~N мин»
```

**Зачем:** карточки от одновременной работы защищены с 30.07 (шаг 0b), сам ЦИКЛ — нет.
Захват карточки ловит столкновение уже ПОСЛЕ шагов 0/0a/0b — то есть после самой дорогой
части прогона, — и не ловит вовсе, когда вторая сессия берёт СЛЕДУЮЩУЮ карточку и два
автономных пушера идут в один `origin/main` наперегонки.
Замок ОБЩИЙ (лежит в главном рабочем дереве рядом с журналом объявлений — циклы по §3.4
работают из `/tmp`-worktree, и локальный замок не увидел бы никто), atomic-mkdir, живость
держателя измеряется тем же кодом, что шаги 0a/0b (`session_pid` + `session_pid_start`).
Мёртвый держатель ⇒ замок снимается; «живость не измерена» блокирует не дольше окна 3ч
(`--unmeasured-ttl-hours`) — необратимое «не измерено» было бы вечным замком, а не порогом.
Поломка самого замка (нет каталога, не разрешилось общее дерево) ⇒ вердикт `unprotected`,
код 0: цикл идёт и **говорит об этом вслух** — сторож, убивающий то, что охраняет, вреднее
отсутствия сторожа.

**Шаг 0 — контекст.** Прочитать `docs/STATE.md`, `docs/decisions/INDEX.md`,

**Шаг 0-офис — инвест-офис и сторожа (ОБЯЗАТЕЛЬНО, ADR-066 Фазы 2–3).**
`python3 scripts/consume_office_reports.py` — выводит в контекст house_view офиса
(постура/конфликты/возможности), здоровье аналитиков, находки сторожа
`architecture_conformance`, **расхождения офис↔книга (`data/house_view_gap.json`,
Контур C1)** и **отчёт моста находка→карточка (`data/findings_bridge_report.json`, C2 —
включая `deferred` и статус доставки карточек на origin)**,
и пишет квитанции потребления (по ним сторож проверяет, что офис ЧИТАЮТ, — B3).
**Прочитанное обязывает:** RED-постура, расхождение офиса с фактической аллокацией,
CRITICAL-находка сторожа → карточка (needs-owner при capital-релевантности, иначе
agent-backlog). С Фазы 3 карточки по находкам сторожей заводит **мост автоматически**
(dedup · гистерезис · ≤5/сутки · авто-закрытие исчезнувшей находки); руками сессия
заводит только то, что мост не покрывает, и **никогда не дублирует** уже заведённую
им карточку (у неё в frontmatter есть `finding_key`). Строки «❌ НЕ ПРОЧИТАН» и
«[ИСТОЧНИК НЕ ПРОЧИТАН]» — тоже находка, не пропускать: молчащий сторож не закрывает
карточки, но и не отчитывается за тишину.

**Гонять из ПРОД-дерева** (`~/Documents/SPA_Claude`), а не из worktree — либо
`--data-dir <прод>/data`. Артефакты офиса пишет живой флот в прод-дерево и они в
`.gitignore`, поэтому в worktree их нет ПО ПОСТРОЕНИЮ. **Это НЕ противоречит правилу
«очередь и `docs/` читать из worktree на `origin/main`» (урок #193) — вопросы разные:**
карточки и документы живут в git, и на хосте они стухшие; артефакты офиса в git не
живут вовсе, и на origin их нет никогда. Одно дерево свежее по коду и документам,
другое — по рантайму, и перепутать их легко.
С цикла #236 шаг сам отличает «в этом дереве нет НИ ОДНОГО артефакта офиса» (ОДНА
строка «⚠️ ОФИС НЕ ИЗМЕРЕН», код возврата **3**) от «артефакт пропал у живого
производителя» (по-прежнему «❌ НЕ ПРОЧИТАН» по строке на артефакт, код 0).
До этого запуск из worktree давал **двадцать** ложных «НЕ ПРОЧИТАН» под подписью
«действовать (карточки)» — и по протоколу выше это читалось как двадцать находок о
мёртвом инвест-офисе, который жив (замер #207).
**Зачем:** аудит 2026-08-05 — 12 аналитиков месяцами писали отчёты, у которых не
было НИ ОДНОГО обязательного читателя; оркестратор house_view не читал вовсе.

**Шаг 0a — «объявил → доставил?» (ОБЯЗАТЕЛЬНО, до выбора задачи).**
`python3 scripts/check_undelivered_work.py` (read-only, stdlib, без сети) — сверяет объявленную
в `data/session_changes.jsonl` работу с `origin/main` во всех рабочих деревьях репозитория.
**Зачем:** 30.07 работа ЧЕТЫРЁХ сессий подряд (#41–#43) осталась в `/tmp`-worktree, а `STATE.md`
уже отчитывался о доставке — каждый раз это находила следующая сессия вручную, пофайлово.
Коды возврата: **0** — всё измерено и доставлено; **1** — есть находки; **2** — что-то не
измерено (fail-CLOSED). Находка — **сигнал к ручной сверке**, а не команда: рабочее дерево не
подписано, атрибуцию к сессии инструмент не выдумывает, авто-доставки чужой работы нет.
Перед подъёмом чужой работы — как и раньше: `ps -p <pid>`, announce-лог, и НЕ принимать отчёт
умершей сессии на веру (перепроверять прогонами).

**Тот же шаг отвечает и на второй вопрос — «созданная карточка доехала?»** (цикл #140).
`orchestrator_queue.py create` пишет карточку в трекер ТОГО дерева, чья копия скрипта
запущена (`cwd` не влияет), а список файлов на пуш собирается по рабочему дереву цикла ⇒
карточка, созданная посреди цикла хост-копией, не попадает в него НИКОГДА и не объявляется
(значит, разбором объявлений не ловится по построению). Раздел **«🗂 КАРТОЧКИ НЕ ДОСТАВЛЕНЫ»**
перечисляет карточки в НЕтерминальном статусе, лежащие в любом рабочем дереве и
отсутствующие на `origin/main`. Находка — доставить карточку (текст автора дословно), а не
переписывать. **Создавая карточку из worktree, указывай своё дерево:**
`orchestrator_queue.py create … --tracker-dir <своё дерево>/nimbalyst-local/tracker`
(иначе `create` громко предупредит в stderr, что карточка легла в чужое дерево).

**Шаг 0b — «эту карточку уже кто-то взял?» (ОБЯЗАТЕЛЬНО, перед взятием карточки).**
`python3 scripts/check_card_claim.py check <карточка> --files <файлы, которые собираюсь править>`
(read-only, stdlib, без сети). **Зачем:** 30.07 две автономные сессии независимо взяли ОДНУ
карточку `agent-ci-ignores-golive-gate-tests` (`pid6621` 14:04Z и `pid17579` 15:16Z), проделали
одну и ту же работу и правили одни и те же `ci.yml`/`test.yml`; доставлена одна, вторая осталась
в `/tmp`-worktree. Шаг 0a на этот вопрос НЕ отвечает — он про доставку, а не про занятость.
Проверка читает `claimed_by`/`claimed_at` карточки и объявления, относящиеся к ней (поле `card:`
· файл карточки в объявленном владении · упоминание идентификатора в тексте), и измеряет
активность объявившей сессии тем же кодом, что шаг 0a.
Вердикты: `free` — брать можно · `claimed` — **НЕ брать, взять следующую** · `stale` — кандидат
на ручной подъём осиротевшей работы (порядок шага 0a, авто-захвата нет) · `unchecked` —
занятость не измерена, брать нельзя. Коды возврата: 0 / 1 / 1 / 2 (fail-CLOSED).
Карточку, которой нет в рабочем дереве, проверка читает с `origin/main` и говорит об этом
строкой «карточка прочитана с …» (цикл #140: десять карточек жили только на origin, и о
каждой шаг 0b отвечал «НЕ ИЗМЕРЕНО» — то есть взять их было нельзя никогда). Видно при этом
ОПУБЛИКОВАННОЕ состояние захвата; журнал объявлений проверяется полностью, как и прежде.
Взять такую карточку = сперва забрать её в своё дерево (команду печатает сам отказ `claim`).
Свой идентификатор сессии передавать флагом `--session pid<N>` (из своего же объявления) —
иначе собственное объявление читается как чужой захват: журнал пишет pid ОДНОКРАТНОЙ
CLI-команды (карточка `agent-durable-session-id`).

Взяв карточку — пометить её: `python3 scripts/check_card_claim.py claim <карточка>`
(пишет `claimed_by`/`claimed_at`, видно в `_BOARD.md`); в объявлении указывать
`--card <карточка>`, а по завершении — `--card <карточка> --card-state done` (снимает захват;
он и так не действует после `done`/`ingested`).

**Шаг 1-пред — «а тот ли это список?» (ОБЯЗАТЕЛЬНО, до разбора очереди).**
`python3 scripts/check_tracker_drift.py --tracker-dir <ХОСТ-дерево>/nimbalyst-local/tracker`
(read-only, stdlib, без сети). **Зачем:** `list` читает трекер ТОГО дерева, чья копия скрипта
запущена, а циклы пушат прямо на origin — хост-дерево не обновляется никогда, и эти два набора
карточек не сверял никто. Замер 07.08 на живом входе: **260 карточек в хост-дереве против 281 на
`origin/main`**; очередь выдала 5 карточек `inbox/new`, из которых на origin закрыты 4, и НЕ
показала 21 карточку, включая **три вопроса владельца в `needs-owner`**, а в очереди владельца
три УЖЕ отвеченных вопроса числились ждущими ответа. Список был неверен в обе стороны сразу.
Коды возврата: **0** — расхождений нет · **1** — есть находки · **2** — не измерено (fail-CLOSED).

Сам `list` теперь сверяется с `origin/main` сам и говорит в stderr: доказанно устаревшая карточка
(её содержимое найдено в истории origin для того же пути — при необходимости с точностью до полей
захвата) читается **с origin**, поэтому закрытая на origin больше не выдаётся как `new`. Всё
остальное НЕ переписывается: карточка со своей правкой (`diverged`) и карточка, которой в дереве
нет (`hidden`), только **называются поимённо**. Отключить сверку — `--no-origin-check`
(список станет неподтверждённым). **Массовый `git checkout origin/main -- <трекер>` ЗАПРЕЩЁН:**
он стирает карточки, живущие только в рабочем дереве.

**Остаточная граница, названная честно:** карточку, которой нет в дереве (`hidden`), выдать
невозможно — файла нет, а путь-фантом сломал бы `set-status`. Увидеть её содержимое = работать
из worktree от `origin/main` (что протокол §3.4 и так требует).

**Шаг 0в — «этот переход кто-нибудь объяснил?» (ОБЯЗАТЕЛЬНО, вместе с шагом 0a).**
`python3 -m spa_core.monitoring.tracker_status_sentinel --root ~/Documents/SPA_Claude`
(read-only над трекером, stdlib, без сети; пишет только свой снимок и отчёт).
**Зачем:** 09.08 00:25 UTC три карточки owner-gate сайта сменили `status:` САМИ —
живой вопрос владельцу закрылся без ответа владельца и исчез из очереди `needs-owner`,
а уже разобранный ответ зеркально вернулся как неотвеченный. Тела карточек целы,
переписаны ровно строки `status:`; ни один сторож не сказал ни слова, нашли глазами.
Сторож сверяет снимок статусов с предыдущим и требует, чтобы каждый переход был покрыт
записью журнала `data/tracker_status_audit.jsonl` (его ведут `queue.set_status` и
`owner_answer.record_owner_answer`). Переход без записи — **неатрибутированный**:
уход из `needs-owner` и приход в `owner-done` = CRITICAL (так теряется вопрос владельца
и обходится инвариант #14), остальные — WARN. Коды: **0** — норма · **1** — WARN ·
**2** — CRITICAL либо не измерено (нет предыдущего снимка ⇒ fail-CLOSED, не «чисто»).
Находка — **карточка**, а не строчка в отчёте: неатрибутированный уход из `needs-owner`
означает, что вопрос владельца могли закрыть без него.
**Дереву прода — свой прогон:** бот и немой писатель живут в хост-дереве, поэтому
`--root` указывает на него, а не на worktree сессии.

**Шаг 0г — уборка мёртвых рабочих деревьев (по правилу, не жестом).**
`python3 scripts/reap_stale_worktrees.py --root ~/Documents/SPA_Claude` (сухой прогон) →
`--apply` (архив + квитанция + снятие). **Зачем:** 14.08 в `git worktree list` числились
**70** регистраций, старейшая от цикла #189, и шаг 0a цикл за циклом выдавал из них одни и те
же 6–7 строк «НЕ ДОСТАВЛЕНО». Работа при этом была доставлена: `docs/STATE.md` из дерева #227
«нет в истории origin» ровно потому, что цикл #228 переписал файл ПОСЛЕ него. Сторож прав по
своему контракту и отвечает не на тот вопрос, который читают, — а постоянные ложные строки и
есть механизм, которым сторожа глохнут.

**Дерево снимается только если ВСЁ верно** (иначе остаётся, с названной причиной): оно
линкованное, а не главное · сессия молчит (ни свежих объявлений внутри него, ни файлов,
изменённых за окно, по умолчанию 24 ч) · git в нём отвечает · **каждый** расходящийся с
`origin/main` путь объяснён — либо его точный blob уже есть в истории origin (`delivered`;
пуш идёт прямо в origin через API, поэтому «незакоммичено» ≠ «не доставлено»), либо origin
двигался по этому пути после HEAD дерева (`superseded` — промежуточное состояние перекрытой
работы). Хоть один путь `unique`/`absent` ⇒ **дерево остаётся**: там может лежать
недоставленная работа, и её называют поимённо (так нашлись `scripts/edge_criterion_consensus.py`
в `spa_wt_rnd49` и две карточки в `spa_wt_c196`).

**Сторож доставки при этом НЕ ослабляется.** Перед снятием пишутся архив
(`~/SPA_backups/worktree_reap/`, правка + копии файлов + манифест) и **квитанция**
`data/worktree_reap_log.jsonl`; шаг 0a её читает. Без квитанции уборка меняла бы шило на
мыло: объявленный путь внутри исчезнувшего дерева даёт «доставку измерить нечем» (код 2)
навсегда — необратимое «не измерено» вместо разбираемой находки. Пропуск получает ровно путь,
названный в квитанции `delivered`/`superseded`; нет квитанции · нет пути в ней · вердикт
другой ⇒ прежнее «не измерено» либо находка. Замер 14.08 на всём журнале (824 записи):
«не измерено» 1031 → 873, и одна строка из осадка стала НАХОДКОЙ (объявленного
`spa_core/tests/test_briefing_track_integrity.py` на origin нет — файл доставлен в `tests/`).

**Шаг 1a — ПРОВЕРКА ИСТОРИИ (ОБЯЗАТЕЛЬНО, до создания карточки; owner-directive 2026-07-16, §6.6).**

`docs/STATE.md`, `docs/journal/` (+ при нужде `git log`): **не делали ли мы это уже, не делаем ли
сейчас, не отказались ли осознанно.** Механизм — `spa_core.owner_queue.history_check.history_check(text)`
(детерминированный сбор кандидатов из памяти + семантический вердикт через `ask_router`/claude).
Действие по вердикту:
- **DONE** (уже сделано) → карточку-дубль НЕ создавать; Telegram-ответ по-человечески: «Это уже сделано
  тогда-то, вот результат: …» (со ссылкой на коммит/файл/карточку). Закрыть inbox-карточку `done`.
- **IN-PROGRESS** (уже в работе) → дубль НЕ создавать; ответ: «Уже в работе, вот карточка: …».
- **REJECTED** (осознанно решили не делать) → дубль НЕ создавать; ответ: «Мы решили это не делать
  тогда-то (ADR-XXX), причина: … Хочешь пересмотреть решение?». Если владелец отвечает «да, пересмотреть»
  → создать карточку с пометкой «**пересмотр решения ADR-XXX**» + ссылкой на старое решение.
- **PARTIAL / сомнительно** → карточку СОЗДАТЬ, но в теле и в Telegram-ответе написать: «похоже на
  <то-то>, проверь» (со ссылкой на возможное совпадение).
- **NEW** (совпадений нет) → обычная классификация (см. ниже).
**Каждый такой ответ (DONE/IN-PROGRESS/REJECTED/PARTIAL) — записать в `docs/journal/<неделя>.md`**
(что пришло, какой вердикт, на что сослались). Дубли не плодить — источник правды один.

Для каждой `new` inbox-карточки (прошедшей Шаг 1a как NEW или PARTIAL) классифицировать (амендмент §6.3):
- **ЗАДАЧА** (есть конкретное действие) → создать задачу с acceptance-критериями (см. «Правила задач»),
  перевести карточку в `in-progress` (`set-status <path> in-progress`), вписать ссылку на порождённую
  задачу. Telegram-ответ владельцу: «создал задачу: …».
- **ИДЕЯ** (мысль / наблюдение / «а что если») → сохранить в `docs/ideas/<дата-slug>.md` с датой,
  **задачу НЕ создавать** (инвариант «идея ≠ инструкция»). Telegram-ответ: «записал как идею».
- **НЕПОНЯТНО** или **конфликт с инвариантами** (risk-политика, refusal-first, no-solicitation …) →
  создать карточку `own-*` `needs-owner` (`create --type owner-decision …`, формат §2.4) с уточняющим
  вопросом / объяснением конфликта + `notify`, **не исполнять молча**. Telegram-ответ: «есть вопрос — смотри карточку».
- **§6.4 — закрыть исходную карточку со ссылками:** после обработки допиши в тело inbox-карточки ссылки
  на порождённые задачи/идею/`own-*` и переведи её в `done` (`set-status <path> done`) — владелец всегда
  проследит судьбу задания.

**Шаг 2 — инжест решений владельца.**
`python3 scripts/orchestrator_queue.py list --type owner-decision --status owner-done --json`

**Ответ владельца виден теперь из ЛЮБОГО дерева (цикл #244).** Раньше здесь стояло «гонять из
прод-дерева» — заплатка на дисциплину: ответ владельца пишет БОТ, а он живёт в прод-дереве, и на
`origin/main` этот ответ не уезжает **ничем** (мост доставки карточек везёт только то, что создал
или закрыл сам за прогон — `IDLE`, ADR-081, — а ответа владельца он не создавал). **Замер 14.08
(цикл #231):** владелец ответил в 12:26Z (`owner-done`, вариант 1); из worktree на `origin/main` —
то есть оттуда, где §3.4 велит работать — эта команда вернула **пустой список**, и два цикла
подряд (#230, дважды) прошли мимо живого решения.

Теперь эта же команда сама опрашивает ГЛАВНОЕ рабочее дерево и выдаёт найденное **отдельной
записью** с полями `cross_tree_check: owner_answer_only_in_main_tree`, `source_tree`,
`source_path`, `local_status` и `age_hours` («сколько ответ лежит без разбора»), плюс отдельная
громкая строка в stderr. Обе копии карточки видны как две записи — их и правда две, и врать про
их число значило бы чинить видимость враньём.

* **Разбирать — СВОЮ копию** (`local_path`), а не ту, что в главном дереве: только своя уедет на
  origin. След ответа перенесёт сам `set-status … ingested` (`carry_owner_answer`).
* **`cross_tree_check: unmeasured`** — опросить главное дерево не удалось; **пустой список тогда
  НЕ означает «решений нет»**, и команда возвращает код **2** (при пустом списке полей в JSON нет
  по построению, и код возврата — единственный оставшийся канал).
* Инвариант #14 цел: сторож только ЧИТАЕТ чужую копию. `owner-done` по-прежнему ставит только
  владелец.

Из прод-дерева поведение не меняется (второго дерева спрашивать не о чем) — это закреплено
обратным контролем, чтобы починка не начала звонить на верном действии.

**Сначала посмотреть поле `origin_check` у КАЖДОЙ выданной карточки** (#178). Значение
`answer_may_be_already_ingested` означает: в дереве `owner-done`, а на `origin/main` та же
карточка уже в терминальном статусе — решение почти наверняка разобрано и доставлено, и
повторный инжест наплодит дубли (ADR, задачи, ответы владельцу). Проверить, прежде чем
разбирать. Значение `unmeasured` — сверка с origin НЕ состоялась, список не подтверждён.
**Зачем:** 09.08 эта команда на прод-дереве вернула две карточки `owner-done`, обе на origin
давно `ingested`; сторож знал об этом, но говорил только в stderr, а шаг читает JSON. Причина
не устранена (бот пишет ответ в хост-дерево, инжест пушит на origin, копии не сходятся) —
поэтому поле смотреть обязательно.

Для каждой `owner-done` карточки:

2. Исполнить / декомпозировать решение (по «Правилам задач»). Если конфликтует с инвариантом —

3. Если это архитектурное решение — выписать/дополнить ADR (`docs/decisions/`, шаблон `_TEMPLATE.md`),

   СОЮЗУ `origin/main`, дерева и РЕЗЕРВОВ, и тут же забирает номер, создавая на origin
   `refs/adr-reserved/<NNN>` (атомарно: вторая ветка получает отказ и берёт следующий). Не смог
   зарезервировать ни git-транспортом, ни GitHub API ⇒ номер НЕ выдаётся (код 2). Посмотреть, не

   видно `reservations`, снимать `release <NNN>`.
   Взгляд на каталог в начале работы — это и есть механизм столкновения: 2026-08-08 две пары
   параллельных сессий заняли `ADR-073` и `ADR-076` за один день, потому что между выбором номера

## 🤖 Автономный рабочий мандат (owner-approved 2026-07-15, «управляемая автономия»)

Владелец хочет, чтобы система двигалась сама (не простаивала) — НО под контролем. После разбора
очереди (шаги 0–2), если явных заданий нет, оркестратор берёт **ОДНУ безопасную задачу** сам и
доводит до конца под протоколом. **Это НЕ «no questions, no stops» — это работник под правилами.**

**РАЗРЕШЕНО автономно (scope: очередь + hardening + мелкие фичи):**
- разбор очереди (inbox / owner-done); **карточки авто-бэклога моста C2** (`source:
  findings-bridge`, поле `finding_key`) — при отсутствии явных заданий их берут в первую
  очередь: это находки живых сторожей, а не догадки;
- hardening (тесты, доки, чистка CI, мелкие фиксы);
- **мелкие НЕ-owner-gated** пункты backlog/roadmap (напр. SEO-страницы, changelog, мелкий UI) — по одной.

**ЗАПРЕЩЕНО автономно → только карточкой Needs Owner (не делать молча):**
- RiskPolicy / kill-switch / risk-логика; живой go-live трек (`data/equity_curve_daily.json`);
  деплой/выгрузка агентов; числа/нейминг/legal на сайте; всё «owner-gated» или спорное;
  **ослабление/отключение тестов** (инвариант #16).

**КАЖДЫЙ автономный заход:**
1. Прочитать STATE + очередь + `data/session_changes.jsonl` (кто чем владеет) и прогнать
   шаг 0a (`scripts/check_undelivered_work.py`) — не осиротела ли работа прошлых циклов.
2. Объявить владение файлами (`log_session_change.py --card <карточка>`) — не трогать чужое;
   перед взятием карточки — шаг 0b (`scripts/check_card_claim.py check`), занята → взять следующую.
3. Одна задача → изолированный worktree → **тесты зелёные до пуша** → пуш: **КОД** через
   `push_to_github.py`; **ЛЮБОЙ файл сайта `landing/**` — ТОЛЬКО через `scripts/safe_site_push.py`**.
4. Отчёт в journal + announce. Спорное → карточка. Ничего «в воздухе».

## 📏 Правила задач (§3.4)

Каждая техническая задача:
- **acceptance criteria** прописаны в теле;
- работа в **изолированном git worktree** (не пачкать основную ветку параллельных процессов);
- **тесты до закрытия** (код-изменения без зелёных тестов не закрываются) — прогон в том
  объёме, который **гейтит CI**, а не в удобном: команда из `CLAUDE.md` («Все тесты»).
  **Зачем:** цикл #189 измерил — workflow `SPA Tests` был красным на 8 коммитах подряд, и
  каждая сессия честно отчитывалась «зелено», прогнав только `spa_core/tests/`; каталог
  `tests/` в предписанный прогон не входил. Тот же класс, что fail-OPEN мониторы: сторож
  отвечает на свой вопрос, а не на нужный. Расхождение предписанной команды с CI теперь
  краснит `spa_core/tests/test_prescribed_run_matches_ci.py`.
- **Приёмка — ДВА прогона (свой + контрольный на чистом `origin/main` того же sha), и порядок
  их запуска решается ЗАМЕРОМ на этой машине, а не правилом.** Перед тем как гонять их рядом
  либо ставить в очередь — один раз замерить:

      python3 scripts/measure_acceptance_contention.py \
          --tree <своё дерево> --tree <контрольное дерево> \
          --log-dir /tmp/acceptance_contention -- tests/

  Вердикт `starves` (код 1) ⇒ гонять **по очереди**; `scales` / `shares` (код 0) ⇒ гонять
  **рядом**; `unmeasured` (код 2) ⇒ порядок не измерен, значит по очереди (fail-CLOSED).
  **Зачем именно замер, а не строка «всегда по очереди».** Карточка
  `inbox-dva-predpisannyh-progona-ryadom-drug-druga-morya` измерила на рабочем Mac 14.08,
  что два прогона рядом почти останавливаются: **~2 байта лога за 15 минут** против
  **18 332 байт за 60 с** у одиночного. Тот же набор в Linux-контейнере 17.08 дал
  **противоположное**: одна копия `tests/` (13 067 тестов) — 472.5 с, две копии рядом в
  разных деревьях — 477.7 с обе, с побайтово одинаковым итогом и без единого фантомного
  падения; очередь стоила бы 945.0 с. Правило, выведенное из первого замера, отняло бы у
  второй машины **ровно половину** пропускной способности приёмки — а медленная приёмка и
  есть механизм, которым мы теряем работу (#210 / #212 / #220 / #224 умерли между «сделал»
  и «доставил»). Ответ зависит от машины, поэтому в протоколе стоит команда, а не константа.
- **точка сохранения ДО верификации — коммит в своём worktree** (цикл #258, карточка
  `agent-orphaned-work-recurred-after-its-card-was-closed`). Закончил правки — **коммить в
  worktree, не пушить**, и только потом иди в полный прогон тестов:

      git -C /tmp/spa_cNNN add -A && git -C /tmp/spa_cNNN commit -m "wip(cNNN): <карточка> — до верификации"

  **Зачем.** Циклы #97 и #98 умерли на верификации не доставив, причём #98 умер ровно на
  подъёме работы #97: замер шага 0a — `origin/main` за весь прогон #98 не сдвинулся,
  `ps -p 52912` и `ps -p 35027` пусты, в обоих `/tmp`-деревьях лежат одни и те же 6 изменённых
  файлов + 1 новый и **ни одного коммита**. Адопция начинала с нуля в своём дереве, поэтому
  смерть возвращала систему в исходное состояние — прогресс не накапливался, сколько бы циклов
  ни пробовало, а `main` оставался красным при готовом лежащем фиксе три цикла подряд.
  Коммит стоит секунду и превращает «6 изменённых файлов без коммита» в готовый коммит, который
  следующий цикл переносит одной командой вместо ручной пофайловой сверки; он же делает точку
  сохранения ИЗМЕРИМОЙ — `git -C <дерево> log --oneline <база>..HEAD` отвечает, есть она или нет.
  Доставку это не подменяет: доставка — по-прежнему пуш на `origin/main`, и шаг 0a судит по нему.
- **убрать за собой — только ИЗМЕРЕННЫМ снятием** (цикл #257), и только ПОСЛЕ пуша:

      python3 scripts/reap_stale_worktrees.py --worktree /tmp/spa_cNNN            # сухой прогон
      python3 scripts/reap_stale_worktrees.py --worktree /tmp/spa_cNNN --apply    # снять

  Инструмент меряет каждый расходящийся путь дерева, архивирует правку и оставляет квитанцию,
  по которой шаг 0a потом отвечает «работа объяснена при снятии». **`git worktree remove`
  руками — запрещён:** снятое так дерево не оставляет измерения, и шаг 0a про каждый
  объявленный путь навсегда пишет «доставку измерить нечем» с кодом 2. **Зачем:** замер
  16.08 — цикл #256 доставил работу на origin и по-хорошему убрал за собой руками; следующий
  заход получил **12 строк «НЕ ИЗМЕРЕНО»**, которые не разойдутся уже никогда (байтов нет ни
  в дереве, ни в архиве). Это класс «необратимое „не измерено“ морит очередь»: разбирать
  такие строки бессмысленно, а рядом с ними однажды проедет настоящая находка.
  Отказ инструмента («здесь может лежать НЕДОСТАВЛЕННАЯ работа») — не помеха, а находка:
  сперва доставить, потом снимать. Звать из ГЛАВНОГО дерева: из снимаемого он откажется
  (снятие вынуло бы каталог из-под собственного `cwd`). Не убрал за собой — дерево заберёт
  подметающий прогон через сутки, тоже с квитанцией.

## 🚦 Инварианты протокола

1. Агент **никогда** не ставит `owner-done` (только владелец; `set_status` бросает `OwnerDoneForbidden`).
2. Конфликт задания с risk-инвариантами → `needs-owner`, не исполнять молча.
3. Идея ≠ инструкция: `docs/ideas/` и `docs/rules-draft/` не исполняются без промоушена (`#promote` / явная карточка).
4. Новые вопросы владельцу — только карточки `needs-owner` + Telegram-уведомление.
5. **Карточка закрывается (`done`) только по работе, которая УЖЕ на `origin/main`.** Это не
   пожелание: `set-status … done` сверяет карточку с её версией на локальной копии
   `origin/main` (`spa_core/owner_queue/delivery_gate.py`, без сети) и при расхождении
   ОТКАЗЫВАЕТ (rc 2, статус не меняется). Порядок цикла: доставить → `git fetch origin main`
   → закрыть карточку. Осознанный обход существует и громкий — `--allow-undelivered
   "<причина>"`; молчаливого нет.
   **Почему:** класс «осиротевшая работа» (#97→#98, #244, #252→#254, `rnd60`) вредит не
   потерянными файлами, а закрытой карточкой: следующая сессия видит `done` и задачу не
   берёт. Замер по `data/tracker_status_audit.jsonl` за 13–18.08.2026 — **10 из 10**
   закрытий в дереве не видны на `origin/main`.
