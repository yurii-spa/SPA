# Studio OS v0.4 · Тик расписания

> **Статус:** LOCAL ONLY · ТЕНЬ · замер **2026-09-24**

## Второго планировщика нет

Ни демона, ни расписания, ни очереди. Есть одна чистая функция `mission_kernel.tick`,
которую зовут ОБА существующих входа — событийный триггер и часовой backstop. Поэтому
«событие пришло» и «часовой подобрал пропущенное» дают одно и то же решение.

Закреплено пробой: два входа из одного снимка дают ОДНО намерение, второй получает
`ALREADY_PREPARED`.

## Защита от устаревшего решения (§9)

```
читаем ревизию N (без замка)
  → считаем готовность (чистый расчёт, вне замка)
    → под замком: ревизия всё ещё N?
      да  → фиксируем намерения
      нет → DISCARDED_STALE_SNAPSHOT, не пишем НИЧЕГО
```

Решение, записанное поверх изменившегося состояния, было бы принято по состоянию,
которого больше нет. Половина такого решения хуже отсутствия решения, поэтому отбрасывается
целиком. Отбрасывание не запирает расписание: следующий тик проходит.

## Граница побочного действия (§10)

Работника нельзя запускать, держа замок реестра: запуск длится минуты, замок обязан жить
миллисекунды. Поэтому:

```
ACTION_INTENT_PREPARED  (под замком, замок отпущен)
  → ACTION_STARTED      (владелец объявлен: pid + время рождения + отпечаток команды)
    → ACTION_RESULT     (исход записан)
       либо ACTION_ABANDONED (владелец мёртв, исхода НЕТ)
```

Тик не запускает процессов вовсе — это утверждение о коде, проверенное разбором
(`subprocess`, `Popen`, `fork`, `spawn` в ядре отсутствуют).

### Восстановление после падения

| состояние | что делать | почему |
|---|---|---|
`PREPARED` | `REPLAY_SAFE` | действие не начиналось |
`STARTED`, владелец жив и НАШ | `RECOVER_EXISTING` | искать существующую работу |
`STARTED`, владельца нет | `REPLAY_SAFE` | исхода нет, попытка свободна |
`STARTED`, номер занят другим | `REPLAY_SAFE` | время рождения не совпало |
`STARTED`, живость не измерена | `REPLAY_NOT_MEASURED` | начать заново поверх живого = две попытки |
`RESULT` | `ALREADY_DONE` | повторять ЗАПРЕЩЕНО |

Живость и личность — ДВА прибора с разными именами параметров (`stat_runner` и
`birth_runner`): один параметр на два контракта есть известный способ проверить не то.

## Идемпотентность запуска (§11)

Личность запуска = `hash(mission_id, work_item_id, plan_revision_id,
input_candidate_context_id, attempt)`. Отсюда:

* тот же запуск дважды — это ОДИН запуск;
* та же работа по НОВОЙ ревизии — другой запуск (прежнее решение устарело);
* реализация на других байтах — другая работа;
* после записанного исхода следующая попытка получает свою личность.

Своей аренды, очереди и допуска по ресурсу ядро не заводит: берутся существующие.
