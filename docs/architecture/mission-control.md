# Studio OS v0.3 · Центр миссий

> **Статус:** LOCAL ONLY · ТЕНЬ · замер **2026-09-24** · производство НЕ активировано
> Каждое утверждение ниже подкреплено замером существующей системы либо пробой.

## Зачем миссия появилась как сущность

Аудит 24.09 отвечал на десять вопросов ARB по существующим реестрам. Девять из десяти
дали «уже есть, переиспользовать». Один дал «нет»:

| вопрос | ответ замера |
|---|---|
| есть ли канонический объект ЗАДАНИЯ | ДА — `Ledger.items`, 7 состояний, замок, атомарность |
| есть ли родитель/потомок | ДА для КАНДИДАТОВ (`candidate_context.derive`), НЕТ для работ |
| есть ли зависимости | ДА как ДАННЫЕ (`KANBAN.depends_on`, 8 рёбер) — **читателей ноль** |
| есть ли приоритет | ДА, машинный (`durable_job.PRIORITY_ORDER`) |
| есть ли роль/владелец | ДА, но у заданий вырожденно (`owner` печатается константой) |
| **есть ли группировка в программу** | **НЕТ** |
| есть ли политика повтора | ДА, частично и в трёх местах |
| **есть ли состояние интеграции** | **НЕТ** — поиск дал 0 совпадений |
| есть ли критерий приёмки | ДА — `done_when` в пакете + `card_acceptance.PROBES` |
| есть ли канонический исход | ДА — `TERMINAL`, `arb_recommendation` |

Поэтому НОВОГО заведено ровно четыре понятия: **Миссия**, **рёбра зависимости с
валидатором**, **Пачка изменений как долговечная запись**, **Ворота интеграции**.

## Где что живёт: один хозяин на одно понятие

| понятие | единственный хозяин | где |
|---|---|---|
| Миссия | `mission_registry` | ключ `missions` документа реестра |
| СТРУКТУРА работы (граф, зоны, критерии) | `mission_registry` | ключ `work_graph` |
| **СОСТОЯНИЕ работы** | `zero_touch_trigger.Ledger` | ключ `items` — **и больше нигде** |
| допуск по ресурсу | `resource_lease` | каталоги аренд |
| долгая работа (CI) | `durable_job` | `jobs/<id>.json` |
| личность и родословная кандидата | `candidate_context` | улики кандидата |
| изменение как работа | `change_bundle` | ключ `change_bundles` |
| сборка работ в кандидата | `integration_gate` | ключ `integrations` |
| кандидат выпуска и готовность | `release_train` | ключ `release_candidates` |
| право канонической доставки | `delivery_authority` | подпись владельца |
| проекции для экрана | `mission_projection` | ничего не хранит |

**Четвёртого хранилища правды не появилось.** Миссия, граф, пачки, интеграции и выпуски
лежат в ОДНОМ документе реестра и правятся ЕГО замком. Причина не в экономии файлов:
замок реестра уже пережил настоящую гонку четырёх процессов (замер 22.09 — проигравший
записывал `NEW` поверх `CLAIMED` победителя), и второе хранилище означало бы второе
правило о том, кто пишет последним. Закреплено пробой
`test_mission_and_ledger_share_ONE_document_and_ONE_lock`.

## Почему у работы НЕТ своего состояния

Состояние живёт ровно в строке реестра заданий. Работа, ещё не попавшая туда, получает
`PLANNED` — и это ИЗМЕРЕННОЕ отсутствие строки, а не догадка о состоянии. Две записи об
одном состоянии разошлись бы в тот момент, когда одна обновилась, а вторая нет; это и
есть второй бэклог, который запрещён. Закреплено `test_a_work_item_has_NO_state_field`.

## Состояние миссии маленькое, остальное ВЫВЕДЕНО

Объявленных состояний четыре: `NEW · PLANNING · ACTIVE · CLOSED`. Всё, что владелец
видит как «идёт / ждёт меня / готово», считается из работ и помечается `DERIVED`. Большой
перечень состояний миссии пришлось бы обновлять на каждом переходе работы — и он
расходился бы с работами так же, как второй бэклог.
