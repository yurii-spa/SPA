# Идея · «Шов двух симуляций» — повторяющийся класс, не единичный случай

**Не инструкция.** Свободная заметка (см. CLAUDE.md «идея ≠ инструкция»); действие требует
`#promote` владельцем.

## Наблюдение

Один и тот же класс бага нашли уже ДВАЖДЫ, в двух независимых подсистемах:

1. **ADR-109 (2026-08-18→08-21)** — `equity_curve_daily.json` / `paper_evidence.json`: оба
   файла несли один и тот же синтетический прогревочный кусок (20 дней ровного прироста +
   откат на 205 назад ещё на 11 дней), а витринная «максимальная просадка» считалась по ВСЕМ
   дням разом. Шов между прогревом и настоящими данными читался как −0.20% просадка — при
   0.00% на настоящих днях. Go-live-проверка не обманулась (уже считала строго по реальным
   дням), витрина — обманулась.

2. **ADR-201 §4 (2026-09-02)** — `spa_core/strategy_lab/sleeve/composer.py`: trailing-DD
   ревью тени клеило хвост backtest-фазы (guardian-разогрев) и forward-точки в один массив;
   пока forward короче окна, окно неизбежно захватывало шов backtest→forward. Обе фазы НЕ на
   одной базе капитала (бэктест левериджа кончается выросшим, forward стартует с сид-
   капитала) — разрыв читался как −72.7% просадка при двух положительных дневных
   доходностях. Реально применил сдвиг весов на первый живой день.

## Общая форма

Где бы в системе НЕ ни склеивались две фазово-разные серии (backtest+forward, прогрев+трек,
любая будущая пара «синтетика + реальность») в ОДИН массив для последующей агрегатной метрики
(просадка, волатильность, любой rolling-показатель) — шов между фазами арифметически
неотличим от настоящего события, если агрегат не знает о границе явно.

Оба раза причина находилась не там, где искали изначально (расхождение двух файлов → на самом
деле проблема аналитики; ревью тени → на самом деле проблема измерения), и оба раза
gate/проверка, которая уже считала по правильному подмножеству дней (go-live-checker; теперь
и composer после фикса), оказывалась НЕ обманутой — обманывалась только производная/витринная
метрика.

## Возможный паттерн (не решение — на будущее рассмотрение)

Если появится третий случай — возможно, стоит формализовать как явное правило: «любая
rolling/агрегатная метрика, построенная на конкатенации фаз, обязана либо (а) исключать шов
явным индексом границы, либо (б) требовать минимум N точек ПОСЛЕ границы прежде чем читать
метрику как значимую» — по сути то, что уже сделано вручную в обоих случаях (ADR-109: считать
только по реальным дням; ADR-201: требовать полное trailing-окно из forward-only данных).
Кандидат для `.claude/rules/` или общего теста-класса — но только после `#promote`, не сейчас.
