контрольном worktree `/tmp/spa_wt_c103_ctl`, 4 failed за 3.69 с). Это не регрессия цикла #103.

Причина найдена и подтверждена переключением одной переменной окружения:

```

SPA_SESSION_PID=97309   pytest …то же самое…                                    →   4 failed
```

`SPA_SESSION_PID` выставляет `scripts/agent_orchestrator.sh`, то есть **ровно тот запуск, в котором

никогда (цикл #102: 1 failed / 91 210 passed на том же коде).

## Почему это важно, а не косметика

Красные — это **положительные контроли самой защиты от столкновения** (дефект #46, карточка
`agent-card-claim-collision-guard`, закрыта 30.07):

сессии сделали одну работу (`owner-decision-dva-tsikla-orkestratora-rabotali-odnovre`,
ждёт владельца).

**Косвенное подтверждение с живой системы:** в цикле #103 захват карточки прошёл, а

## Правдоподобная (НЕ подтверждённая) линия причины

Похоже на побочный эффект `agent-durable-session-id` (журнал научился писать `session_pid` /

## ЗАКРЫТО циклом #105 (2026-08-03)

### Причина названа по коду — и это НЕ та ветка сравнения, на которую указывала карточка

Карточка предполагала «побочный эффект `agent-durable-session-id` × `agent-self-claim-blocked-by-
own-second-identity`: сравнение „своя ли сессия“ стало срабатывать шире». Сравнение (`self_identities`
в `check_card_claim.py`) оказалось **исправным**. Врал ПИСАТЕЛЬ журнала, и его собственный докстринг
описывает контракт, который код тут же нарушал (`scripts/log_session_change.py::record`):

```python
"""``session`` overrides the writer's own id (a caller announcing on behalf of a session whose
   id it was given — otherwise the entry would carry this process's pid instead)"""
...
proc, _why = durable_process() if process is None else process   # ← якорь МОЕГО процесса
entry.update(proc)                                               #   штампуется ВСЕГДА
```

Смысл `session=` — «эта запись НЕ моя, я её только записываю». Якорь
(`session_pid` + `session_pid_start`) в той же записи утверждал ровно обратное. Читатель
верит якорю, а не ярлыку — **по замыслу**, потому что ярлык это кличка, а подтверждённая пара
(pid, старт) это личность, — поэтому чужая запись с моим якорем читалась как МОЯ.

### Ветка развилки выбрана замером, а не вкусом

Прод проверен сквозным прогоном ДО правки: два НАСТОЯЩИХ долгоживущих процесса
(`sleep` с разными pid, как две обёртки `agent_orchestrator.sh`), временный трекер и журнал —
A берёт карточку, B **корректно** получает `⛔ ЗАНЯТА` и отказ при `claim`. То есть обычный
случай «два цикла» защищён и без правки: `export SPA_SESSION_PID=$$` даёт каждой обёртке свой
якорь. **Дыра открывается ровно там, где одна команда объявляет ЗА другую сессию** — а это
единственный прод-путь `record(session=…)`: `announce_claim` в `claim_card`/`release_card`.

### Правка (одна, в писателе)

Якорь пишется только когда запись несёт СОБСТВЕННЫЙ id этого процесса; объявление за другую
сессию якоря не получает. Направление fail-CLOSED: без якоря читатель откатывается на
сопоставление по ярлыку, то есть на поведение, которое было ДО якорей — чужая запись остаётся
чужой, карточка читается ЗАНЯТОЙ. `agent-self-claim-blocked-by-own-second-identity` не отменён:
там несколько авто-ярлыков `pid<N>` ОДНОГО процесса, и такие записи идут с `session=""` ⇒ якорь
сохраняют (пиннится положительным контролем).

### Главный пункт — CI больше не слеп

Режим задаётся ВНУТРИ теста, а не окружением прогона: новый класс
`TestGuardUnderADeclaredDurableProcess` сам объявляет живой долгоживущий процесс
(`os.getpid()` — существует по построению) и проверяет предусловие явно: якорь не измерился ⇒
тест **КРАСНЫЙ**, а не пропущенный (иначе это был бы fail-OPEN-скип класса #37/#39).

**Мутационная приёмка (обе стороны, обе в двух режимах окружения):**

| мутация | без `SPA_SESSION_PID` (глазами CI) | с `SPA_SESSION_PID` |
|---|---|---|
| дефект возвращён (`elif True` — якорь всегда) | **3 failed** ← раньше CI видел 0 | 6 failed |
| перелёт (`elif False` — якоря нет никогда) | **2 failed** | 2 failed |
| откат мутаций | 195 passed | 195 passed |

Верхняя строка и есть закрытие пункта «CI перестаёт быть слепым»: на том же дефекте раннер
раньше не краснел вообще, теперь краснеет тремя проверками без всякой правки workflow.
