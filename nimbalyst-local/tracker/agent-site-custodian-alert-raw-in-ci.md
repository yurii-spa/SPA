## Что случилось

04.08 в 08:51:55Z владельцу пришёл алерт дословно так:

```
🛡️ SITE CUSTODIAN — 1 FAIL(s) @ 2026-08-04T08:51:55Z
  [FAIL] STALE_SNAPSHOT: snapshot as_of 2026-08-03 is 32.9h old (> 30h)
```

— и владелец завёл карточку «писать мне в чат простым языком, а не вот это вот».

При этом перевод на русский (`spa_core/telegram/humanize.py`) существует с 29.07 и знает
И заголовок `SITE CUSTODIAN — N FAIL(s)`, И код `STALE_SNAPSHOT`. То есть правила перевода
были в порядке — **перевод просто не запускался**.

## Корень (доказан, не предположен)

`.github/workflows/site_freshness.yml` зовёт монитор так: `python scripts/site_freshness_monitor.py`.
При запуске файла `sys.path[0]` — это каталог **`scripts/`**, а рабочий каталог в `sys.path`
не попадает вовсе. Корня репозитория на пути нет ⇒ `from spa_core.telegram.humanize import
humanize_body` падает `ModuleNotFoundError` ⇒ `except Exception: pass` его молча глотает ⇒
владельцу уезжает сырой английский.

Доказательства:
- воспроизведено локально: из каталога `scripts/` → `ModuleNotFoundError: No module named 'spa_core'`;
- сверено по времени: прогон workflow `2026-08-04T08:51:36Z` (schedule, `failure`) → алерт в `08:51:55Z`;
- на Маке дефекта не видно: `scripts/site_content_audit.py` импортирует `_alert` **пакетом**
  (`from scripts.site_freshness_monitor import _alert`), там корень на пути есть. Поэтому
  дефект жил только в CI и не попадался при ручной проверке.

Тот же молчаливый `except` глушил и `from spa_core.alerts import telegram_manager` — в CI алерт
всегда уходил нижней ступенью (сырой Telegram API), тоже незаметно.

## Что сделано

`scripts/site_freshness_monitor.py`:
- новая функция `_humanize_body(msg)` — сначала обычный импорт, при неудаче загрузка
  `spa_core/telegram/humanize.py` **по пути к файлу** (`importlib`), fail-safe → исходный текст;
- `_alert` зовёт её вместо голого импорта.

**Осознанное ограничение объёма:** загрузчик намеренно **НЕ трогает `sys.path`**. Вставить туда
корень репозитория было бы на строку короче, но тогда в CI стал бы достижим и `telegram_manager`
с его дедупом/кулдауном — а это изменение того, **каким каналом и с каким подавлением уходит
ТРЕВОГА** (риск fail-open: подавленный FAIL сайта). Владелец просил язык, а не маршрут доставки.
Лестница доставки осталась байт-в-байт прежней. Если менять маршрут — отдельным решением.

`humanize.py` НЕ трогал: им в этот же час владел цикл #109 (карточка
`agent-site-custodian-detail-still-english`, шаг 0b дал `claimed`). Правки не пересекаются:
там правила перевода, здесь — то, что перевод вообще запускается.

## Проверка

`spa_core/tests/test_site_custodian_alert_humanized.py` (+7 тестов). Проверяют ЭФФЕКТ в дочернем
процессе с CI-подобным `sys.path` (корень убран), а не текст исходника:

- **положительный контроль** — в дочернем процессе `spa_core` действительно не импортируется
  (без него файл был бы зелёным по ошибке, проверяя обычный импорт вместо условия инцидента);
- дословное сообщение владельца переводится, сырые `SITE CUSTODIAN` / `STALE_SNAPSHOT` / `[FAIL]`
  до него не доходят;
- числа выживают вербатим (`32.9h`, `30h`, обе даты) — перевод не съедает данные;
- нераспознанный код проходит вербатим; пустой ввод не роняет алерт-путь;
- структурные пины: `_alert` зовёт загрузчик, загрузчик не трогает `sys.path`.

**Приёмка двумя мутациями** (иначе «зелёный» ничего не значит):
1. вернул голый импорт в `_alert` → красный `test_alert_calls_humanize_loader`;
2. убрал загрузку по пути (наивная версия) → красный `test_owner_message_arrives_in_russian`,
   и он выдал **ровно тот текст, на который жаловался владелец**, байт-в-байт.

Прогоны: новый файл 7 passed; смежный срез (`humanize` / `no_live_telegram` / `cycle_gap_monitor`)
162 passed; `site_freshness_monitor` + `site_content_audit` + `safe_site_push` 24 passed;
`lint_llm_forbidden` — 167 файлов, 0 нарушений. Ни один существующий тест не изменён и не ослаблен
(инвариант #16).

Замечание для будущих сессий: новый тест поднимает **дочерний процесс**, куда внутрипроцессный
`telegram_guard` не достаёт. Живой отправки там быть не может по построению — вызывается только
чистая текстовая функция `_humanize_body`, `_alert` и любые сендеры не трогаются, а в окружении
дочернего процесса нет ни токена, ни chat-id.
