## Что измерено (цикл #150, 2026-08-07)

При доставке цикла #150 `push_to_github.py` отказал (fail-CLOSED, страж `guard_entry_loss` из цикла #139):

```

```

Ни одна запись не исчезала. Обе строки — заголовки, которым цикл #150 **дописал номер цикла**
(`… оркестратора **#2**) — …`, `## 2026-07-17 **— автономный цикл #16 …**`). Тела записей
совпали с remote **побайтово** (1256 и 6213 не-заголовочных строк), `git diff` — ровно
5 вставок / 5 удалений, все пять строки-заголовки.

## Две стороны находки

1. **Ложная тревога.** Страж сравнивает ТЕКСТ заголовка, поэтому переименование = исчезновение.
   Сама по себе она безобидна и даже полезна (fail-CLOSED, обход есть — `--allow-overwrite`).
2. **Опасная — список неполон.** В том же пуше переименован заголовок и в `2026-W31.md`
   (`… оркестратора **#28** — очередь владельца разобрана`), но страж его **не назвал**.
   Решение «обходить или нет» человек принимает ПО ЭТОМУ СПИСКУ. Список короче правды —
   значит, при настоящей потере в позднем файле обход будет дан по неполной картине.
   Похоже на выход из проверки после первого файла с находкой — проверить.

## Что предлагается

- Померить, обрывается ли проверка на первом файле с находкой, или причина другая.
- Различать **переименование** и **исчезновение**: заголовок, тело которого (до следующего
  заголовка) совпало с remote побайтово, — это переименование; называть его отдельным классом,
  но НЕ отказывать. Отказ оставить для настоящей потери тела.
- Тест в обе стороны: переименование заголовка не блокирует; удаление записи блокирует;
  находка во ВТОРОМ файле называется так же, как в первом.

## Сделано (цикл #154, 2026-08-07)

**Гипотеза карточки подтвердилась чтением кода, а не догадкой.** `build_entries`
(`push_to_github.py`) звал стража внутри цикла по файлам, и первый же
`DivergenceRefused` выбрасывал наружу — до второго файла дело не доходило никогда.
Побочно: blob'ы файлов ДО сбойного успевали создаться — мусор в репозитории при
отменённом пуше.

**Две правки, обе в `push_to_github.py`:**

1. **Переименование ≠ потеря.** Новая `classify_missing_entries` возвращает
   `(потеряно, переименовано)`. Две фазы, и порядок значим: сперва гасим по
   ЗАГОЛОВКУ с кратностью, и только у оставшихся смотрим ТЕЛО (до следующего
   заголовка, `entry_blocks`). Совпало побайтово под другим, ещё не
   сопоставленным заголовком ⇒ запись на месте. Пустое тело в кандидаты не
   берётся — оно совпало бы с чем угодно. **Не ослабление:** отказ наступает
   всегда, когда исчезает содержимое; случай переименования всё равно
   НАЗЫВАЕТСЯ нотой (проводка ноты через `guard_overwrite` на всех трёх путях —
   safe / unmeasured / пере-база — иначе «называть» было бы некому).
2. **Список — по ВСЕМ файлам.** Сперва через стража проходят все файлы, потом
   создаются blob'ы. Один сбойный файл — сообщение стража ДОСЛОВНО (на нём стоят
   существующие тесты и глаз человека); несколько — слитый список с именами всех
   файлов. Класс отказа сохраняется, если причина одна, и падает до
   `DivergenceRefused`, если причины разные: по классу вызывающий выбирает код выхода.

**Приёмка.** `spa_core/tests/test_entry_guard_rename_and_full_list.py`, +21 тест;
существующие тесты НЕ тронуты (инвариант #16 — только новый файл). Три мутации,
каждая красит РОВНО свою цель, откат sha256 байт-в-байт:
M1 (переименование не распознаётся) — 4 красных; M2 (обрыв на первом файле) — 2;
M3 (исходный переплетённый цикл guard+blob) — 3, включая тест на blob'ы-сироты.
Контроль в обратную сторону — 5 тестов на то, что настоящая потеря по-прежнему
отказ (в т.ч. самый тонкий случай: два одинаковых заголовка с одинаковым телом,
уцелел один).
