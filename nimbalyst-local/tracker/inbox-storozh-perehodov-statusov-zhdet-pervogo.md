## Что случилось и почему это важно

09.08 три карточки owner-gate сменили `status:` сами — вопрос владельцу закрылся без
владельца (карточка `inbox-statusy-kartochek-vladeltsa-perepisalis`). Цикл #187 поставил
пару «журнал аудита + сторож неатрибутированных переходов»: теперь ЛЮБОЙ переход без
записи в `data/tracker_status_audit.jsonl` называется вслух, с тяжестью CRITICAL, если
карточка ушла из `needs-owner` или пришла в `owner-done`.

Механизм стоит, но улова ещё нет: писатель себя не проявлял с момента установки, а
код в прод-дерево приедет штатным `code_sync_from_origin.sh` перед следующим циклом.

## Что от тебя нужно (агенту, не владельцу)

1. В каждом цикле выполнять шаг 0в протокола (`--root ~/Documents/SPA_Claude`) и **не
   проглатывать** находки: неатрибутированный уход из `needs-owner` = карточка.
2. Поймав первый переход — назвать писателя по журналу (pid/argv/дерево) и только ТОГДА
   решать пункт 2 исходной карточки (сопоставление ответа владельца по идентификатору,
   а не по заголовку). Чинить по гипотезе исходная карточка запрещает.
3. Постоянный прогон сторожа отдельным агентом launchd — **деплой, за владельцем**:
   автономно агентов не грузим (мандат). Пока сторожа двигают циклы оркестратора.

## Как понять, что готово

Журнал называет писателя поимённо хотя бы для одного настоящего перехода, либо за
30 дней прогонов ни одного неатрибутированного перехода не случилось — и это записано,
а не подразумевается.

## Что будет после

Либо чиним конкретного писателя (не гипотезу), либо закрываем класс как исчерпанный.

## Замер 2026-08-17 — писатель НАЗВАН, но у сторожа найдена встроенная ложная тревога

**Посылка карточки устарела.** «Писатель себя не проявлял с момента установки» — уже неверно:
живой журнал прода `data/tracker_status_audit.jsonl` содержит **7 записей**, все
`queue.set_status`, с pid, командой и деревом. Продюсер подключён в `spa_core/owner_queue/queue.py`
(`set_status` → `record_status_write`), `scripts/orchestrator_queue.py` зовёт его через
`cmd_set_status`; отдельного вызова аудита в самом скрипте нет и не нужно.

**Пара «журнал + сторож» проверена в обе стороны на живом коде** (изолированное дерево, `data/`
не тронуто):

| что сделали | что сказал сторож |
|---|---|
| законный переход `needs-owner → ingested` через `orchestrator_queue.py set-status` | `OK`, переход атрибутирован: `queue.set_status · pid 24298 · argv…`, код 0 |
| молчаливая правка строки `status:` руками | `FINDINGS`, `НЕАТРИБУТИРОВАН`, код 1 |

То есть первая половина приёмки («журнал называет писателя поимённо хотя бы для одного
настоящего перехода») **исполнена и доказана замером**, а не гипотезой.

**Найден дефект, из-за которого сторож в проде будет врать по построению.** Карточки лежат в git
(484 файла), журнал аудита — нет (`.gitignore:48` → `data/**/*.jsonl`). Законное закрытие вопроса
владельца, сделанное сессией в её дереве через наш API, приезжает в прод-дерево без записи о себе,
и сторож печатает `CRITICAL: неатрибутированный уход из needs-owner` — то есть «вопрос закрыли
без владельца». Воспроизведено: дерево A закрывает через API (журнал в A, 1 запись, писатель
назван), git довозит в дерево B только карточку, сторож в B → `verdict=FINDINGS critical=1 exit=2`,
«в журнале аудита нет ни одной записи об этом переходе». Протокол ОБЯЗЫВАЕТ работать из отдельного
дерева (§3.4) и гонять шаг 0в по проду — значит тревога звучит не иногда, а каждый раз.

**Чинить не стал: карточка это прямо запрещает** («чинить по гипотезе исходная карточка
запрещает»), а выбор лечения — решение владельца (след в карточке / журнал в git / чтение чужих
деревьев / принять шум). Заведена карточка
`owner-decision-zakrytie-voprosa-vladeltsa-iz-rabochego` с вариантами и рекомендацией.

**Постоянного прогона по-прежнему нет** (п. 3 карточки — деплой за владельцем): ни расписания, ни
вызывающего; в рабочем дереве нет даже первого снимка (`data/tracker_status_snapshot.json`
отсутствует), поэтому вердикт всегда «первый прогон, измерить не с чем» (484 карточки, 0 переходов).

**Поправка к подсказке про мёртвые захваты.** Освобождение `cycle-28258` (263 ч), `cycle-87477`
(233 ч), `cycle-81141` (202 ч), `pid43119` (48 ч) событий этому сторожу НЕ даёт:
`scripts/check_card_claim.py` пишет только `claimed_by`/`claimed_at` (`_CLAIM_KEYS`) и строку
`status:` не касается — переходов статусов там не возникает по построению.
