## Что измерено (цикл #315, 20.08, worktree на origin c79a7dec6)

Положительный контроль нового сторожа `spa_core/tests/_package_data_guard.py` запускает
дочерний `pytest` на подставном тест-файле. Первая редакция клала этот файл в `tmp_path`
родителя — и дочерний прогон **не доходил даже до `--collect-only`**: 300 с и таймаут.

```
subprocess.TimeoutExpired: [... '-m', 'pytest',
  '/private/var/folders/.../pytest-of-yuriikulieshov/pytest-4633/test_child_run_.../test_writer.py',
  '-q', '-p', 'no:cacheprovider', '-p', '_package_data_guard'] timed out after 300 seconds
```

Тот же файл, положенный в каталог от `tempfile.mkdtemp()` (то есть ВНЕ дерева basetemp
родителя), отрабатывает за **0.00 с** и даёт ровно ожидаемый результат. Воспроизведено
трижды: внутри прогона (дважды, 300 с) и отдельной командой из оболочки (мгновенно —
значит дело не в нагрузке и не в конкуренции с родителем).

**Признак:** тест-файл дочернего прогона лежит внутри `…/pytest-of-<user>/pytest-N/…`.
Причина точно не установлена (кандидат — уборка нумерованных каталогов / блокировки
`TempPathFactory`), и в этом цикле не измерялась: задачей было другое.

## Почему это стоит времени

В репозитории есть целый класс тестов, которые МЕРЯЮТ ЭФФЕКТ в дочернем процессе — иначе
его не видно (урок `pytest-diversion-blinds-effect-tests`, карточки #226/#229). Каждый
такой тест сегодня рискует зависнуть на пять минут вместо того, чтобы дать ответ, и
зависание выглядит как «тест долго идёт», а не как «проверка не выполнилась». Если такой
тест попадёт в CI без `--timeout`, он съест job целиком (ровно тот класс, ради которого в
`test.yml` держат `pytest-timeout`).

## Что сделать

1. Сосчитать, сколько тестов набора запускают дочерний `pytest` с файлом из `tmp_path`
   (grep по `subprocess.run(... "-m", "pytest"` рядом с `tmp_path`), и померить каждый:
   сколько из них уже платят этой задержкой молча.
2. Назвать причину замером (какая именно операция pytest не завершается), а не гипотезой.
3. Если причина подтвердится — договориться об ОДНОМ способе: каталог дочернего прогона
   берётся `tempfile.mkdtemp()`, и закрепить это тестом/линтом, а не устной договорённостью.

## Исполнено (цикл #382, 2026-08-25) — причина названа ЗАМЕРОМ, обе гипотезы неверны

**Пункт 1 — сколько тестов платят этой задержкой молча: ноль, но держится это на везении.**
Дочерний `pytest` запускают пять файлов набора. Ни один сегодня не кладёт тест-файл в `tmp_path`:
два guard-файла ушли на `tempfile.mkdtemp()` после аварии #315, `test_telegram_prefs_isolation`
брал `TemporaryDirectory`, `test_backup_root_hermetic_and_responsive` гоняет git-tracked
`_child_backup_pin_check.py`, а `test_tester_agent` настоящий pytest не зовёт вовсе.

**Пункт 2 — причина.** Гипотезы карточки (уборка нумерованных каталогов, локи `TempPathFactory`)
**опровергнуты**. Стек, снятый `faulthandler.dump_traceback_later` на висящем дочернем прогоне:

```
File "_pytest/pathlib.py", line 969 in scandir
File "_pytest/main.py",   line 557 in collect      # Dir.collect
File "_pytest/main.py",   line 837 in perform_collect
```

Механизм: без ini-файла среди предков аргумента pytest берёт **rootdir = общий предок cwd и
аргумента**. `tmp_path` — путь РАЗРЕШЁННЫЙ (`/private/var/folders/…`), cwd тоже (`/private/tmp/…`),
поэтому общий предок схлопывается в **`/private`**. `confcutdir` наследует rootdir, и
`Session.collect` строит `Dir`-узлы на КАЖДОМ предке аргумента внутри confcutdir — включая
`$TMPDIR`. `Dir.collect` делает по нему `scandir`. На замерявшейся машине в `$TMPDIR` лежало
**9 780 560** записей. Это не взаимоблокировка, а O(размер системного /tmp).

Измерено (то же дерево, тот же файл):

| форма вызова | время |
|---|---|
| `tmp_path`, без якоря | **TIMEOUT >25 с** |
| `tmp_path` + `--rootdir` | 0.26 с |
| `tmp_path` + `--confcutdir` | 0.13 с |
| `tmp_path`, cwd = каталог файла | 0.13 с |
| `mkdtemp` (неразрешённый `/var/…`) | 0.13 с |
| **тот же `mkdtemp` после `.resolve()`** | **TIMEOUT >25 с** |

Последняя строка и есть главное: **`mkdtemp` не чинит, а везёт.** Он возвращает неразрешённый
`/var/folders/…`, у которого с cwd нет общего предка кроме `/`, и pytest откатывается к каталогу
самого аргумента. Один `.resolve()` где угодно по дороге — и пятиминутный простой возвращается
молча. Договорённость «берите mkdtemp», о которой просил пункт 3, закрепила бы совпадение.

**Пункт 3 — один способ, закреплённый линтом.** `spa_core/tests/_child_pytest.py`
(`child_pytest_argv` / `run_child_pytest`) всегда пинит `--rootdir` на каталог самого файла.
Все три места, где дочерний файл может оказаться вне репозитория, переведены на него
(`test_package_data_guard`, `test_live_data_write_guard`, `test_telegram_prefs_isolation`).
`test_child_pytest_rootdir.py` держит договорённость: линт по обоим каталогам тестов + именной
список исключений с причинами (файлы, чей аргумент всегда внутри репозитория, — им rootdir даёт
`pytest.ini`), и сам список ведён только вниз.

**Приёмка — три мутации:** (1) снять `--rootdir` из хелпера → 3 failed, и сквозной контроль
воспроизводит аварию дословно («не ответил за 30.0 с»); (2) молча вернуть незаякоренный
`subprocess.run` → линт краснеет; (3) внести в список исключений файл без предмета → краснеет
храповик списка. Восстановленное дерево — 77 passed по всем затронутым файлам.

**Найдено по дороге, в своей же работе.** Вторая редакция линта засчитывала якорь ИЗ
КОММЕНТАРИЯ: мутация (2) осталась зелёной, потому что рядом лежал комментарий со словом
`--rootdir`. Это класс «сторож, описавший свою аварию, кормит свой же корпус». Линт теперь
судит по КОДУ — комментарии и докстринги снимаются перед проверкой; предфильтр по сырому тексту
оставлен ради скорости и может только расширять множество кандидатов (6.8 с → 0.26 с).
