## Как найдено

Побочная находка цикла #107 (задача — гейт mypy, к этому файлу отношения не имеет). Цикл, как
предписывает протокол, гонял полный срез в СВОЁМ worktree и контроль на чистом `origin/main`
**одновременно** — так делают все последние циклы, чтобы уложиться в бюджет времени.

## Что измерено

Параллельный прогон (обе стороны стартовали в одну секунду):

```
worktree #107 : 12954 passed, 8 errors   ← ERROR tests/test_fund_api.py::FundAPITestCase::test_01…test_08
контроль      : 12951 passed, 1 error    ← ERROR tests/test_fund_api.py::MissingFileTestCase::…
```

Тот же набор, прогнанный ПОСЛЕДОВАТЕЛЬНО (сначала worktree, потом контроль):

```
worktree #107 : 12962 passed, 38 skipped, 0 errors, 0 failed
контроль      : 12952 passed, 38 skipped, 0 errors, 0 failed
tests/test_fund_api.py в одиночку: 9 passed  (на обеих сторонах)
```

⇒ восемь «падений» существовали только потому, что рядом шёл второй pytest. Причина в коде:

```python
# tests/test_fund_api.py:30
PORT_MISS = 18766   # тест отсутствующих файлов
# tests/test_fund_api.py:38
server = http.server.HTTPServer(("127.0.0.1", port), api_module.FundAPIHandler)
```

Порты **фиксированные**, сервер поднимается по-настоящему. Два прогона на одном хосте дерутся
за один и тот же порт: кто успел — тот забиндил, второму прилетает `OSError: address already
in use`, и это выглядит как «тесты упали».

## Почему это стоит починить

Это дефект **измерения**, а не продукта, и он бьёт ровно по методике, на которой построена
приёмка всех автономных циклов: «worktree против контроля на чистом origin в том же
окружении». Фантомные ошибки:

1. **шумят в сторону ложной тревоги** — цикл видит падения, которых нет, и тратит заход на
   их разбор (цикл #107 потратил два полных прогона, чтобы это исключить);
2. **могут замаскировать настоящие** — «ну это опять порт» становится удобным объяснением для
   любой ошибки в этом файле;
3. **несимметричны** — числа зависят от того, кто первым добежал до этого файла, то есть
   «дельта passed» между worktree и контролем перестаёт быть воспроизводимой.

Стоит перепроверить, не этим ли объясняется часть `ERROR`, которые прошлые циклы (#104, #105,
#96) фиксировали в своих таблицах приёмки как «предсуществующие, байт-в-байт одинаковые» —
у них контроль тоже шёл параллельно.

## Что предлагается сделать

Занимать порт **0** (ядро выдаёт свободный) и читать фактический номер из
`server.server_address[1]`, а не хардкодить 18766/8766. Тогда параллельные прогоны
изолированы по построению, и правка не ослабляет ни один ассерт — она вообще не трогает то,
что тесты проверяют.

## Acceptance criteria

- ни один порт в `tests/test_fund_api.py` не задан константой; адрес берётся у уже поднятого
  сервера;
- положительный контроль: ДВА полных прогона `tests/test_fund_api.py` одновременно дают
  `9 passed` оба (сейчас второй краснеет) — проверяется запуском, а не рассуждением;
- ни один существующий ассерт не изменён (инв. #16);
- запись в `docs/journal/<неделя>.md`.

**Не входит:** RiskPolicy / kill-switch / живой трек / launchd / `landing/**`. Сам
`scripts/fund_api_server.py` (прод) не трогать — дефект в тесте, а не в сервере.

## Сделано — цикл #114 (2026-08-04, `SPA_SESSION_PID=7886`, worktree `/tmp/spa_wt_c114` от `origin/main e2c80a555`)

Карточка была **осиротевшей**: цикл #110 (`pid7817`) взял её в 11:31Z и умер до пуша, работа
осталась в `/tmp/spa_wt_c110`. Шаг 0b дал `СТАРЫЙ ЗАХВАТ`, `claim` корректно **отказал**
(авто-захвата осиротевшего нет) ⇒ подъём вручную по шагу 0a. **Отчёту мёртвой сессии не верил** —
всё перемерено прогонами в своём дереве.

### Дефект воспроизведён ДО правки (на чистом `origin/main`)

Два одновременных прогона `tests/test_fund_api.py`, оба на неисправленном дереве:

```
прогон A: 1 passed, 8 errors   ← ERROR FundAPITestCase::test_01…test_08
прогон B: 8 passed, 1 error    ← ERROR MissingFileTestCase  (OSError: [Errno 48] Address already in use)
```

Это и есть заявленная несимметричность: кто первым забиндил 18765/18766 — тот и «прошёл».
Одиночный прогон на том же дереве: `9 passed`.

### Что изменено (`tests/test_fund_api.py`)

* `PORT_MAIN = 18765` / `PORT_MISS = 18766` **удалены**; `_start_server` больше не принимает порт
  аргументом (пока номер можно было назвать — его называли константой), биндит `("127.0.0.1", 0)`
  и кладёт фактический номер в `thread.port`, прочитанный у уже забиндившегося сокета;
* оба тест-класса подключаются на `cls.server_thread.port`;
* `server.allow_reuse_address = True` **удалено**: присвоение шло ПОСЛЕ конструктора, то есть уже
  после `bind` — оно не могло ни на что повлиять и лишь создавало впечатление, будто конфликт
  портов чем-то обработан;
* добавлен `_stop_server()`: прежний teardown звал только `shutdown()` (выводит `serve_forever` из
  цикла), но не `server_close()` — слушающий сокет оставался забинденным после каждого прогона;
* новый `EphemeralPortTestCase` (2 теста) — гейт против рецидива.

### Осознанное отличие от версии мёртвой сессии #110

Работа #110 разобрана и в основном подтверждена, но её второй гейт-тест
(`test_port_is_assigned_by_the_kernel_not_by_the_test`) **не взят**: он поднимает два сервера
ПОСЛЕДОВАТЕЛЬНО и требует разных портов, объясняя это тем, что «ядро не переиспользует только что
освобождённый эфемерный порт сразу». Объяснение неверное: тест зелёный лишь потому, что между
стартами звался `shutdown()` без `server_close()`, то есть первый сокет оставался ЗАНЯТ. Как
только утечка чинится (а она здесь чинится), тест начинает зависеть от политики переиспользования
портов ядром — то есть становится флаки-тестом, притворяющимся гейтом. Заменён на два честных:
`test_concurrent_servers_get_distinct_live_ports` (три сервера ОДНОВРЕМЕННО — детерминизм от
настоящей одновременности) и `test_reported_port_is_the_one_the_socket_is_bound_to`.
