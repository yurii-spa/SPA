**Единственный источник блокировки — одно объявление цикла #49** от 2026-07-30T23:23:28Z,
и обе карточки упомянуты в нём **В ОТРИЦАНИИ**:

> «Шаг 0b: agent-durable-session-id = ЗАНЯТА …, agent-idea21-verdict-data-drift =

Тот же цикл #49 через 49 минут объявил `card_state: done` по СВОЕЙ карточке
(`agent-push-batch-per-file-commits`) и завершился. То есть карточки заперты записью
сессии, которая явно от них отказалась и давно закончила работу.

## Почему это не «просто осторожность», а дефект

Инструмент **сам** объявляет обратное поведение обязательным (докстринг
`scripts/check_card_claim.py`, «Осознанные границы»):

> **слабый признак (упоминание в тексте) блокирует только пока свеж.** Старое упоминание
> уходит в раздел «история», а не в находку: **иначе любая когда-либо тронутая карточка
> была бы занята навсегда.** Старая НЕдоставленная работа — домен шага 0a.

Ровно этот сценарий и наступил, просто по другому маршруту, чем автор закрыл. В `_classify`
порядок веток такой (`scripts/check_card_claim.py`):

```python
if state == ACTIVE or age <= grace:      # свежий  → находка
    ...
if state == sibling.UNKNOWN:             # ← СТОИТ РАНЬШЕ проверки силы признака
    _unmeasured(...)                     #   → «не измерено» независимо от возраста
    return
if strength == STRONG:                   # старый сильный → stale
    ...
else:                                    # старый слабый  → история   ← сюда не доходит
    ...
```

Ключ в том, что `UNKNOWN` здесь **не временное состояние**. `check_undelivered_work.session_state`
возвращает `UNKNOWN` для идентификатора без pid (`cycle49`, `cycle55`, `cycle56`, `cycle57`)
**детерминированно и навсегда** — pid из строки не появится ни через час, ни через год. Значит
для любой сессии с таким id ветка старения недостижима **по построению**, и одно упоминание
карточки в свободном тексте запирает её до конца существования журнала.

**Это не гипотеза — это уже случилось.** Циклы #50, #51, #53, #54 в своих объявлениях записали
одну и ту же строку «шаг 0b — 2 не измерено (id cycle49 без pid)» и каждый раз просто брали
другую карточку. Две карточки бэклога недоступны **19 часов и далее без ограничения срока**,
причём одна из них (`agent-durable-session-id`) — это ровно та задача, которая чинит корень
`UNKNOWN`. Очередь голодает, и никто этого не заметил, потому что вердикт выглядит как
осторожность, а не как поломка.

## Что сделать

Применить объявленный докстрингом инвариант и к неизмеримой активности: **для СТАРОГО
(вне окна свежести) признака решает сила признака**, а не измеримость сессии.

- `WEAK` + старый + `UNKNOWN` → **история** (как уже работает `WEAK` + старый + `NOT_CONFIRMED`);
- `STRONG` + старый + `UNKNOWN` → **остаётся «не измерено»** (fail-CLOSED НЕ ослабляем:
  сильный признак — это заявленный захват, а не обмолвка в тексте);
- свежий (в пределах окна) — поведение не меняется ни для одной комбинации.

Почему это безопасно: настоящий захват карточки **всегда** сопровождается сильным признаком —
поле `card:` в записи и/или файл карточки в объявленном владении (`announce_claim`, цикл #54
сделал «взял, но не объявил» невозможным состоянием). Слабый признак — это по определению
не захват, а совпадение текста; именно поэтому докстринг и отводит ему окно свежести.
Старая недоставленная работа остаётся доменом шага 0a, который её и находит.
