## ✅ Закрыто циклом #102 (2026-08-03)

**Сделано.** Сверка доставленного включена во ВСЕХ трёх точках записи, одной
реализацией на оба CLI (`verify_sha_delivery` / `verify_blob_delivery`,
`DeliveryUnverified`):

| точка записи | что сверяется | расхождение |
|---|---|---|
| `push_file` — PUT `/contents/{path}` | `content.sha` vs git-blob-SHA отправленных байтов | FAIL (`ok=False`), файл назван |
| `create_blob_from_bytes` — POST `/git/blobs` | `sha` vs git-blob-SHA байтов | `DeliveryUnverified` ДО коммита — ветка не двигается |
| `update_ref` — PATCH `/git/refs/heads/{br}` | `object.sha` vs наш commit sha | `DeliveryUnverified` (exit 6 в обоих CLI) |

**Главный вопрос карточки — цена и риск ложного красного — решён ИЗМЕРЕНИЕМ, а
не рассуждением.** Второго GET после записи нет вовсе: сверяем sha, которую
вернул САМ ответ на нашу запись. Поэтому задержка согласованности Contents API
(та, что уже ловилась на refs, `_read_ref_with_404_retry`) физически не может
дать ложный красный — мы не читаем remote повторно. Стоимость: **ноль
дополнительных обращений к API**, и это пиннят два теста, которые считают
вызовы и требуют равенства (`test_verification_costs_zero_extra_requests_*`);
они зелёные И до, и после фикса — то есть измеряют цену, а не фикс.

**«Не смогли сверить» осталось «не измерено»** (инв. #2): sha нет / она не
40-hex → печатается явной строкой, доставку НЕ блокирует, а итоговая строка
`OK: N файл(ов) (pushed=…, сверка НЕ ИЗМЕРЕНА у K)` не имеет права быть
зеленее замера.

**Проверка.** Новый файл `spa_core/tests/test_push_delivery_verification.py`,
22 теста: на чистом `origin/main` **16 краснеют**, 6 зелёные в обе стороны
(два замера цены + отсутствие ложных красных + гейт против второй копии).
Мутации M1 (страж перезаписи снят) / M2 (409-ретрай снят) / M3 (mismatch →
warning) — **все пойманы**, после отката 34/34 зелёные.

**Инвариант #16 — что изменено в существующих тестах и почему.** Два стаба
PUT-ответа возвращали заглушку `"f" * 40` (`test_push_divergence_guard.py`,
`test_filelock_concurrent.py`): поле `content.sha` тогда никто не читал дальше
`[:8]` для печати. Настоящий Contents API возвращает sha именно того blob'а,
который сохранил. Доказано ТРИЖДЫ, а не объявлено: (1) это равенство уже
несущее в проде — идемпотентный пропуск `push_file`/`split_unchanged` сравнивает
remote sha с `git_blob_sha` локальных байтов и работает много циклов; (2) тот же
`test_push_divergence_guard.py` уже моделирует blob-эндпоинт Git Data API
честно; (3) прямой замер: `git rev-parse origin/main:README.md` = `ebfbaa2c…` =
`git_blob_sha(README.md)`. Стабы стали ТОЧНЕЕ (считают sha независимой
реализацией, не функцией из кода под тестом) — **ни один ассерт не удалён, не
ослаблен и не заскиплен**, а обе группы тестов по-прежнему ловят свой исходный
дефект (мутации M1/M2). Запись — `docs/journal/2026-W32.md`.

**Не делал:** RiskPolicy / kill-switch / пороги / живой трек / launchd / деплой /
`landing/**` — не трогал.

## Как найдено

Вторая половина карточки `agent-task-povtornoe-dopisyvanie-faila-v-odnom-tsik` (закрыта циклом
#99). Сама причина дубля там починена, но общий механизм остался: **пушер сообщает
`OK … pushed=N, skipped=0`, ни разу не сверив доставленное с тем, что реально легло на remote.**

В цикле #95 дубль в `docs/journal/2026-W32.md` заметили только потому, что после пуша вручную
выполнялась побайтовая сверка (`git show origin/main:<файл> | cmp - <файл>`). То есть поймала
ДИСЦИПЛИНА вызывающего, а не инструмент. Убери сверку из протокола — порча уехала бы в общую
память проекта незамеченной.

## Почему это отдельная карточка, а не часть предыдущей

Это **изменение поведения доставки**: то, что сейчас отчитывается `OK`, может начать краснеть.
Пушер зовут живые пути, которые никто не смотрит в момент запуска:

- `com.spa.autopush` → `auto_push.sh`;
- дневной цикл (`run_daily_paper_cycle.sh`);
- кастодиан сайта / `safe_site_push.py`.

Ложный красный в любом из них — это тихо вставшая доставка, то есть ровно та цена, которую
карточка про дубль и описывает, только с другой стороны. Поэтому: одна задача за заход
(мандат автономии), и сначала измерить, а не «включить проверку».

## Что предлагается сделать

После успешного PUT перечитать файл с remote и сравнить побайтово с тем, что мы отправляли.
Расхождение ⇒ честный FAIL с указанием файла (не «warning»: предупреждение, которое никто не
читает, — это fail-OPEN класса #29/#31/#35–#38/#40).

**Обязательно измерить до включения:** сколько дополнительных GET это стоит на типовом батче,
и не даёт ли GitHub Contents API согласованность «с задержкой» (тогда сразу после PUT можно
прочитать старое содержимое и покраснеть на ровном месте — это и есть главный риск ложного
красного; нужен либо ретрай, либо сверка по возвращённому в ответе PUT `content.sha`,
что дешевле и не требует второго GET).

## Acceptance criteria

- расхождение доставленного с remote даёт FAIL, а не `OK` (положительный контроль: подменить
  ответ так, чтобы remote отличался, — тест обязан краснеть);
- отсутствие расхождения не даёт ложных красных на живых путях: измерено на реальном батче,
  а не рассуждением;
- «не смогли сверить» остаётся «не измерено» и НЕ выдаётся за совпадение (инв. #2), но и не
  блокирует доставку молча — печатается явной строкой, как это уже сделано в `guard_overwrite`;
- существующие тесты пушера не ослаблены (инв. #16);
- сеть в тестах не трогается (страж `network_guard`), ответы API инжектятся.

**Не входит:** RiskPolicy / kill-switch / живой трек / launchd / `landing/**`.
