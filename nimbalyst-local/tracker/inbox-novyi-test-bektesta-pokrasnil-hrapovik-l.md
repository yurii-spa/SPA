## Почему это не чинится прицепом

Литеральные даты в файле — **швы бэктеста** (`_BACKTEST_START` 2024-07-01, `_BACKTEST_END`
2026-05-31, швы 2025-06-30 / 2026-01-01). То есть дата здесь **и есть предмет**, а это ровно
третий разрешённый случай правила (`.claude/rules/deployment.md`, § «Время в тестах»):

> 3. **Литеральная дата — только если сама дата является предметом** (парсинг, golden-файл,
>    исторический инцидент). Тогда пометить файл `# FROZEN-DATE-OK: <причина>` — это решение
>    на протоколе, а не недосмотр.

Значит починка — **пометка с причиной**, а не переписывание фикстуры. Но пометка есть
ЗАЯВЛЕНИЕ о чужой работе: причину обязан назвать тот, кто знает, почему шов именно такой.
Дописывать файл в `frozen_date_baseline.json` **ЗАПРЕЩЕНО** (база только убывает).

## Что надо сделать

3. Положительный контроль: храповик обязан краснеть, если пометку снять.

## Класс ПОВТОРЯЕТСЯ — и это замер, а не догадка

Ровно эта находка уже заводилась карточкой
`inbox-hrapovik-zamorozhennyh-dat-krasen-na-chi` (28.09, статус `done`): там предметом был
`spa_core/tests/test_studio_os.py` из коммита `5b6525778` — шесть литералов
`2026-09-28T00:00:00Z`. Тот экземпляр закрыт, **класс — нет**: починка здесь по построению
ПОФАЙЛОВАЯ (пометка с причиной либо инъекция часов), поэтому закрытие одного файла следующий
не предотвращает.

Что из этого следует для замера, а не для настроения: **доставки, приносящие новые тест-файлы
с историческими окнами, краснят `main` систематически**, и у этого есть цена — «было красно и
стало красно» перестаёт быть сигналом для каждого следующего дифференциального замера (ровно
жалоба заказа G832 п. 4). Вопрос, который стоит задать ЗАМЕРОМ, а не починкой: сколько
доставок за последние N дней покраснили этот храповик, и нет ли у класса общего ПИСАТЕЛЯ
(например, один агент-автор тест-файлов с бэктест-окнами) — тогда чинить надо шаблон писателя,
а не файлы по одному.
