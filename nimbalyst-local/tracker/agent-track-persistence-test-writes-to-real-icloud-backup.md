## Как найдено

Побочная находка цикла #112 (задача цикла — перевод алертов Site Custodian, к персистенсу
отношения не имеет). Полный прогон `spa_core/tests/` **не завершился**: процесс встал на 0 % CPU
и висел, держа слушающий TCP-сокет. То же самое обнаружилось у осиротевшего прогона мёртвой
сессии цикла #110 — он висел на этот момент **3 ч 26 мин** в СВОЁМ дереве, то есть на коде
БЕЗ правок #112. Контрольный прогон на чистом `origin/main` тоже повис. Значит дефект
предсуществующий и от изменений цикла не зависит.

Цикл #111 видел ровно этот файл (`test_track_persistence.py::test_persist_success_writes_valid_nonempty_db_and_ok_flag`
в списке падений контроля) и записал: «стендэлоун-прогон файла завис на 15-м тесте — снял…
причину не измерял, карточку не заводил». Здесь причина **измерена**.

## Причина (измерена, а не предположена)

`--timeout=90 --timeout-method=thread` на одном файле дал стек:

```
spa_core/tests/test_track_persistence.py:405  test_persist_success_writes_valid_nonempty_db_and_ok_flag
  ok = cr._persist_track(tmp_path, cr._default_track_persister, notes)
spa_core/paper_trading/cycle_runner.py:604   _persist_track
spa_core/paper_trading/cycle_runner.py:554   _default_track_persister →  backup = run_backup(ddir)
spa_core/persistence/backup.py:167           run_backup      → _atomic_copy(src, dest / name)
spa_core/persistence/backup.py:93            _atomic_copy    → os.replace(tmp_name, dest)   ← ВИСИТ ЗДЕСЬ
```

Тест зовёт **настоящий** `_default_track_persister` и не передаёт `backup_dir`, поэтому
`run_backup` берёт `default_backup_dir()` (`backup.py:64`):

```
$SPA_BACKUP_DIR → ~/Library/Mobile Documents/com~apple~CloudDocs/SPA_backups (iCloud) → ~/SPA_backups
```

Переменная не выставлена, каталог iCloud на этой машине существует ⇒ тест пишет в **реальный
off-site бэкап живого трека**, а `os.replace` блокируется на слое синхронизации iCloud.

**Подтверждение, что дело в файловой системе, а не в логике теста:** обычный `ls` этого каталога
из шелла тоже **не вернулся за 2 минуты** (снят по таймауту). Каталог не отвечает — виснет всё,
что его касается.

## Почему это важно

1. **Полный прогон `spa_core/tests/` на этой машине НЕ МОЖЕТ завершиться.** Ровно этим срезом
   циклы отчитываются «X passed / 0 failed» перед пушем. Пока iCloud не отвечает, такой отчёт
   получить нельзя — прогон висит вечно, а не падает (виснущий прогон легко принять за «долгий»).
2. **Тест пишет в продовое хранилище.** Это класс `tests-write-live-alert-state` из постоянной
   памяти: прогон тестов мутирует настоящее состояние. Здесь — off-site бэкап живого трека,
   то есть последний рубеж восстановления.
3. Осиротевшие висящие прогоны копятся: один провисел 3.5 ч и был бы вечным.

## Чего это НЕ значит (честная граница)

**CI от этого не краснеет.** На Linux-раннере `_ICLOUD_PARENT.exists()` = False ⇒
`default_backup_dir()` уходит в `~/SPA_backups`, каталог локальный и отвечает. Дефект
**специфичен для macOS-хоста** (там же, где крутится прод-флот). Утверждать «из-за этого красный
main» — нельзя, и я этого не утверждаю: единственный красный на main — другой тест
(`test_telegram_guard_stays_outermost`, карточка `agent-network-guard-attempts-never-reset`).

## Что предлагается (acceptance)

- [ ] тест не касается продового хранилища: `backup_dir` передаётся явно (tmp) **или** прогон
      тестов принудительно резолвит `SPA_BACKUP_DIR` в tmp (например, autouse-фикстура в
      `conftest.py`) — герметичность, а не отключение проверки;
- [ ] покрытие не уменьшается: путь `_default_track_persister` по-прежнему проверяется, просто
      против управляемого каталога (положительный контроль: с подменённым корнем тест ловит тот же
      дефект, ради которого написан);
- [ ] `_atomic_copy` / `run_backup` не могут заблокироваться навсегда на неотвечающем каталоге —
      либо таймаут/пробник доступности, либо честная ошибка в `result["errors"]`
      (`run_backup` документирован как «never raises», поэтому отказ должен быть ЗАПИСАН, а не
      проглочен молча — fail-CLOSED, инв. #2);
- [ ] регресс-тест: неотвечающий каталог бэкапа не вешает прогон.

## Чего НЕ делать

- **Не скипать и не удалять тест** (инв. #16) — он покрывает реальный money-path трека.
- Не менять `default_backup_dir()` приоритеты (iCloud как off-site — сознательное решение,

- Не трогать `spa_core/paper_trading/cycle_runner.py` в обход обычной процедуры money-path.

## Что цикл #112 сделал вместо починки

Ничего в репозитории по этому поводу **не менял**. Для СВОИХ замеров прогон запускался с
`SPA_BACKUP_DIR=/tmp/...` — это документированный официальный override самого модуля
(`backup.py:66`), он не трогает ни репозиторий, ни CI-конфиг, ни сам тест, и в git не уезжает.
Снял два висящих прогона (свой и осиротевший от мёртвой сессии #110, 3.5 ч на 0 % CPU).
