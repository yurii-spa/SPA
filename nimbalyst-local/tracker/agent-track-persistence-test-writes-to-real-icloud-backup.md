## Причина (измерена, а не предположена)

`--timeout=90 --timeout-method=thread` на одном файле дал стек:

```
spa_core/tests/test_track_persistence.py:405  test_persist_success_writes_valid_nonempty_db_and_ok_flag
  ok = cr._persist_track(tmp_path, cr._default_track_persister, notes)
spa_core/paper_trading/cycle_runner.py:604   _persist_track
spa_core/paper_trading/cycle_runner.py:554   _default_track_persister →  backup = run_backup(ddir)
spa_core/persistence/backup.py:167           run_backup      → _atomic_copy(src, dest / name)
spa_core/persistence/backup.py:93            _atomic_copy    → os.replace(tmp_name, dest)   ← ВИСИТ ЗДЕСЬ
```

Тест зовёт **настоящий** `_default_track_persister` и не передаёт `backup_dir`, поэтому
`run_backup` берёт `default_backup_dir()` (`backup.py:64`):

```
$SPA_BACKUP_DIR → ~/Library/Mobile Documents/com~apple~CloudDocs/SPA_backups (iCloud) → ~/SPA_backups
```

Переменная не выставлена, каталог iCloud на этой машине существует ⇒ тест пишет в **реальный
off-site бэкап живого трека**, а `os.replace` блокируется на слое синхронизации iCloud.

**Подтверждение, что дело в файловой системе, а не в логике теста:** обычный `ls` этого каталога
из шелла тоже **не вернулся за 2 минуты** (снят по таймауту). Каталог не отвечает — виснет всё,
что его касается.

## Почему это важно

1. **Полный прогон `spa_core/tests/` на этой машине НЕ МОЖЕТ завершиться.** Ровно этим срезом
   циклы отчитываются «X passed / 0 failed» перед пушем. Пока iCloud не отвечает, такой отчёт
   получить нельзя — прогон висит вечно, а не падает (виснущий прогон легко принять за «долгий»).
2. **Тест пишет в продовое хранилище.** Это класс `tests-write-live-alert-state` из постоянной
   памяти: прогон тестов мутирует настоящее состояние. Здесь — off-site бэкап живого трека,
   то есть последний рубеж восстановления.
3. Осиротевшие висящие прогоны копятся: один провисел 3.5 ч и был бы вечным.

## Чего это НЕ значит (честная граница)

**CI от этого не краснеет.** На Linux-раннере `_ICLOUD_PARENT.exists()` = False ⇒
`default_backup_dir()` уходит в `~/SPA_backups`, каталог локальный и отвечает. Дефект
**специфичен для macOS-хоста** (там же, где крутится прод-флот). Утверждать «из-за этого красный
main» — нельзя, и я этого не утверждаю: единственный красный на main — другой тест
(`test_telegram_guard_stays_outermost`, карточка `agent-network-guard-attempts-never-reset`).

## Сделано (цикл #113, 04.08)

**Дефект воспроизведён на этой машине перед починкой, а не принят на веру.** `_ICLOUD_PARENT.exists()`
= True ⇒ `default_backup_dir()` отдаёт iCloud-корень; обычный `os.listdir` этого корня
**не вернулся за 20 с** (замер в отдельном демон-потоке, чтобы сам замер не завис).

Починены **две независимые половины** — каждая проверяется своим набором, каждая подтверждена
мутацией.

### A. Герметичность — ни один тест больше не резолвит продовый бэкап

`spa_core/tests/backup_dir_guard.py` (по образцу `push_state_guard` / `telegram_guard`) +
autouse-фикстура `_no_live_backup_dir` в **обоих** conftest'ах (`spa_core/tests/`, `tests/`),
модуль грузится по абсолютному пути из одного источника — корни не могут разъехаться.
`$SPA_BACKUP_DIR` пиннится в песочницу `tempfile.mkdtemp()`.

**Это перенаправление, а не мок** (требование acceptance «покрытие не уменьшается»):
`default_backup_dir()`, `run_backup()`, `_atomic_copy()`, ротация и манифест по-прежнему
исполняются целиком — меняется только каталог назначения. Тест
`test_real_backup_still_runs_against_the_sandbox` проверяет это явно: файл реально скопирован,
`manifest.json` реально записан.

Фикстура **на каждый тест**, а не одна на сессию: `tests/test_backup.py::test_A2` делает
`del os.environ["SPA_BACKUP_DIR"]` в `finally`, и без пере-установки пина это утекало бы в
следующий тест.

### B. Живучесть — неотвечающий корень больше не вешает прогон навсегда

`run_backup` перед записью пробит корень с жёстким дедлайном (`_probe_backup_root`,
`$SPA_BACKUP_PROBE_TIMEOUT_S`, по умолчанию 10 с). Проба выполняет **ровно тот набор системных
вызовов**, который нужен самому бэкапу (mkdir → mkstemp → fsync → `os.replace` → unlink).

Ключевая деталь: зависший системный вызов из Python **отменить нельзя**, поэтому дедлайн стоит на
ПОТОКЕ, а не на вызове — воркер демонический, на таймауте он остаётся припаркован в ядре, а
вызывающий уходит. Отказ **ЗАПИСАН**, а не проглочен: `status="error"` +
`errors: ["backup_root_unavailable: …"]` (инв. #2, fail-CLOSED). Контракт «`run_backup` никогда не
бросает» сохранён и на этой ветке.

`default_backup_dir()` и приоритет iCloud **не тронуты** (карточка это прямо запрещала);
`cycle_runner.py` **не тронут**.

  (16 прямых + один в дочернем процессе).

  которой дедлайн пробы стоит на ПОТОКЕ, а не на вызове.
- **Ранее висевший набор теперь завершается:** `spa_core/tests/test_track_persistence.py` +

  увидит СЛЕДУЮЩИЙ тест», изнутри ломающего теста оно ненаблюдаемо, а порядок в реальном наборе
  перемешивается `pytest-randomly`. После добавления мутация 2 краснит ровно его.
- **Положительные контроли** (чтобы страж не был заглушкой «всегда ок» / «всегда завис»): здоровый
