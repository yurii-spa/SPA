## Что случилось и почему это важно

Цикл #171, 2026-08-09 00:25 UTC. Три карточки owner-gate сайта в ПРОДЕ одновременно сменили
`status:` — сами, без участия сессии:

| Карточка | Было (записано сессией 00:19–00:20) | Стало в 00:25 |
|---|---|---|
| `…owner-gat` | `ingested` | `ingested` (не тронута) |
| `…owner-gat-2` | `ingested` | **`needs-owner`** |
| `…owner-gat-3` | `needs-owner` (новая, владельцу) | **`ingested`** |

То есть **вопрос владельцу закрылся сам**, а уже разобранный ответ снова встал в очередь как
неотвеченный. Тела карточек не пострадали — переписаны ровно строки `status:`. `_BOARD.md`
перегенерирован той же секундой.

**Чем это опасно:** живой вопрос владельцу (`-3`) стал невидим в очереди `needs-owner` —
ровно тот класс потери, ради которого в #147 вводили сверку с origin. Обнаружено случайно,
при ручной перечитке; ни один сторож не сказал ни слова.

## Что ИЗМЕРЕНО, а что нет

**Измерено:** прогон тестов из worktree прод-трекер НЕ трогает — проверено сверкой sha256
трёх карточек и `_BOARD.md` до и после прогона (`ПРОД НЕ ТРОНУТ`). Значит писал не тест.
`scripts/build_tracker_board.py` пишет только свой файл — тоже не он.

**НЕ измерено: кто именно переписал.** Гипотеза (не проверена): маршрутизация ответа
владельца по ЗАГОЛОВКУ, а не по идентификатору. У всех трёх карточек заголовок совпадает
дословно — «Сайт: автономная правка задела owner-gated область — нужно решение», потому что
его формирует генератор `safe_site_push` одной константой. Кандидат в писатели —
`spa_core/owner_queue/owner_answer.py` (разбор ответа/кнопки из Telegram): карточке `-3`
уведомление ушло в 00:19, а ответ владельца по такому же заголовку лежит в `-2` со вчера.

## Второй случай в том же цикле — механизм проступил

00:31:14 UTC. Сессия ДОПИСАЛА текст (только `cat >>`, ни одной правки строки `status:`) в четыре
карточки `owner-decision-kritichnaya-nahodka-petli-com-spa-*`. Секунда в секунду все четыре
сменили `needs-owner → ingested`.

Это уже не совпадение, а **закономерность: любая запись в файл карточки будит разборщика,
который переписывает `status:`**. Для этих четырёх исход ВЕРНЫЙ (находки опровергнуты #169,
закрытие законно — у карточек есть `finding_key`, их ведёт мост находок). Но у карточек сайта
`finding_key` НЕТ, а переставили и их — значит писатель сопоставляет карточки чем-то ещё,
и заголовок остаётся главным подозреваемым.

Опасна не автоматика, а её **немота**: закрытие вопроса владельца не оставляет ни строчки
в журнале сессии, и увидеть его можно только перечитав файл глазами.

## Что сделать

1. Сначала НАЙТИ писателя, а не чинить по гипотезе: временный аудит-лог на каждую запись
   `status:` в трекере (кто, какой pid, какая карточка, из какого дерева).
2. Если подтвердится маршрутизация по заголовку — сопоставлять ответ только по ИДЕНТИФИКАТОРУ
   карточки; совпадение по заголовку при нескольких кандидатах = отказ + карточка, а не выбор
   наугад (fail-CLOSED: молча закрыть чужой вопрос хуже, чем не закрыть свой).
3. Генератор `safe_site_push` обязан давать РАЗЛИЧИМЫЕ заголовки (например, с именем файла):
   три неотличимых карточки — это и есть условие ошибки.
4. Сторож: переход `needs-owner → ingested` БЕЗ соответствующей записи в журнале сессии —
   подозрительный, о нём надо говорить вслух.

## Как понять, что готово

Аудит-лог называет писателя поимённо; после починки два подряд уведомления по разным карточкам
с одинаковым заголовком не переставляют статусы — доказано прогоном, а не рассуждением.
Положительный контроль воспроизводит перестановку 00:25.
