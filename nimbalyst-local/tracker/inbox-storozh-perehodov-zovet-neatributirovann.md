## Что измерено (цикл #922, 2026-10-24)

`status_audit.trail_explains(text, old, new)` НЕ объясняет переход, который дословно записан
ПОСЛЕДНЕЙ строкой следа, если перед ней есть хотя бы одна непрерывная строка. Замер на живой
карточке `owner-decision-kritichnaya-nahodka-petli-com-spa-daily.md` (байты с `origin/main`):

```
след: needs-owner    -> owner-accepted · owner_answer.record_owner_answer
      owner-accepted -> ingested       · queue.set_status · cycle-53970

trail_explains(..., 'owner-accepted', 'ingested')  → None      ← последняя строка ЕСТЬ этот переход
trail_explains(..., 'needs-owner',    'ingested')  → True
```

Причина в разборе цепи: `chain_start` начинается с последней записи, но условие совпадения
(`entries[chain_start]["old"] == old`) проверяется ТОЛЬКО ПОСЛЕ первого декремента. Цепь
длиной в одну запись поэтому недостижима, пока слева есть непрерывный сосед.

## Чем это стоит

Это механизм ЛОЖНОЙ ТРЕВОГИ сторожа `tracker_status_sentinel`, то есть ровно то, против
чего написан сам след (его docstring: «требовать окна значило бы объявлять КАЖДУЮ
доставленную карточку неатрибутированной»). Население замерено в тот же день: прод-дерево
несло ПЯТЬ карточек `kritichnaya-nahodka-petli-com-spa-*` в статусе `owner-accepted`, тогда
как на origin все пять давно `ingested` с отчётом агента (цикл #807) и следом cycle-53970.
Приведение прод-копий к байтам origin — штатное и единственно верное действие — даёт пять
переходов `owner-accepted -> ingested`, и КАЖДЫЙ из них след объясняет, а функция — нет.
Цикл #922 закрыл их записями журнала аудита (`cycle-922.prod_copy_caught_up_with_origin`),
то есть ВТОРЫМ каналом атрибуции; след как канал остался неработающим для этого класса.

Чем ЧАЩЕ прод-копия догоняет origin из промежуточного состояния, тем чаще сторож будет
называть неатрибутированным то, что записано. Глохнет сторож именно так.

## Чего НЕ делать

Не «ослаблять» сторожа. Предмет узкий: цепь длиной в одну запись обязана быть достижима,
и у правки обязан быть контроль в ОБЕ стороны — переход, которого в следе НЕТ, по-прежнему
обязан получать `None` (иначе починка ложной тревоги купит слепоту к настоящей подмене
`status:`, ради которой весь модуль и написан, цикл #171).

## Как понять, что готово

`trail_explains` на байтах карточки `…com-spa-daily.md` с `origin/main` возвращает запись для
перехода `owner-accepted -> ingested`, и при этом возвращает `None` для перехода, которого в
следе нет (например `ingested -> needs-owner`). Оба утверждения — тестом.
