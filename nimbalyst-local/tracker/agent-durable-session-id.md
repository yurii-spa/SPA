**Как найдено (цикл #45).** При постройке шага 0a (`scripts/check_undelivered_work.py`,
карточка `agent-undelivered-work-guard`) выяснилось: проверить, жива ли объявившая работу
сессия, сегодня НЕЛЬЗЯ.

## Что не так

`scripts/log_session_change.py:29` — `os.environ.get("SPA_SESSION_ID") or f"pid{os.getpid()}"`.
Переменная `SPA_SESSION_ID` не выставляется НИГДЕ в проде (grep: только в тестах), поэтому в
`data/session_changes.jsonl` пишется pid **однократного CLI-процесса**, который умирает вместе
с командой. Следствия:

1. `ps -p <pid>` для ЛЮБОЙ записи, включая только что сделанную своей же сессией, отвечает
   «процесса нет» — измерение бессодержательно;
2. по журналу нельзя сказать, какие объявления принадлежат одной сессии (каждая строка — новый
   pid), т.е. нет и атрибуции рабочих деревьев `/tmp/spa_wt_*` к сессиям;
3. шаг 0a вынужден опираться на **возраст объявления** (окно ожидания 3ч) вместо факта
   активности — это работает, но грубее: сессия, работающая дольше окна, попадёт в находки
   как «не доставила» (ложная тревога в безопасную сторону).

## Что предлагается сделать

Выдавать сессии durable-идентификатор и писать его во ВСЕ её записи: например
`SPA_SESSION_ID=cycle45-<pid оболочки>` из `scripts/agent_orchestrator.sh` (и аналогично для
интерактивных сессий), плюс поле с pid ДОЛГОЖИВУЩЕГО процесса, по которому `ps` осмыслен.
Тогда шаг 0a сможет отличать «сессия работает» от «сессия исчезла» измерением, а не эвристикой,
и окно ожидания станет страховкой, а не основным критерием.

## Acceptance criteria

- [x] все записи одной сессии в `session_changes.jsonl` несут один и тот же идентификатор
      (`SPA_SESSION_ID` из обёртки цикла) и один и тот же `session_pid`;
- [x] по записи можно проверить активность долгоживущего процесса (`ps`), а не однократного CLI;
- [x] `scripts/check_undelivered_work.py` использует это как ОСНОВНОЙ критерий, окно ожидания
      остаётся запасным (существующие 42 теста не ослабляются);
- [x] обратная совместимость: старые записи вида `pid<N>` продолжают разбираться как сейчас.

**Не входит:** авто-доставка чужой работы; правки launchd/деплоя.

## Закрыто циклом #62 (2026-07-31)

**Что сделано.** Сессия объявляет свой долгоживущий процесс через `SPA_SESSION_PID`;
`log_session_change.durable_process()` подтверждает его через `ps` **в момент записи** и кладёт
в запись `session_pid` + `session_pid_start` (verbatim `lstart`). Не подтвердился — поле не
пишется вовсе. `check_undelivered_work.session_state()` меряет в порядке: своя сессия →
долгоживущий процесс записи (**основной критерий**) → pid из идентификатора (как раньше);
совпадение времени старта — проверка ЛИЧНОСТИ процесса, поэтому переиспользованный ОС pid даёт
измеренное «это другой процесс», а не ложное «сессия жива». Те же поля прокинуты в шаг 0b
(`check_card_claim._classify`) — иначе улучшение до второго потребителя не доехало бы.
`scripts/agent_orchestrator.sh` экспортирует `SPA_SESSION_PID=$$` / `SPA_SESSION_ID=cycle-$$`
до вызова claude: эта оболочка ждёт весь цикл, т.е. и есть его долгоживущий процесс.

**Отличие от предложения карточки, осознанное:** pid НЕ берётся из `os.getppid()`. Родитель
однократной команды — оболочка, из которой её запустили; у человека в терминале она живёт
сутками, и такой «долгоживущий процесс» отвечал бы `ACTIVE` вечно ⇒ шаг 0a молчал бы о
недоставленной работе (fail-OPEN, класс #29/#31/#35–#38/#40). Durable-процесс существует только
там, где сессия объявила его сама; запрет пиннится тестом по поведению и по AST.

**Проверка.** +44 герметичных теста (`spa_core/tests/test_durable_session_id.py`), на чистом
`origin/main` — 26 красных / 18 положительных контролей; смежные 4 сюиты 174 passed до и после
(ни один существующий тест не изменён); живой смоук с НАСТОЯЩИМ процессом: `active` пока жив →
`not_confirmed` после смерти, та же запись без новых полей — прежнее `unknown`; догфуд: шаг 0a
на живом журнале байт-в-байт идентичен, шаг 0b по всем 105 карточкам — вердикты идентичны
(поведение изменится с первого цикла, который объявит процесс); mypy чисто, `lint_llm_forbidden`
163/0. Журнал: `docs/journal/2026-W31.md`, цикл #62.

**Осознанная граница:** захват в frontmatter карточки (`claimed_by`) durable-процесса не несёт —
там лежит только идентификатор сессии; измеримо стало её объявление в журнале.
