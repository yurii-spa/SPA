## Находка

Замер цикла #131 (2026-08-06, чистый sandbox-чекаут `origin/main` 11abfaf1c,
`scripts/audit_protocol_blindness.py --tier C`):

```
modules=180  counts={'blind_constant': 9, 'unchecked': 103, 'failed': 64, 'dormant': 4}
blind_equivalent=9  sensitive=0
```

* **103 unchecked** — ни один entrypoint не принимает protocol-контекст, то есть
  модуль в принципе не может дать протокол-специфичный сигнал;
* **64 failed** — падают с исключением (детали в `_meta.module_status.not_ok`
  живого `data/analytics_report_full.json`);
* **4 dormant** — возвращают результат, не коэрсируемый в score;
* **9 ok** — и все девять `blind_constant`: одинаковый score на тройке, на
  повторе, на всей широкой вселенной `_protocol_facts` и на несуществующем
  контрольном протоколе.

**Протокол-чувствительных модулей в Tier-C: ноль из 180.**

Цикл #131 закрыл ЧЕСТНОСТЬ артефакта (`_meta.protocol_differentiation` = NONE,
`protocol_specific: false` — число больше не притворяется замером по протоколу)
и намеренно НЕ трогал судьбу самих модулей: это отдельная задача со своим
радиусом.

## Что сделать

По директиве владельца «90 % должно РАБОТАТЬ, а не спать» — по каждому из 180
модулей должно быть либо доказанное подключение, либо **честное списание
карточкой**, но не молчание. Разумный порядок:

1. **64 failed** — самая дешёвая группа: посмотреть исключения, часть чинится
   тривиально (нет входного файла / нет ключа), часть — надгробия.
2. **103 unchecked** — модуль не принимает контекст. Решить пофамильно:
   дописать context-совместимый entrypoint (если данные протокол-специфичны в
   принципе) или списать.
3. **9 ok-констант** — либо подключить к `_protocol_facts` (как фаза 2 сделала
   для Tier-A/B), либо списать; сейчас они дают ровно ту константу 20.56,
   которая и была симптомом.
4. Каждое списание — записью, а не удалением: реестр `_module_registry` должен
   продолжать знать, что модуль есть и почему он не считается.

## Как понять, что готово

Для каждого из 180 модулей есть либо доказанная протокол-чувствительность
(вердикт `protocol_differentiation` = OK на живом прогоне), либо запись о
списании. Ежедневная метрика «% работающего слоя» считает Tier-C в знаменателе
(правка шага 4 в `spa-daily-90pct-audit/SKILL.md` уже сделана).

## Замер цикла #133 (2026-08-06): группа «64 failed» РАЗОБРАНА — вывод обратный ожиданию

записей, движок итерирует dict и получает строковые КЛЮЧИ:
`'str' object has no attribute 'get'` — 46 случаев из 64. Модуль не сломан; его
позвали не тем.

**Проверена очевидная починка — «провести их на `_protocol_facts`, как фазу 2
для Tier-A/B» — и она ОТКЛОНЕНА замером.** Новый инструмент
`scripts/audit_tier_c_wiring_feasibility.py` спрашивает не только «различается

## Цикл #136 (2026-08-06): группа «64 failed» разобрана. Поправка к карточке

**Пункт 1 плана («самая дешёвая группа: часть чинится тривиально») исходил из
неверной посылки. Чинить в этих модулях нечего — их не вызывали.**

### Что измерено (sandbox-worktree от `origin/main` 056320f9e, живое `data/` не тронуто)

1. Аудит воспроизведён точь-в-точь: `modules=180 counts={'blind_constant': 9,
   'unchecked': 103, 'failed': 64, 'dormant': 4}`.
2. Множество из 64 `failed` **ПОИМЁННО совпадает** с
   `_meta.module_status.not_ok.failed` живого прод-отчёта
   (`data/analytics_report_full.json`, 03:00Z): `identical: True`, разностей в
   обе стороны ноль. Значит отказы настоящие, а не артефакт харнесса, — это
   стоило проверить до того, как что-то чинить.
3. Разбор исключений по классам: **53 из 64 — `AttributeError`**, из них 46
   дословно `'str' object has no attribute 'get'` / `'dict' object has no
   attribute <доменное поле>`. Остальные — `TypeError: pools must be a list`,
   `ValueError: Missing required keys` и т.п.
4. Трассировка вскрыла КОРЕНЬ, и он один на всю группу — в агрегаторе, а не в
   модулях. `_ModuleAdapter._invoke` выбирал entrypoint через
   `inspect.signature(fn).bind(...)`, а `bind` проверяет **только арность**.
   Для `analyze(inp: BasisTradeInput)` привязка словаря проходит, модуль
   вызывается с контекстом вместо своего доменного входа и падает.
5. Замер радиуса: у **62 из 64** первый параметр entrypoint'а типизирован
   не-Mapping'ом (дата-классы, `List[...]`, `list[dict]`); только **2** реально
   принимают `dict` и падают по доменной причине.

### Что сделано

`run()` научился отличать «модуль сломан» от «агрегатору нечем построить его
вход»: **59 модулей** переехали `failed → unchecked` с НАЗВАННОЙ причиной
(`entrypoint requires non-mapping input, adapter supplies Mapping:
analyze(inp: BasisTradeInput); raised AttributeError: …`). Текст исключения
сохранён — тише не стало нигде.

Опубликованное число не шевельнулось, и это проверено: множество ok-модулей
до и после совпадает (9 = 9, поимённо), score ни у одного не изменился, новых
`failed` ноль, `dormant` 4 = 4. Менялся ЯРЛЫК у тех, кого и так не вызывали.

### Грабли, на которые наступил и которые закреплены тестом

Первая версия отказывалась ВЫЗЫВАТЬ entrypoint с не-Mapping аннотацией — и
погасила `defi_liquidation_cascade_risk_analyzer`, **работающий модуль Tier-A**
(блокирующий тир): он объявляет `analyze(positions: list[dict])`, но после
массовой обвязки protocol-контекстом принимает и контекст, а аннотацию ему
никто не обновил. **Аннотация в этом коде — не гарантия.** Поэтому разделение
делается ПОСЛЕ падения, а не вместо вызова: ни один модуль не перестаёт
исполняться. Поймал существующий `test_tier_a_protocol_context.py`; удержано
навсегда `test_wired_module_with_stale_annotation_still_runs`.
