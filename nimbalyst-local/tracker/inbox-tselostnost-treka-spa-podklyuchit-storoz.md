## Что случилось и почему это важно

Сводка SPA показывает «целостность трека: 28 из 61 дат расходятся, максимум $215.99, расходится и сегодняшний день» (`cycle_health_monitor.check_evidence_vs_curve`, own-32). Это расхождение ДВУХ записей об одних деньгах: `data/paper_evidence.json` (`equity_value`) против `data/equity_curve_daily.json` (`close_equity`). Причины уже разобраны в двух карточках бэклога (`agent-dve-zapisi-o-dengah-prichina-1-semantika-povtornoi-zapisi`, `agent-dve-zapisi-o-dengah-prichina-2-razryv-treka-10-06`), решение по переписыванию июня — у владельца (`own-32-evidence-vs-curve-diverge`).

Параллельно в отдельном репозитории `~/Documents/earn-defi` (BTC Signal Engine, paper-трек с 2026-09-02) тот же класс задач решён по построению, и там есть три вещи, которых у трека SPA НЕТ, хотя цепочка хешей над доказанной кривой (`spa_core/audit/equity_proof_chain.py` → `data/rates_desk/equity_track.jsonl`, 77 строк) и подписанный журнал аудита у SPA ЕСТЬ:

1. **Пересчёт трека из сырых входов** (`replay`): кривая заново вычисляется из сохранённых входов дня и обязана сойтись с цепочкой до цента. У SPA сторож сравнивает две ЗАПИСИ между собой, но ни одна из них не выводится заново из входов — поэтому «какая из двух правдива» ответить нечем.
2. **Сторож согласованности артефактов подключён к рантайму.** `spa_core/audit/data_integrity.py` (SPA-V430) существует, покрыт `test_data_integrity.py`, но у него НОЛЬ вызывающих в `spa_core`/`scripts` — класс ADR-259 «объявленный продукт, который никто не вычисляет».
3. **Commit-reveal решения книги**: хеш пакета (дата, входы, целевая раскладка, версия правил) публикуется ДО исполнения, пакет раскрывается через день. У SPA якоря есть у rates-desk (`anchors.jsonl`, `verify_spa.py`), у главной книги — нет.

Что это даёт: фраза с `/fundability` «каждое число проверяется одним верификатором» становится верной для самой equity-кривой, а не только для решений rates-desk; сторож «28/61» перестаёт быть вечным WARNING; у ревьюера появляется команда «пересчитай сам». Продуктово — тот же ров, что у BTC-движка: не идея, а проверяемая дисциплина.

## Что чинить (порядок и приёмка)

**Задача 1 — подключить существующий сторож (без нового кода, самая дешёвая).**
Вызвать `spa_core.audit.data_integrity` из `cycle_health_monitor` (или `agent_health`) с третьим исходом: `skip` входного файла = «не измерено», не «зелёное». Результат — ЧИСЛО в состоянии монитора + строка в `SYSTEM_BRIEFING`.
Приёмка: `grep -rn data_integrity spa_core/monitoring` ≠ пусто; тест формы вызова (как `test_cio_acceptance_guards_are_wired`); мутация «вызов снят» краснит тест; на живом дереве в сводке появилась строка сторожа.

**Задача 2 — измерить, хватает ли сохранённых входов для пересчёта (ЗАМЕР, не код).**
`_save_cycle_snapshot_safe` пишет снимок цикла. Взять 3 последних реальных дня, попробовать РУКАМИ вывести `close_equity` из снимка (APY по позициям × веса × время) и сравнить с `equity_curve_daily.json`. Три исхода: сходится до цента / не хватает полей (назвать каких) / формула начисления не восстанавливается.
Приёмка: записка в `docs/journal/<неделя>.md` с тремя датами и тремя вердиктами. Без этой записки задачу 3 НЕ начинать.

**Задача 3 — архив входов + пересчёт (side-car, аддитивно).**
Если задачи 2 хватило: новый append-only `data/cycle_inputs.jsonl` (снимок входов дня, `atomic_save`, hash-chained через существующий `spa_core/audit/hash_chain.py`) + модуль `spa_core/audit/replay_equity.py`: пересчитывает кривую из архива в памяти и сравнивает с `equity_track.jsonl`; отчёт `diffs`, `max_abs_diff`. Прогон по крону из `cycle_health_monitor` (третий исход при отсутствии архива). Историю до даты включения НЕ пересчитывать — она помечается `origin: pre-archive`, не дорисовывается.
Приёмка: 5+ тестов (детерминизм, подмена одного числа ⇒ diff, отсутствие архива ⇒ UNCHECKED, а не PASS); 7 живых дней подряд `diffs=0`; строка в `SYSTEM_BRIEFING`.

**Задача 4 — commit-reveal раскладки главной книги.**
В момент, когда цикл принял целевую раскладку и ДО «исполнения» (виртуального), считать SHA-256 пакета `(дата, snapshot_id из audit_trail, целевые веса, версия RiskPolicy v1.0, соль)`, писать в hash-chained `data/book_commitments.jsonl` и отправлять хеш в Telegram; на следующий день — раскрывать пакет. Страница проверки — расширить `verify_spa.py` (тот же канонический JSON + SHA-256; спека `docs/PROOF_CHAIN_SPEC.md`). Образец реализации: `~/Documents/earn-defi/earn_defi/commit_reveal.py` (stdlib, 4 теста).
Приёмка: 3 раскрытых пакета подряд сходятся у `verify_spa.py` на чистой машине; сайт показывает трейл (owner-gate: страница без чисел доходности).

**Задача 5 — закрыть «две записи о деньгах» (ЕСТЬ карточки, владелец).**
Не дублировать: выполнить `agent-dve-zapisi-o-dengah-prichina-1/2` после ответа `own-32`. С задачей 3 появится критерий, какая запись верна (та, что сходится с пересчётом).

## Что НЕ трогать

RiskPolicy v1.0, kill-switch, `spa_core/execution/`, money-path цикла, `data/` руками. Всё выше — чтение существующих артефактов и НОВЫЕ append-only файлы рядом. Исторические записи не переписывать; исправление = корректирующая запись. LLM запрещён (инвариант #3). Доставка — каталогами, приёмка `deployment_acceptance` до и после, `daily_cycle` не долгожитель (перезапуск не нужен). Полный CI-прогон ДО пуша, база падений сверяется поимённо.

## Риски честно

- Задача 3 добавляет шаг в цикл: обернуть в try/except с записью в состояние монитора — падение шага НЕ должно ронять цикл; файл может расти (~1 запись/день, копейки).
- Задача 2 может показать, что входов не хватает: тогда пересчёт возможен только с даты, когда архив начнёт писаться — это нормальный исход, его надо назвать, а не обойти.
- Ничего из перечисленного не улучшает доходность; это улучшает доказуемость трека — актив для go-live и внешнего капитала (docs/05 в earn-defi, `/fundability` в SPA).
