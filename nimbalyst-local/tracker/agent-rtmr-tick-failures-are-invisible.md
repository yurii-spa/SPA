пишет ли он вообще что-нибудь». Ровно один вышел аномалией: `com.spa.rtmr_sense` — `KeepAlive`,

Ложной тревоги нет: heartbeat свежий (`data/monitoring/sense_heartbeat.json`, ts обновляется),

## Что измерено

### Дефект 1 — сообщение об отказе тика не доходит до лога НИКОГДА

`spa_core/monitoring/rtmr_service.py::main()`:

```python
print(f"rtmr_service: started, sensors={...}, interval={interval}s (PAPER)", flush=True)   # ← flush есть
while True:
    try:
        tick(cfg, int(time.time()))
    except Exception as exc:
        print(f"rtmr_service: tick failed ({exc!r})")                                       # ← flush НЕТ
    time.sleep(interval)
```

Стартовая строка флашится, строка об ОТКАЗЕ — нет. stdout сервиса перенаправлен в файл ⇒ Python
использует блочную буферизацию (8 КБ), а процесс не завершается никогда ⇒ буфер не сливается.

**Воспроизведено на этой машине** (не рассуждение): 50 строк «tick failed», процесс жив, лог через
3 секунды — **8 байт** (только флашнутая стартовая строка). Затем `SIGKILL` (ровно то, что делает
`launchctl` при перезапуске KeepAlive-агента) — лог по-прежнему **8 байт**: все 50 сообщений об
отказе **потеряны безвозвратно**.

При интервале 45 с и ~70 байт на строку первое сообщение доходит до диска не раньше чем через
~117 отказов ≈ **1.5 часа непрерывного отказа**, а перезапуск агента обнуляет и это.

**Этот след уже стоил инцидента.** Разбор 29.07 (`docs/journal/2026-W31.md`, инцидент №2) описывает
портфель, застрявший в DEFENSIVE с 26.07 по 29.07 и уехавший в all-cash, и там же:
«убиты два процесса-сироты rtmr_service от 5 июля … **17 806 „tick failed (FileNotFoundError)“ в
логе**». Те 17 806 строк — это сирота, чей буфер СЛИВАЛСЯ (сирот убивали, буфер уходил на диск).
Штатный же агент в это время писал в свой лог ровно ничего.

### Дефект 2 — `alive: true` публикуется после 1-й из 3 стадий тика

`rtmr_service.py::tick()` — три стадии подряд:

```python
signals   = SL.run_tick(...)          # стадия 1: сенсоры + persist + ── ЗДЕСЬ ставится heartbeat ──
debounced = _debounce_stale(...)
A.react_and_apply(debounced, ...)     # стадия 2: лестница реакций (де-риск, posture, алерт)
reconcile_and_persist(...)            # стадия 3: САМООЧИСТКА posture (re-entry)
```

`sense_loop._heartbeat()` пишет литерально `{"ts": …, "sensors": …, "alive": true}` и вызывается
**внутри `run_tick`**, то есть в конце стадии 1. Стадии 2 и 3 идут ПОСЛЕ. Их падение ловится в
`main()` тем самым непечатающимся `print` ⇒ на диске остаётся **свежий heartbeat с `alive: true`**,
и ни одного признака, что аварийная стадия и самоочистка не выполнялись.

Это класс #29/#31/#35–#38/#40: утверждение об измерении, которого не было.

**Почему это дорого именно здесь.** Стадия 3 — единственный путь ВЫХОДА portfolio из DEFENSIVE
(`reconcile_and_persist`, счётчики re-entry), а `rtmr_posture_gate` в `cycle_gates` по DEFENSIVE
клампит все таргеты в 0. Отказ стадии 3 на каждом тике = книга заперта в all-cash, heartbeat
рапортует `alive: true`, лог молчит. Это ровно форма инцидента 26–29.07.

**Дубля нет (шаг 1а).** 29.07 в этом же файле починены ЧЕТЫРЕ бага (нулевая цена Binance,
`{} or _SLUGS`, слепой liquidity-сенсор, несохраняемые счётчики re-entry). Ни один из них — не эти
два: там чинили ЧТО сервис делает, здесь — то, что он **сообщает о себе**.

## Что сделано

Строго аддитивно, только наблюдаемость. Пороги, лестница реакций, `posture`, `cycle_gates`,
стоп-кран, интервалы — **не тронуты**.

1. `_report_stage_failure()` — `flush=True` и ИМЯ упавшей стадии (`sense` / `react` / `reconcile`)
   вместо одного непрозрачного текста на три разные поломки.
2. Стадии тика разделены и обёрнуты по отдельности: падение стадии 2 больше не отменяет стадию 3
   (самоочистку) — раньше исключение из `react_and_apply` уносило с собой и re-entry. Стадия 1
   по-прежнему пробрасывает: умерли сенсоры — heartbeat не пишется вовсе, и уход в stale и есть
   правильный fail-CLOSED-сигнал.
3. `SL.annotate_heartbeat()` — heartbeat перестал утверждать больше, чем измерил: `alive` теперь
   конъюнкция ВСЕХ стадий, добавлены `stages_ok` / `failed_stages` / `last_error`. `ts`/`sensors`
   НЕ перештампованы: сенсинг действительно был в тот момент, и `heartbeat_age_sec` обязан значить
   ровно то же, что значил (у него есть потребитель).
4. **Починен близнец этажом выше** (урок #37/#47 — фикс одной копии оставляет вторую):
   `/api/rtmr/status` считал `alive` ТОЛЬКО по свежести, поэтому публиковал «жив» о сервисе, у
   которого стадии 2/3 падали каждый тик. Теперь `alive` = свежесть И отсутствие упавших стадий,
   добавлены `heartbeat_fresh` / `stages_measured` / `failed_stages`.
5. `SL.stage_health()` отвечает **«не измерено»**, а не «упало», на heartbeat старого формата:
   живой сервис пишет старый формат до своего следующего рестарта, а рестарты owner-gated ⇒
   эскалация по отсутствующему ключу выдумала бы ложную тревогу на дни (память: чинить fail-OPEN
   через UNCHECKED, не через эскалацию).

## Acceptance criteria

- отказ ЛЮБОЙ из трёх стадий попадает в лог немедленно (флашнут) и с именем стадии;
- отказ стадии 2 не мешает стадии 3 выполниться;
- heartbeat после отказа стадии 2/3 не утверждает `alive: true`;
- положительные контроли: успешный тик по-прежнему даёт `alive: true` и все стадии; отказ стадии 1
  (сенсоры) ведёт себя как раньше; `heartbeat_age_sec` возвращает то же, что и до правки;
- инвариант #16: ни один существующий ассерт не ослаблен и не удалён.

**Не входит:** RiskPolicy / kill-switch / пороги / лестница реакций / `cycle_gates` / живой трек /
launchd / `landing/**`.
