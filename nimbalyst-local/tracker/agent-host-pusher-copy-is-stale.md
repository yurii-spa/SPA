**Как найдено (цикл #53, 2026-07-31).** Доставка цикла легла на `main` **ВОСЕМЬЮ коммитами вместо
одного** — ровно то поведение, которое цикл #49 закрыл карточкой `agent-push-batch-per-file-commits`
(набор файлов уезжает одним коммитом через Git Data API). Регрессии в доставленном коде НЕТ:
на `origin/main` `push_to_github.py` содержит `batch_push` и маршрутизирует туда любой набор > 1
файла. Разошлась КОПИЯ.

## Что не так

`git diff origin/main -- push_to_github.py` в хост-репо: **1 файл, +7 / −574**. Копия в
`/Users/yuriikulieshov/Documents/SPA_Claude/push_to_github.py` — до-#49: `grep -c batch_push` даёт
**0** против **2** на origin. Хост-дерево живёт на своей ветке (`env-setup-v3`) и, как записано в
памяти проекта, штатно дрейфует от origin, потому что пуши идут прямо в origin через API.

**Почему это ловушка, а не частный промах.** `CLAUDE.md` в разделе «Команды» инструктирует
буквально:

```
python3 push_to_github.py --files /abs/path/file.py --message "..."
```

— то есть относительный путь от корня хост-репо. Сессия, делающая ровно то, что написано в
`CLAUDE.md`, получает **до-#49** доставку: N файлов = N коммитов, промежуточные состояния `main`
могут быть красными. Работа цикла #49 при этом на месте и исправна — она просто не участвует.

**В этом цикле обошлось, и это измерено, а не предположено.** Порядок, в котором легли коммиты
(сначала фикс сканера `dbcdbeebc`, затем новые тесты `21be734ef`, и только потом ужесточённый
потолок `1b7e9e3d9`), оказался безопасным: каждый из трёх кодовых коммитов прогнан на чистом
чекауте — 20 passed / 23 passed / 23 passed, красного состояния на `main` не было. Обратный порядок
(потолок 2284 раньше фикса сканера) дал бы `main` с наблюдаемыми 4049 против потолка 2284, то есть
красный CI. Порядок здесь — везение, а не свойство.

## Что предлагается сделать

Варианты (выбирает исполнитель, решение записать):

1. **Убрать саму возможность позвать не ту копию:** в `CLAUDE.md` заменить относительный вызов на
   явный (`python3 "$(git rev-parse --show-toplevel)/push_to_github.py"` не годится — в worktree
   это даст ту же ветку; нужен вызов копии ИЗ рабочего дерева цикла) + короткое правило «пушер
   берётся из того дерева, которое ты собрал и протестировал».
2. **Само-проверка версии в пушере:** при старте сверять свой хеш/наличие `batch_push` с origin и
   при расхождении честно отказывать (fail-CLOSED, инв. #2), а не молча доставлять по-старому.
   Требует сети до пуша — она и так есть.
3. **Подтянуть хост-копию к origin** — разовое лечение симптома; без (1)/(2) разойдётся снова, так
   как хост-дерево дрейфует по построению.

Рекомендация: (2) + (1). (3) — как немедленная мера, но не вместо.

**Смежное:** в памяти проекта записано, что копий `push_to_github.py` в системе ДВЕ и они «должны
оставаться синхронными» (autopush). Эта карточка про третий экземпляр расхождения — хост-репо
против origin; проверить заодно копию, которую зовёт `auto_push.sh`.

**Не входит:** переписывание самого механизма доставки (Git Data API уже сделан циклом #49) и
правка `log_session_change.py` / шага 0a — отдельные карточки.
