## Как найдено

Не воспроизводил намеренно — наткнулся в цикле #81, когда подбирал работу, осиротевшую **два раза
подряд** (#79 написал фикс красного CI и умер, #80 подобрал и умер), и первым делом решил
застраховаться чекпойнтом.

## Дефект 1 — первый чекпойнт новой сессии падает с трейсбеком

```
$ checkpoint_deliver.py push --session cycle81 --files …
  File "/private/tmp/spa_wt_c81/push_to_github.py", line 727, in _api
    with urllib.request.urlopen(req) as resp:
urllib.error.HTTPError: HTTP Error 404: Not Found
```

Последовательность (измерена по состоянию origin до/после):

1. `_ensure_branch` (`checkpoint_deliver.py:215`) — `GET /git/ref/heads/wip/cycle81` → **404**
   (ветки ещё нет), это ожидаемо и обработано; далее `POST /git/refs` → ветка **создана**;
2. затем `push_to_github.py:734` делает **свой** `GET /git/ref/heads/{branch}` по только что
   созданной ветке → **404** → **необработанный `HTTPError`, процесс падает**.

Что ветка действительно создалась — проверено сразу после падения:
`GET /git/refs/heads/wip` → `refs/heads/wip/cycle81 d995a9573`.
**Повторный запуск той же команды прошёл без единой ошибки** (`ref: existed`, коммит `e8f98af75`,
7 файлов).

**Цена дефекта ровно противоположна назначению инструмента.** `checkpoint_deliver.py` построен
циклом #65 для того, чтобы работа переживала смерть сессии. Но первый же его вызов в сессии
завершается трейсбеком — и сессия, которая умрёт на этом месте (а умирают они именно в конце,
см. `agent-verification-outlives-cycle-budget`), останется **без** чекпойнта, то есть ровно в том
состоянии, от которого инструмент защищает.

**Граница честности:** причина 404 на свежесозданном ref **не изолирована**. Наблюдение —
одноразовое (второй запуск прошёл), поэтому наиболее вероятна согласованность-в-конечном-счёте
refs-API GitHub сразу после `POST /git/refs`. Утверждать это как доказанное я не могу и не буду —
для карточки важно, что **воспроизводимо наблюдаемо падение, а не его первопричина**.

## Дефект 2 (процессный) — инструмент просто не вызывают

На `origin` **единственная** ветка `wip/*` — `wip/cycle81`, созданная этим циклом.

То есть циклы **#79 и #80, оба осиротевшие на одной и той же задаче**, чекпойнт **не делали ни
разу**, хотя шаг 0a-bis в протоколе есть с цикла #65. Механизма, который обязывает или хотя бы
напоминает, нет: шаг — текст в документе, а не проверка. `main` пробыл красным ~4 часа именно
поэтому.

## Что предлагается сделать

1. **Дефект 1:** `push_to_github` при GET только что созданного ref не должен падать —
   ретрай с малым бэкоффом на 404 ИЛИ передавать уже известный sha из `_ensure_branch`, не
   перечитывая ref. Отказ обязан остаться fail-CLOSED: «не смог прочитать ref» ≠ «ветки нет».
2. **Дефект 2:** обсудить, чем сделать шаг 0a-bis наблюдаемым (например, шаг 0a печатает
   «работа объявлена, чекпойнта нет» — измерение, а не запрет).

## Acceptance criteria

  «404 на первом GET, 200 на втором»;
- существующие 57 тестов `checkpoint_deliver` не ослаблены (инв. #16), правки аддитивные.
